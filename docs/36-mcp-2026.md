# MCP 2026: протокол, discovery, transport и trust boundaries

Глава 6 объяснила роль MCP, а глава 35 — как собирать контекст для решения. Здесь разберём совместимость конкретных revisions и диагностируем обмен с server. Для этого нужно получить реальные данные: прочитать конфигурацию маршрутизатора, найти ticket, проверить состояние deployment. Сами системы уже имеют API и CLI. Зачем между ними и harness ставить ещё один протокол?

Представьте команду, которая написала сетевой adapter для одного агента. Затем его нужно подключить к другому harness, IDE и внутреннему помощнику SRE. В каждой интеграции снова описывают операции, разбирают ответы и решают, как показать доступные возможности. **Model Context Protocol, или MCP, стандартизирует этот интерфейс обмена, но не выбирает за инженера безопасные операции и не управляет жизненным циклом задачи.** Хороший adapter можно переиспользовать; плохой через MCP тоже становится переиспользуемым.

Разберём подключение учебного сервера `network-lab`, который читает состояние `lab-edge-1`. Сначала отделим роли и версии, затем пройдём один вызов до результата, выберем transport и проверим границы доверия. Имена tools и данные примера - учебный contract, не встроенные методы AX и не готовый API производителя оборудования.

## Что именно соединяет MCP

MCP server - программа, которая предоставляет возможности через протокол. Это может быть локальный subprocess или удалённый сервис. **Host** - приложение, в котором работает агент; **client** - компонент host, обслуживающий взаимодействие с определённым server. LLM не устанавливает TLS-соединение и не хранит OAuth token: она предлагает действие, а harness и client организуют его выполнение. Такое разделение следует из [архитектуры MCP](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture).

В нашем примере host отвечает за goal, контекст, policy и журнал задачи. Client переводит доступный tool в представление, понятное модели, формирует MCP request и разбирает response. Server проверяет допустимость обращения, вызывает сетевой API и возвращает результат. Устройство остаётся источником истины для своей конфигурации; ни client, ни текст ответа модели не заменяют эту проверку.

Отсюда простой диагностический приём: вместо «MCP сломан» спросите, на какой границе нарушен contract. Модель выбрала неправильный tool? Client не поддерживает revision? Proxy задерживает stream? Server не может обратиться к устройству? Эти неисправности требуют разных исправлений, хотя пользователь видит один неудачный вызов.

## Когда MCP оправдан, а когда достаточно API

MCP полезен там, где одну интеграцию будут использовать разные совместимые hosts или требуется единый способ предоставлять каталог возможностей. Он добавляет protocol adapter, проверки совместимости и ещё одну эксплуатационную зависимость. Это разумная цена за переиспользование, но не обязательный налог на каждый agent loop.

| Ситуация | С чего начать | Что определяет выбор |
| --- | --- | --- |
| Один сервис, один harness, несколько фиксированных операций | Прямой API или library adapter | Меньше слоёв; contract и проверки всё равно нужны |
| Одинаковая интеграция для нескольких hosts | MCP server | Совместимые версии, понятные tools, владелец сервиса |
| Локальный анализ файлов в ограниченной среде | CLI/tool wrapper или stdio MCP | Нужен ли общий интерфейс; как ограничить filesystem |
| Общий инструмент для многих tenants | Удалённый MCP с отдельным policy layer | Identity, изоляция, quotas, отказоустойчивость |
| Обязательный порядок destructive steps | Детерминированный workflow и executor | MCP может доставлять вызовы, но не заменяет transitions |

Перед внедрением проверьте не количество tools в каталоге, а полезность интерфейса. Если для простого read вызова модель должна выбирать среди сотни похожих имён, интеграция усложняет решение. Лучше предоставить узкую операцию для конкретной задачи и расширять каталог по наблюдаемой потребности.

## Tools, resources и prompts решают разные задачи

[Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) - вызываемые операции: запрос к API, поиск или вычисление. Tool не обязательно меняет состояние. `network.read_route` читает маршрут, а `network.apply_config` меняет конфигурацию; категория одна, риск разный. Для каждого tool нужны понятные input и result contracts.

[Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources) предоставляют адресуемый контент через URI. Учебный `inventory://lab/devices/lab-edge-1` может обозначать карточку устройства; resource template - такие карточки для разных devices. Host решает, что включать в контекст. URI не означает, что нужно автоматически скачать всю связанную документацию.

[Prompts](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts) - получаемые у server шаблоны сообщений, например `diagnose_packet_loss` с аргументами device и prefix. Они помогают начать задачу, но не являются policy engine. Skill из главы 6 может описывать более широкую процедуру со scripts и references; MCP prompt сам по себе этого пакета не гарантирует.

Для `network-lab` удобно разделить inventory resource, read tool и диагностический prompt. Не стоит превращать всё в `run_anything(text)`: executor снова будет угадывать намерение из естественного языка. И обратная крайность не нужна - поддерживать все три категории, если задаче достаточно двух read tools.

## Две модели протокола нельзя смешивать

Reference point книги - **MCP `2026-07-28`**. По [правилам совместимости](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) это modern-модель с metadata каждого запроса. Legacy revisions, включая `2025-11-25`, используют handshake `initialize` и `notifications/initialized`. На HTTP session identifier в legacy зависит от реализации; нельзя утверждать, что он всегда обязателен.

| Contract | Legacy | 2026-07-28 |
| --- | --- | --- |
| Версия и capabilities | Устанавливаются при initialization | Передаются в каждом request |
| Protocol session | Есть initialization lifecycle | Нет скрытой связи вызовов через session |
| Server-to-client interaction | Отдельные server requests | Дополнительный ввод через MRTR results |
| HTTP notifications | Возможен отдельный GET stream | Request-scoped stream; подписки через listen request |

Последние два различия раскрывают [message patterns](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns) и [HTTP binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http). Это не косметика: modern-only client и legacy-only server не становятся совместимыми от одинакового URL. Dual-era реализация должна явно поддерживать оба поведения. Не пытайтесь лечить любой `400` добавлением `Mcp-Session-Id` или удалением metadata.

В deployment contract фиксируйте revision протокола отдельно от версии SDK, server image и tool schema. Надпись «MCP supported» не отвечает на вопрос, какой transport и какие extensions действительно работают. Проверяйте пару client/server в acceptance tests, включая заведомо несовместимую revision и понятную диагностику отказа.

## Discovery не является поиском доверенных серверов

Нужно различать три шага. Адрес или launch command поступает из управляемой конфигурации host. Затем `server/discover` сообщает поддерживаемые versions и capabilities. Наконец, `tools/list`, `resources/list` и `prompts/list` раскрывают соответствующие каталоги. Метод `server/discover` обязателен для modern server, но предварительный вызов необязателен для client: это определено в [Discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover).

Discovery не сканирует сеть и не доказывает, что server заслуживает доверия. `serverInfo` - самоописание для отображения и диагностики, а не удостоверение identity. Аналогично, `clientInfo.name` не заменяет authenticated principal. Имя `network-lab` может указать любой process.

Для допуска server проверяйте владельца, адрес или digest пакета, доступные ему сети и credentials. Для каждого tool храните связь с конкретной интеграцией, а не только короткое имя: два servers могут иметь `search`. В audit record должны сохраняться и source server, и исходный tool name, даже если host показывает модели собственный alias.

Каталог также является входными данными. Description может содержать вредоносную инструкцию; annotation `readOnlyHint` не является доказательством отсутствия side effects. Разрешённый список операций и их risk classification должны исходить из проверенного contract. Скрыть tool в интерфейсе полезно, но server всё равно обязан проверять каждый вызов.

Большой каталог читайте с pagination и ограничением объёма; модели передавайте только подходящие для задачи операции. В local cache связывайте описание с server configuration, authenticated scope и contract revision. Не используйте каталог одного tenant для другого. Изменение credentials или schema требует повторной проверки доступности, а не продолжения работы по сохранённому списку.

## Один read вызов от предложения до evidence

Продолжим задачу главы 35: проверить маршрут `192.0.2.0/24` в `VRF LAB` на `lab-edge-1`. Модель предложила `network.read_route`; harness проверил scope задачи и аргументы. Client отправляет следующий учебный request по stdio. Здесь нет headers, а JSON для читаемости разложен по строкам; на stdio он передаётся одной JSON-строкой.

```
{
  "jsonrpc": "2.0",
  "id": "route-read-17",
  "method": "tools/call",
  "params": {
    "name": "network.read_route",
    "arguments": {
      "device": "lab-edge-1",
      "vrf": "LAB",
      "prefix": "192.0.2.0/24"
    },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "lab-harness", "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

Обязательные protocol version и client capabilities находятся в `params._meta`; пустой capabilities object здесь означает, что client не заявляет дополнительных возможностей. Эти поля и формат JSON-RPC определены в [base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic/index). Request ID связывает response с данным запросом. Он **не является idempotency key** для бизнес-операции.

В input contract учебного tool все три arguments обязательны, лишние поля запрещены. Но JSON Schema с типом `string` не докажет, что prefix является корректной сетью CIDR, а device принадлежит caller. CIDR проверяет semantic validator, принадлежность - authorization layer. Для result contract заранее задайте типы полей: `present` boolean, `config_revision` string, `observed_at` timestamp. При изменении semantics обновляйте contract и test fixtures, даже если имя tool осталось прежним.

Server проверяет caller и разрешённое устройство, читает маршрут и возвращает учебный result. Названия полей внутри `structuredContent` принадлежат нашему tool contract, а не MCP:

```
{
  "jsonrpc": "2.0",
  "id": "route-read-17",
  "result": {
    "resultType": "complete",
    "isError": false,
    "content": [{
      "type": "text",
      "text": "Route present; config revision 17; raw artifact route-17"
    }],
    "structuredContent": {
      "device": "lab-edge-1", "vrf": "LAB",
      "prefix": "192.0.2.0/24", "present": true,
      "config_revision": "17",
      "observed_at": "2026-10-03T08:11:00Z",
      "raw_ref": "artifact://run-17/route-17.json"
    }
  }
}
```

Harness проверяет result schema, scope и freshness перед записью evidence. Route present не означает, что packet loss исчез или причина найдена. Наблюдение нужно сопоставить с telemetry, а revision 17 - с состоянием, на которое опирается план. Невалидный result не становится фактом только потому, что транспорт доставил JSON.

Для HTTP JSON body остаётся тем же. Client добавляет `Content-Type: application/json`, `Accept: application/json, text/event-stream`, `MCP-Protocol-Version: 2026-07-28`, `Mcp-Method: tools/call` и `Mcp-Name: network.read_route`, а для защищённого endpoint - credentials. Headers должны соответствовать body; source of truth - body. Если schema использует `x-mcp-header`, client также обязан корректно зеркалировать отмеченные параметры. Поэтому рабочий SDK adapter надёжнее вручную написанного HTTP wrapper.

## Выбор transport меняет эксплуатацию, но не полномочия

Стандартные bindings - [stdio и Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports). В [stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio) client запускает subprocess и обменивается JSON-RPC через stdin/stdout. Stdout нельзя смешивать с debug prints; logs идут в stderr. Потеря child process требует нового подключения, но не оправдывает слепой повтор write.

Выбирайте stdio для локального adapter, когда host управляет запуском и удобно ограничить его filesystem и environment. Сам pipe не создаёт sandbox. Пакет server исполняет код с выданными OS permissions; launch command нужно рассматривать так же внимательно, как установку обычного executable. Закрепляйте версию зависимости, проверяйте происхождение и не выдавайте ей весь environment агента.

Streamable HTTP удобнее для общего сервиса, независимого rollout и централизованных quotas. За это придётся обслуживать DNS, TLS, identity, балансировщик и streams. Для modern revision нет protocol sessions и отдельного GET notification endpoint; ответы могут приходить JSON или request-scoped SSE. Не переносите настройки старого HTTP+SSE tutorial без проверки revision.

Практический признак неправильного proxy: короткие ответы проходят, а progress появляется только в конце или connection закрывается во время нормальной работы. Проверяйте buffering, idle timeout и общий deadline, а не просто увеличивайте retries. Раскладывайте latency на очередь, сеть, обработку server и target API. Backoff с jitter полезен при временном перегрузе, но denied или malformed request не исправляется ожиданием.

## Stateless transport не отменяет state приложения

В modern MCP каждый запрос несёт свой protocol context. Это позволяет распределять независимые запросы между replicas без скрытой conversation session. Но workflow, transaction и длительный job могут иметь состояние. Их explicit handles нужно передавать по contract, а хранить - там, где application обеспечивает требуемую durability.

Если `network.start_capture` вернул `capture_id`, следующий status call должен явно передать этот ID. Replica B сможет ответить только при наличии соответствующего backend state. Объявить server stateless и оставить capture map в RAM replica A - не масштабирование, а потеря доступности после первого переключения.

Handle требует проверки владельца, tenant и срока жизни; его знание не должно давать доступ к чужой операции. Для authentication и replay protections следуйте [security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices). Application ledger хранит handle, состояние и результаты отдельно от transcript. Это та же граница между context и durable state, которую мы провели в главе 35.

Для длительной работы можно использовать backend job API либо согласованное [Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview). Extension не следует считать обязательным core capability: проверьте его поддержку и fallback у обеих сторон. MCP task handle, AX Task и task внутри harness - разные идентификаторы. Явно храните их соответствие; совпадение слова не означает общего lifecycle.

При поддержке Tasks client заявляет extension в capabilities, server может вернуть `resultType: task` и `taskId`. Client сохраняет ID и опрашивает `tasks/get` с учётом рекомендованного polling interval; дополнительный ввод передаёт через `tasks/update`. Отмена через `tasks/cancel` cooperative: она не доказывает остановку underlying job и не является rollback. После потерянного create response задача могла уже появиться - возвращаемся к application operation ledger.

## OAuth открывает endpoint, policy разрешает действие

У защищённого HTTP MCP есть отдельные роли: client обращается к resource server, authorization server выдаёт ему token. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) описывает discovery OAuth metadata и применение access tokens. Для stdio эта HTTP OAuth-схема не используется; credentials обычно поступают через environment. Авторизация в MCP optional, поэтому наличие протокола само по себе не доказывает, что server защищён.

Условно OAuth отвечает: «этот caller может обратиться к network-lab с данным scope». Application policy отвечает точнее: «этот principal в этой Task может читать lab-edge-1, но не production-edge-1 и не применять configuration». Approval на изменение - ещё одно решение, связанное с конкретным действием. Ни успешный login, ни token с широким scope не заменяют его.

Нужно разделять две credential boundaries. Token client предназначен для MCP server. Credential server предназначен для сетевого API. [Security requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations) запрещают token passthrough: входной token нельзя без проверки назначения просто переслать downstream. Для upstream OAuth нужен отдельный token, выданный соответствующим authorization server.

В учебном adapter это означает: server узнаёт caller из проверенной identity, затем разрешает доступ к device и использует подходящий upstream credential. Поле `tenant`, придуманное моделью, не является authenticated identity. Если service account server имеет доступ ко всем устройствам, server обязан сузить его для каждого caller; иначе он становится привилегированным посредником, которому можно заказать чужую работу.

Не кладите tokens в tool arguments, context, URL query или audit payload. При `401` client восстанавливает authentication по поддерживаемому flow; при `403` выясняет scope/policy и останавливает запрещённую операцию. Автоматически запрашивать всё более широкие права, пока вызов не пройдёт, нельзя: повышение доступа должно соответствовать задаче и внешнему решению пользователя или policy.

## Дополнительный ввод не равен разрешению операции

Server может потребовать дополнительную информацию. В modern revision [MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) передаёт её через `resultType: input_required`, `inputRequests` и, при необходимости, opaque `requestState`. Client повторяет исходный метод с `inputResponses`, новым JSON-RPC ID и точным полученным `requestState`. Это продолжение interaction, а не generic retry после timeout.

Harness решает, какие input requests обслужить. Например, уточнить VRF у пользователя допустимо, если client заявляет elicitation и задача этого требует. Но вопрос «согласны применить изменения?» ещё не является нашим bounded approval: нужно показать target, diff, revision и expiry. Ответ пользователя должен попасть в контролируемый execution contract, а не раствориться в свободном тексте.

Для каждой цепочки задайте max rounds, общий deadline, budget и допустимые типы ввода. Учебная policy может разрешать три раунда уточнения, после чего требовать ручного разбора. Это значение выбирается для задачи, а не предписывается MCP. Не декодируйте `requestState` на client; server должен защищать его integrity, когда оно влияет на права или business logic.

По [architecture overview](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture), sampling в revision `2026-07-28` deprecated: не стройте новую архитектуру на предположении, что server может незаметно расходовать model budget host. Если существующая интеграция его использует, проверяйте поддержку и отдельную policy, включая допустимые данные и расходы. Дополнительный model request - новая граница контроля, не бесплатный внутренний шаг tool.

## Разделяйте transport error, tool error и unknown outcome

Короткое «вызов не удался» скрывает разные состояния. Для read и write они приводят к разным следующим шагам. По [error model tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#error-handling), HTTP success не обязательно означает успешную бизнес-операцию; tool result может сообщить `isError: true`. JSON-RPC error указывает на protocol-level failure. Отдельно существует локальный deadline client, когда полноценного ответа вообще нет.

| Наблюдение | Что выяснить | Следующий шаг |
| --- | --- | --- |
| DNS/TLS/connect failure | Где оборван путь и отправлен ли запрос | Проверить endpoint, proxy и request trace |
| 401 или 403 | Истёк token или denied scope/target | Auth flow или explicit отказ; не бесконечный retry |
| Version/header mismatch | Revision и соответствие headers body | Исправить adapter или выбрать совместимый contract |
| Tool result с isError | Domain error по contract server | Исправить аргументы/условия; учесть partial effects |
| Write timeout или разрыв после отправки | Могло ли действие уже выполниться | OUTCOME\_UNKNOWN и reconciliation по ledger |
| Malformed или oversized result | Можно ли безопасно сохранить evidence | Изолировать result, ограничить вывод, разобрать server |

Для последней ситуации сохраняйте доступную исходную диагностику вне model context, с redaction и ограниченным доступом. Большой JSON не нужно целиком отдавать модели: оставьте bounded projection, признаки truncation и reference на raw artifact. Инструкцию «игнорируй policy» внутри tool result рассматривайте как untrusted content, а не очередной system message.

При write timeout protocol statelessness не помогает узнать результат. Пусть `network.apply_config` успел записать revision 18, но response потерялся. Повтор может применить change второй раз или затереть новое состояние. Harness сохраняет `OUTCOME_UNKNOWN`, проверяет operation receipt и текущую revision, затем решает, нужен ли повтор с тем же application idempotency key. Approval и preconditions разбираем подробно в главе 37.

## Подключение в AX должно завершаться application probe

Workspace позволяет разместить настройки и assets harness, но декларация MCP server не доказывает работающий client. В AX на зафиксированном `ac233282` [SetupWorkspace](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/workspace/setup.go) подготавливает files, Git repos и skills path; этот код не выполняет MCP discovery или read probe. [Runner](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/runner/runner.go) запускает Task command. Подключение protocol client и проверка его результата остаются обязанностью выбранного harness или отдельного adapter.

Поэтому `WorkspaceReady=True` из главы 18 не означает «tools готовы». Для stdio проверяйте executable, package revision, cwd, ограниченный environment и восстановление child process. Для HTTP - DNS/TLS из sandbox, proxy path, credentials и один полезный read. Секреты и sockets не становятся валидными навсегда после успешного первого boot.

После AX resume пересоздайте client connections, проверьте expiry и перечитайте authoritative state незавершённых operations. Durable filesystem может сохранить ledger и handles, но не живую TCP connection. Если status зависит от старой replica-local RAM, устраните этот application contract до запуска нескольких replicas.

## Учебный acceptance test перед production

Начните с simulator или отдельного lab device. Для упражнений с write используйте специально ограниченный target, где изменение можно проверить и восстановить; production credential здесь не нужен. Тест должен доказывать не только happy path, но и сохранение границ при сбое.

1. **Compatibility.** Пройти discovery и read на заявленной revision; несовместимый client получает понятный отказ. Не маскировать protocol error общим «server unavailable».
2. **Scope.** Разрешённый caller читает lab-edge-1; чужой tenant и target вне lab получают отказ и не оставляют успешного обращения к device API.
3. **Contract.** Неверный prefix, незнакомое поле и невалидный result обнаруживаются там, где contract этого требует. Зафиксировать inputSchema и outputSchema test fixtures.
4. **Untrusted content.** Встроенная в description или result инструкция о расширении доступа не проходит policy. Raw content не попадает в привилегированный prompt.
5. **Failures.** Отключить stdio child или HTTP server, замедлить upstream, потерять response. Read восстанавливается в пределах budget; write идёт в reconcile, а не дублируется.
6. **Identity and expiry.** Истёкший token и чужой handle отклоняются. OAuth metadata/redirects не обходят вашу egress policy и не открывают произвольный внутренний endpoint.
7. **Limits.** Проверить большой output, pagination и лишний раунд MRTR. Harness останавливается предсказуемо, сохраняя причины и reference на evidence.
8. **Recovery.** Возобновить AX Task и сопоставить harness operation, MCP handle и target receipt. Одно логическое действие не должно превращаться в два после restart.

Полезный audit record связывает Task, authenticated principal, server identity из управляемой конфигурации, tool contract revision, request ID, operation ID, policy result и verification. Отдельно измеряйте connect/auth failures, protocol failures, domain errors, latency и unknown outcomes. Один aggregate success rate не покажет, что read работает, а writes теряются после timeout.

После этих проверок инженер может ответить на три вопроса: зачем здесь MCP вместо прямого adapter, какую совместимость обеспечивают обе стороны и кто ограничивает реальные действия. MCP делает интеграцию понятнее и переносимее. Чтобы она стала безопасной, нужно продолжить цепочку до исполнителя, подтверждения и проверки результата. Это тема следующей главы.
