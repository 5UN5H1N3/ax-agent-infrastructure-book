# Антипаттерны

**Профиль главы на 16.10.2026:** AX `ac233282` и Substrate `df788825`, полные SHA приведены в главе 26. Разобранные обязанности приложения не считаются встроенными возможностями AX. Практический пример работает только с локальными учебными SQLite-базами; стенд и внешние операции не запускаются.

Исследование `billing` закончено, отчёт готов к публикации. В первом прототипе всё делает один агент: читает репозиторий, запускает тесты и отправляет результат. Ему выдали общий token, а на сетевую ошибку добавили повтор. Решение понятно: нужно было получить работающий путь и показать его пользователю.

Через месяц выясняется, что после timeout иногда появляются два отчёта. Инженер добавляет retry ещё и в coordinator, чтобы работа точно завершалась. Дубликатов становится больше. Коллега предлагает улучшить prompt, запретив агенту повторную публикацию. Но после restart в разговоре нет надёжной записи о том, что сервер успел сделать.

Разберём, как такие решения складываются в отказ, и исправим один участок на воспроизводимом примере. Затем рассмотрим соседние привычки: слишком широкие полномочия, Task на каждый шаг, постоянно открытый debug, смешение snapshot и backup, оценку сервиса по зелёным статусам. Нас интересует механизм проблемы и граница, на которой его можно изменить.

## 1. Почему удобное решение становится антипаттерном

**Антипаттерн** — повторяющийся способ решения, который сначала даёт локальную пользу, а затем систематически создаёт нежелательные последствия. Один большой процесс легче запустить. Общий token упрощает интеграцию. Retry скрывает случайный отказ. Проблема возникает, когда условия, делавшие это приемлемым, изменились, а устройство системы осталось прежним.

Например, общий worker вполне подходит для доверенной обработки одинаковых файлов. Когда в нём начинают выполнять код из чужих репозиториев, меняется граница доверия. Теперь одна работа способна повлиять на соседнюю или воспользоваться доступными worker credentials. Разделение jobs по имени очереди само по себе не меняет права процесса, который их исполняет.

Поэтому полезнее спросить, что изменилось в нагрузке, данных или полномочиях, чем сразу объявлять инструмент неправильным. В главе 30 мы выбирали обязанности платформы. Здесь проверим, не пытается ли какой-то компонент незаметно выполнить чужую обязанность: prompt — выдать разрешение, snapshot — сохранить внешнюю транзакцию, readiness — подтвердить доставку отчёта.

## 2. Один агент получает слишком много полномочий

У исследователя `billing` есть причина читать исходники и выполнять ограниченные проверки. Для публикации нужен другой набор прав: записать выбранный отчёт в определённый проект. Удаление чужих документов и изменение deployment для этой работы не требуются. Если универсальный tool и общий token позволяют всё сразу, ошибка выбора действия становится ошибкой с широкими последствиями.

Вредоносная инструкция в README может предложить «проверить окружение» и отправить секреты на внешний адрес. Уязвимость проявляется не в том, что README существует, а в том, как прочитанный текст получает влияние на исполнителя с реальными правами. [OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) выделяет избыточную функциональность, полномочия и автономность как разные источники такого риска.

В нашей системе coordinator хранит цель, входной commit и разрешённые действия. Исследователь получает нужный checkout и read-only доступ к результатам соседних шагов. Исполнитель тестов работает в ограниченной среде. Публикацию выполняет узкий adapter: принять идентификатор проверенного отчёта и записать его в разрешённое место. Произвольная строка shell или произвольный URL для этой обязанности не нужны.

Такое разделение можно сделать в одном приложении с разными компонентами и credentials. Отдельные агенты и Tasks понадобятся там, где требуется самостоятельная среда, срок жизни или изоляция. Если два «агента» имеют один admin token и одинаковый доступ к данным, названия ролей ещё не уменьшили возможный ущерб. И наоборот: один harness может последовательно выполнять несколько безопасных шагов в общей границе.

Проверяйте полномочия в исполнителе и конечной системе. Скрытый из списка tools метод остаётся доступным, если агент может вызвать тот же API через общий HTTP client. Sandbox ограничивает локальную среду, а права token продолжают определять доступ к удалённому хранилищу. Главы 23–24 подробно разбирают эту композицию.

## 3. Разрешение и проверку результата поручают модели

Модель полезна, когда нужно интерпретировать цель, предложить исправление или объяснить изменение. Обязательные поля запроса, совпадение tenant, лимит расходов и разрешение на запись проверяются по формальным правилам. Если модель каждый раз решает их заново из текста, смена контекста способна изменить то, что должно оставаться постоянной границей.

Представим, что в prompt написано «публикуй только в тестовый проект». Исполнитель принимает `project_id` из model output и использует привилегированный token. Сам prompt ничего не мешает передать production project. Удобнее выдать adapter заранее проверенный handle проекта, связать его с доверенной identity и проверять разрешение непосредственно перед записью. Формат tool request помогает ограничить вход, но схема JSON не заменяет проверку права на конкретный объект.

Approval тоже относится к конкретному действию. Человек видел отчёт для commit A; перед отправкой harness построил отчёт для commit B. Старое «да» не разрешает новый payload автоматически. В согласовании нужны субъект, действие, target, нормализованные параметры, срок и правила однократного использования. Исполнитель сверяет их с фактическим запросом. [OWASP Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html) рассматривает эту привязку и контроль переходов как отдельную часть исполнения транзакции.

Hash параметров удобен для сравнения содержимого, но вычислить hash может любой участник. Доверие возникает из происхождения approval и механизма его проверки, а не из самого совпадения строк. Аналогично флаг `user_confirmed=true`, переданный моделью, остаётся её утверждением. Правила выдачи, срока действия, потребления и отзыва разрешения находятся за этой границей.

После записи проверяется обещанный результат. Exit 0 сообщает о завершении программы, а HTTP 200 — об ответе endpoint в его контракте. Чтобы принять отчёт, нужно связать его с нужным commit, проверить содержание и убедиться, что адресат может его получить. Модель может помочь оценить содержание, а обязательные формальные условия остаются проверяемыми отдельно.

## 4. История разговора становится единственной памятью о работе

Теперь вернёмся к timeout публикации. В conversation history осталась фраза «отправляю отчёт». После compaction она могла превратиться в «отчёт отправлен» или исчезнуть. Ни одна из этих формулировок не сообщает, завершилась ли запись у получателя. Для продолжения нужна устойчивая запись намерения и наблюдаемого исхода.

До отправки coordinator сохраняет логический идентификатор операции и её контракт: tenant, repository, входной commit и digest отчёта. Повтор того же намерения сохраняет идентификатор. Новый отчёт получает новое намерение после проверки разрешений. Номер сетевой попытки хранится отдельно: это ещё одна попытка доставить прежнюю операцию, а не новый пользовательский запрос.

После restart приложение читает журнал и разбирает незавершённые операции. Оно может найти результат у получателя и завершить локальную запись. Если результат неизвестен, приложение сохраняет эту неопределённость. Получается явная state machine с переходами, которые можно проверить без восстановления смысла из свободного текста.

Для небольшого coordinator подойдёт транзакционная таблица с уникальным ключом операции и условными обновлениями. Event sourcing для этого необязателен. Когда процесс включает длительные timers, approvals и много шагов, стоит оценить workflow engine из главы 30. В обоих случаях нужно определить одного владельца решения о следующем шаге.

Actor, восстановленный из старого checkpoint, может помнить более раннее намерение. Перед внешней записью он должен свериться с актуальной записью и полномочиями. Для нескольких исполнителей нужны версии, условные обновления или другой механизм, который не даст старому writer перезаписать новое решение. Журнал на диске без контроля конкурентных переходов сам по себе этого не обеспечивает.

## 5. Несколько слоёв одновременно повторяют одну запись

Проследим неуспешный с точки зрения клиента запрос. Adapter отправил отчёт. Получатель записал его и подготовил ответ, но ответ не дошёл. Adapter повторяет запрос, SDK тоже умеет retry, а coordinator повторяет весь шаг. Все участники пытаются помочь; каждый видит только свою часть отказа.

Если на трёх уровнях разрешено по две попытки всего, то при постоянной потере ответов до получателя дойдёт `2 × 2 × 2 = 8` вызовов. Здесь «две попытки» включает исходную; «два повтора после исходной» означало бы по три попытки и уже 27 вызовов. Верхний предел перемножается, когда нижний уровень каждый раз исчерпывает свой лимит. При раннем успехе вызовов будет меньше.

Назначьте владельца повторов для конкретной внешней операции. Остальные слои должны либо возвращать ему исход, либо расходовать согласованный общий бюджет. Отдельно учитываются deadline, отмена, число отправок и стоимость. Повторный запуск coordinator не должен выдавать той же операции свежий неограниченный бюджет. [Разбор AWS о retries](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) объясняет усиление нагрузки несколькими уровнями, а также роль backoff и jitter.

Выбирать повтор нужно по контракту операции и известному исходу. Если получатель достоверно отклонил запрос до записи, повтор может быть допустим. Если клиент потерял ответ после отправки, исход неоднозначен. Один только код 500 или timeout не доказывает отсутствия эффекта. Policy denial требует изменения разрешения или запроса, а исчерпание capacity — ограничения входа и восстановления запаса, иначе retries продлевают перегрузку.

**Идемпотентность** в рассматриваемом контракте означает, что повтор с тем же ключом и параметрами не создаёт второй эффект в пределах установленного срока хранения этого ключа. Она не гарантирует, что эффект вообще случится: все попытки могут быть отклонены. Два разных ключа могут обозначать две разные операции с одинаковым содержимым. Срок дедупликации, привязка параметров и судьба запоздавшего запроса должны быть частью API получателя. [AWS о безопасных идемпотентных API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) разбирает эти условия отдельно.

Локальная таблица «я уже отправил» не делает удалённую запись атомарной. Между записью у получателя и обновлением нашего журнала остаётся окно отказа. Закрыть его для безопасного повтора можно контрактом получателя, например сохранением idempotency key вместе с эффектом. Если такого контракта нет и проверка не даёт определённого ответа, потребуется остановка и разбор. Ограниченный retry всё равно способен создать дубликат.

## 6. Воспроизвести отказ и исправленный путь

В `examples/ch31_retry_boundaries.py` находятся coordinator, его журнал и учебный получатель публикаций. Они используют стандартную библиотеку Python и два отдельных SQLite-файла во временном каталоге. Между ними нет общей транзакции. Получатель в идемпотентном режиме хранит публикацию и receipt одной строкой в собственной транзакции; повтор ключа сверяет digest и возвращает тот же receipt. Это явно реализованный контракт эмулятора, а не свойство любого внешнего API.

Action содержит tenant, repository, полный входной commit и SHA-256 отчёта. Перед намерением проверяются заданный scope и совпадение digest с учебной отметкой согласования:

```
def checked_contract(action, scope, approved_digest):
    if not isinstance(action, Action) or not isinstance(scope, Scope):
        raise ValueError("Action and Scope required")
    if (action.tenant, action.repository) != (scope.tenant, scope.repository):
        raise PermissionError("outside supplied scope")
    fingerprint = action.digest()
    if type(approved_digest) is not str or approved_digest != fingerprint:
        raise PermissionError("approval fixture does not match action")
    return fingerprint
```

Scope и `approved_digest` поступают как доверенные данные упражнения. Функция показывает привязку содержимого; она не аутентифицирует человека, не проверяет срок, отзыв или однократность approval. Для production эти обязанности остаются у сервиса авторизации и исполнителя из главы 24. Сам файл отчёта здесь также не читается: его digest — заданный вход.

Журнал сохраняет намерение до вызова получателя. Перед каждой отправкой он увеличивает счётчик и отмечает исход как `uncertain`: coordinator может остановиться даже между этой отметкой и сетевым вызовом. После известного отказа без эффекта отметка возвращается в ожидание. После потерянного ответа идемпотентный путь читает receipt у получателя. Для режима без дедупликации неопределённость переводится в `manual_review`, и следующая автоматическая отправка не выполняется.

Запуск из корня репозитория:

```
python3 examples/ch31_retry_boundaries.py
python3 -m unittest discover -s examples -p 'test_ch31_retry_boundaries.py'
```

Результаты упражнения:

| Случай | Отправки / эффекты | Результат |
| --- | --- | --- |
| retry\_cascade | 8 / 8 | unknown: каждый ответ потерян, публикации накопились |
| bounded\_idempotent | 1 / 1 | done: потерянный ответ сверён с receipt |
| restart | 0 / 1 | done после повторного открытия баз; новой отправки нет |
| changed\_intent | 0 / 1 | contract\_conflict: другое содержимое под старым ключом |
| wrong\_scope | 0 / 0 | guard\_rejected до записи намерения |
| stale\_approval | 0 / 0 | guard\_rejected: digest не совпал |
| policy\_denied | 1 / 0 | rejected без повтора |
| outage | 2 / 0 | budget\_exhausted; второй запуск не обнуляет счётчик |
| legacy\_timeout | 1 / 1 | manual\_review; второй запуск не отправляет снова |
| new\_key | 2 / 2 | two\_operations: другой ключ создаёт другую операцию |

Счётчик отправок в `restart` относится к возобновлённому coordinator: первая отправка уже создала строку у получателя. В `changed_intent` одна публикация тоже существовала до конфликтного обращения. Модель действительно заново открывает SQLite-файлы, но остановку coordinator обозначает исключением; процесс ОС, сеть и storage failure здесь не эмулируются.

Последняя строка особенно важна. Даже исправный идемпотентный endpoint создаёт два эффекта, если coordinator выдаёт два разных ключа. Поэтому логический идентификатор операции хранится до отправки и не меняется при restart или retry. Если предметная область запрещает две публикации одного результата вообще, потребуется ещё и её правило уникальности, а не только дедупликация отдельных запросов.

Упражнение моделирует одного coordinator. В нём нет конкурентной выдачи полномочий, TTL ключей, удаления receipts, дедлайнов, backoff, подписей и проверки реальных артефактов. Значение `KnownNoEffect` задаёт сам эмулятор до транзакции; его нельзя приписать произвольному timeout настоящего SDK. Тесты подтверждают устройство модели и помогают поймать ошибку протокола, но не сертифицируют безопасность интеграции.

## 7. Каждая мысль становится Task, а RUNNING считается результатом

После инцидента иногда предлагают разнести каждый шаг по новой Task. Так проще представить работу деревом, но между чтением файла и следующим model call может не измениться ни одно требование к среде. Тогда мы добавили создание объектов, подготовку Workspace, наблюдение и cleanup, сохранив прежние права и общий результат.

Для `billing` отдельный тестировщик оправдан запуском недоверенного кода и собственным лимитом. Короткое суммирование уже прочитанного отчёта может остаться шагом harness. Если граница действительно изменилась, сохраняйте связь с общей целью, входным commit и бюджетом. Само делегирование требует журнала и обработки поздних результатов, как в главе 22. Цена новых Tasks должна объясняться полученной изоляцией или независимостью работы.

Другая крайность — следить только за количеством RUNNING Actors. В AX `ac233282` handler выполняет direct reconciliation; отдельную lifecycle-очередь или controller из другого профиля сюда переносить нельзя. Runner после выхода дочерней команды остаётся доступным. Поэтому зелёный инфраструктурный статус совместим с отсутствием дальнейшего прикладного прогресса. Эти детали проверены в исходниках [AX handler](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/server/server.go) и [runner](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/runner/runner.go).

Наблюдайте шаг, возраст последнего подтверждённого прогресса и пользовательский deadline. Число живых сред полезно для capacity, но принятое исследование требует проверенного отчёта. Если после command exit Task сохраняется для осмотра или продолжения, это должно быть осознанным lifecycle приложения с владельцем cleanup.

## 8. Постоянно открытые egress и debug обходят обычный путь

На первом запуске доступ к Git или registry часто не работает. Разрешение всего outbound быстро снимает симптом. Затем исключение остаётся, и агент с широкими tools получает маршрут к нежелательным destinations. Для исправления сначала опишите необходимые зависимости и точки применения policy: модель, Git, выбранные tools, storage, DNS и служебный трафик имеют разные роли.

Проверять нужно фактический путь sandbox, включая proxy, redirects и разрешённые методы. Сетевой allowlist ограничивает направления, но разрешённый сервис тоже может принимать недопустимую запись. Его API требует собственной авторизации. В [Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/) разрешающие правила складываются; добавленная default-deny policy не отменяет широкое разрешение другой применимой policy. Также нужен поддерживающий policy сетевой механизм. Правила Worker Pod нельзя автоматически считать правилами гостевого Actor; для Substrate смотрят выбранный enforcement layer и проверяют его путь, как в главе 15.

Debug создаёт похожий обход. Обычный tool adapter проверяет параметры, а постоянно доступный shell позволяет обратиться к тому же ресурсу напрямую. Инженеру нужен рабочий способ диагностики, поэтому debug оформляется отдельной привилегированной операцией: конкретная цель, именованный оператор, ограниченный срок, аудит и проверяемое прекращение доступа. Отзыв token не обязательно закроет уже установленную сессию — это поведение тоже выясняют заранее.

Положительная проверка отвечает, что нужное обращение работает; отрицательная — что запрещённое отклоняется по ожидаемой причине. Один неуспешный запрос к чужому адресу ещё не доказывает policy: там могло не быть сервера или мог сломаться DNS. Из главы 29 здесь пригодится умение связать наблюдение с конкретным утверждением. Такие probes выполняются только в разрешённой тестовой области.

## 9. Snapshot объявляют либо полноценным backup, либо расходуемым кэшем

Оба упрощения способны привести к потере данных. Snapshot может хранить единственную сохранённую версию файлов исследования. Тогда удалить его и «перестроить среду» означает потерять эти изменения, если другого источника нет. С другой стороны, наличие snapshot не доказывает готовность восстановиться после потери account, базы metadata или ключа расшифрования.

Разделите данные по способу восстановления:

| Данные | Можно ли пересоздать |
| --- | --- |
| Образ и checkout закреплённого commit | Из доступных сохранённых image и repository, с проверкой версий |
| Пересчитываемый индекс | Из исходников и конфигурации, если стоимость и время допустимы |
| Уникальный промежуточный файл только в durable volume | Только из пригодной сохранённой копии этих данных |
| Решение о публикации и результат внешнего действия | Из журнала и состояния получателя по их recovery contract |

Стандартный AX template в этом профиле сохраняет Data и восстанавливает его через golden, поэтому описание любого snapshot как «памяти процесса» тоже вводит в заблуждение. Full scope рассматривается отдельно. В [API guide Substrate](https://github.com/agent-substrate/substrate/blob/df788825e6fc13dd7aa5fd283c8f14bd4c818247/docs/api-guide.md) срок жизни snapshot связан с владельцами: следующий успешный suspend заменяет предыдущий внешний snapshot Actor, а Tag может удерживать версию дольше. Из этого ещё не получается независимый backup с нужной retention.

Для восстановления нужны согласованные metadata, bytes, images, ключи и readers. Если база ссылается на отсутствующий blob, две успешные задачи копирования не образовали пригодный комплект. Глава 27 объясняет recovery manifest, RPO/RTO и прекращение прав старого writer. Например, для [PostgreSQL PITR](https://www.postgresql.org/docs/17/continuous-archiving.html) требуются base backup и нужная непрерывная последовательность WAL. Этот механизм не копирует автоматически внешний snapshot store.

Проверку начинайте с вопроса, какой отказ должен пережить комплект и какие данные разрешено потерять. Восстановление выполняют в отдельной разрешённой среде из сохранённых копий; рабочие Actors и snapshots ради доказательства не удаляют. Расходуемым кэшем можно объявить только то, для чего действительно существует другой проверенный путь восстановления.

## 10. Успешный demo становится обещанием производительности

Пустой Actor на свободном Worker полезен как smoke test: запуск вообще работает. Сервис исследования читает большие checkout, пишет индекс, ждёт модель и разделяет storage с соседями. Если benchmark не включает эти свойства, он пока отвечает на другой вопрос.

Измеряйте путь до правильного результата, как в главе 28. Для Data-профиля важны durable files и восстановление приложения; dirty heap становится самостоятельным фактором при соответствующем Full snapshot, а не автоматически при каждом resume AX. Нужны типичные и крупные данные, холодный и тёплый cache, ожидаемый поток и оговорённый wakeup burst. Область допустимой нагрузки определяется вместе с SLO и условиями отказа.

Особенно опасно улучшить completion rate ценой повторных внешних эффектов. В нашем упражнении восемь публикаций показывают большую активность, но одну логическую работу с неизвестным для клиента исходом. В метриках должны различаться root request, логическая операция и transport attempt. Иначе dashboard награждает механизм, который создаёт дубликаты.

При перегрузке retries добавляют спрос на уже перегруженную зависимость. Требуются ограничение входа, общий бюджет и наблюдение очереди; добавление Workers может усилить конкуренцию за storage. [Google SRE о каскадных отказах](https://sre.google/sre-book/addressing-cascading-failures/) объясняет, почему предел ёмкости и поведение за ним проверяют заранее.

Наблюдаемость готовят до опыта: идентификаторы намерения и попытки, версия policy, этап, безопасный код исхода и ссылка на receipt. Полный prompt или token для этого обычно не нужны. Логи с секретами создают ещё одно хранилище, которое затем придётся защищать и очищать. Решение «включить всё подробное после аварии» одновременно опаздывает за потерянными событиями и расширяет риск раскрытия данных.

## 11. Выбрать средство исправления и порядок работы

Один новый продукт не исправит все разобранные границы. Для нашего случая выбор выглядит так:

| Обязанность | Разумное средство | Граница результата |
| --- | --- | --- |
| Сохранить намерение и бюджет между restart | Транзакционный журнал; SQLite в локальном упражнении, подходящий store в сервисе | Не делает запись в чужом API атомарной |
| Безопасно повторить публикацию | Контракт idempotency у получателя и стабильный ключ coordinator | Требует согласованных параметров, scope и срока хранения ключа |
| Координировать долгие ожидания и несколько шагов | Workflow engine, если самодельная state machine стала сложной | Внешние эффекты всё ещё требуют своего протокола |
| Ограничить опасное действие | Узкий tool adapter и авторизация конечной системы | Сам adapter не является доказательством корректности policy |
| Ограничить недоверенное исполнение | Проверенная sandbox и scoped credentials | Не подтверждает качество отчёта или backup |

Сначала определите текущую угрозу. При подозрении на утечку credential требуется процедура containment и отзыва, а не плановое улучшение retries. Если активного инцидента нет, начните с самой опасной доступной записи и пройдите её путь: кто разрешил, что отправлено, что сохранено до отправки и как узнаётся исход. Ограничение scope и удаление ненужного write tool могут быть небольшим изменением с большим эффектом.

Затем назначьте владельца повторов, сохраните идентичность операции и добавьте проверку неопределённого исхода. Проверьте исправление отрицательным случаем, который воспроизводил проблему. Закрытие egress или debug проводите с наблюдением и подготовленным разрешённым путём диагностики; иначе можно одновременно потерять сервис и способ понять его состояние.

Изменение признаётся полезным по новому поведению. Если поменять prompt, прежняя запрещённая запись остаётся недоступной? Если перезапустить coordinator, он сохраняет бюджет и ключ? Если target не умеет дедупликацию, система останавливается после неопределённого ответа? Ответы должны следовать из механизма, который команда может показать.

## 12. Проверить понимание перед практикумом

Возьмите одну операцию своего сервиса и опишите путь от запроса до внешнего эффекта. Отметьте место выдачи полномочий, запись намерения, все уровни повторов, сохранённое подтверждение и способ проверки результата. Если два компонента независимо решают «можно продолжать», выясните, какое решение они на самом деле принимают и где хранится его актуальная версия.

Для самопроверки измените учебный пример. Выдайте прежней публикации новый ключ и объясните два результата. Затем замените получателя на режим без дедупликации: почему сохранённый журнал помогает остановиться, но не даёт безопасно повторить запись? Наконец предположите, что уникальный файл отчёта остался только в Data snapshot. Какие данные и зависимости теперь должны войти в recovery contract? Ответ «пересоздадим Actor» не восстанавливает содержимое файла.

Следующая глава переводит эти вопросы в лабораторные работы. Она использует отдельный AX `v0.3.1` профиль: там отличаются API Task, controller и suspend intent. Перед практикумом нужно сверить паспорт и CLI/server; правила `CreateTask` из текущего `ac233282` туда не копируются. Интеграционная совместимость лабораторной пары остаётся предметом её обязательной проверки, а не результатом локального упражнения этой главы.

Полезный итог ревью — несколько явно защищённых границ и воспроизводимый случай отказа. Уменьшить полномочия, сохранить намерение, ограничить повторы и проверить восстановление можно последовательно. Каждый шаг должен менять наблюдаемое поведение системы и оставлять понятным следующий допустимый шаг инженера.
