# Две референсные multi-agent архитектуры

В практикуме мы получили два прикладных сюжета: исправление программы и диагностику с ограниченным изменением инфраструктуры. У них похожая последовательность: разобраться, предложить решение, проверить и принять результат. Но цена ошибки и способ завершения различаются. Код можно оставить в отдельной ветке; изменение сетевой политики начинает влиять на трафик сразу после применения.

Здесь спроектируем обе системы так, чтобы другой инженер мог продолжить их работу после отказа. Для первой сохраним задачу главы 32: функция разбиения на пачки теряет последние записи. Во второй перейдём от неверного backend port к выбору пути через двух сетевых провайдеров. Через эти случаи разберём передачу результатов, принятие решений, выбор инструментов и восстановление незавершённого действия.

Референсная архитектура — образец распределения обязанностей, а не готовая установка. Её можно упростить или заменить компоненты, если сохраняются нужные свойства. Отдельная роль появляется там, где нужен иной контекст, независимая проверка либо другое разрешение. Для маленькой задачи реализация может состоять из одного coding agent, обычного кода workflow, CI и человека, принимающего результат.

## Из каких частей состоит общий каркас

Пусть Implementer исправил функцию, а Tester прислал сообщение «все тесты прошли». Следующее действие зависит от нескольких фактов: какую версию проверили, какими тестами, откуда пришёл отчёт и не изменился ли код после запуска. Разбирать эти связи при каждом ответе модели неудобно. Их проверяет обычная программа, управляющая переходами workflow.

Workflow — порядок зависимых работ вместе с правилами перехода между ними. В простом варианте это явно записанная последовательность. DAG описывает ациклические зависимости одного раунда: например, после фиксации candidate тесты и review можно выполнять параллельно. Возврат на исправление создаёт новый раунд с новым candidate, а не делает прежние отчёты доказательством для любых последующих изменений. Coordinator может предложить разбиение исследования; допустимые переходы и пределы работы задаёт приложение.

| Компонент | Его работа | Какой результат он передаёт дальше |
| --- | --- | --- |
| Harness роли | Собирает контекст, вызывает модель и tools, ограничивает цикл | Артефакт роли и описание выполненных действий |
| Контроллер прикладного workflow | Хранит раунды, зависимости, бюджет и принятые результаты | Решение о следующем допустимом шаге |
| Среда исполнения | Запускает процесс, ограничивает доступные ресурсы и обслуживает lifecycle | Наблюдения о запуске и состоянии workload |
| Проверяющие сервисы | Выполняют тесты, читают конфигурацию, проверяют policy | Отчёт с установленным происхождением и точным предметом проверки |
| Исполнитель внешнего действия | Проверяет право на конкретную запись и обращается к backend | Receipt операции и сведения для сверки её исхода |

Эти обязанности не требуют пяти отдельных сервисов. Например, небольшой controller может хранить переходы в транзакционной БД и отправлять задания в очередь. Крупный лог, patch и отчёт теста удобнее хранить как отдельные артефакты, а в журнале — их идентификаторы и digest. Это позволяет обновить состояние короткой транзакцией, не копируя весь контекст агента.

При приёме результата сначала сохраняется завершённый артефакт, затем журнал принимает ссылку на него. Сбой между действиями оставляет непринятый объект, который можно собрать позже. Обратный порядок оставил бы в журнале обязательный результат, байты которого ещё не записаны. Это порядок приёма результата; намерение внешней записи, напротив, фиксируется до вызова исполнителя. Retention, права чтения и проверка доступности важны не меньше checksum: ссылка на уже удалённый объект не позволяет продолжить workflow.

Если используете AX, Task и Workspace предоставляют исполняемой роли рабочую среду, а Substrate — Actor и его lifecycle. При продолжении практикума сохраняйте его отдельный профиль AX `v0.3.1` и интеграционный допуск главы 32. Контроллер нашего прикладного workflow не следует путать с `ax-controller` этого release: первый знает смысл тестов и approval, второй обслуживает ресурсы AX. В runner запускается выбранный harness; зависимости между ролями остаются ответственностью приложения.

### Что фиксировать при передаче результата

Назовём проверяемый вариант работы предметом проверки, или subject. Для кода это сочетание запуска, репозитория, base и candidate. Для сети — incident, конкретный объект, исходная и ожидаемая новая конфигурация, стадия изменения. Добавим digest содержимого и версии правил проверки. Тогда поздний ответ можно однозначно отнести к своему раунду.

Digest отвечает на вопрос, совпадают ли байты с зафиксированными. Источник результата устанавливается другим способом: например, сервис приёма проверяет identity CI и связывает её с загруженным отчётом. Написанное внутри JSON поле `producer: trusted-ci` не выполняет такую проверку. Важен и сам доверенный исполнитель: скомпрометированный CI способен подписать неверный результат с совершенно правильным hash.

| Связь | Зачем она нужна |
| --- | --- |
| Run и target | Отделить соседние задачи, репозитории, устройства и VRF |
| Base и candidate | Понять, к какому изменению и исходному состоянию относится вывод |
| Digest содержимого | Обнаружить замену переданных байтов |
| Версия проверочной политики | Зафиксировать обязательные checks, проверяющих и ограничения |
| Источник и время наблюдения | Проверить происхождение, свежесть и нужную стадию работы |

В настоящем coding pipeline к этому добавляются recipe сборки, зависимости и идентификатор окружения. У сетевого измерения нужны интервал, точка наблюдения, единицы и размер выборки. Одинаковая структура отчётов помогает их передавать; достаточность доказательств определяется предметной задачей.

### Где хранить прогресс и как ограничивать работу

Журнал workflow хранит текущий раунд, принятые артефакты, зарезервированный бюджет, ожидаемое событие и причину остановки. После перезапуска controller читает его и сверяет незавершённые действия с внешними системами. Контекст Coordinator используется для объяснения следующего шага, а решение «запись ещё не выполнялась» берётся из журнала и receipts. Snapshot процесса сам по себе не устанавливает этот факт.

У бюджета есть две части: уже потраченное и зарезервированное для активных работ. Если общий предел равен 20 условным единицам, потрачено 8, а двум ролям выдано по 5, свободно только 2. Выдать следующей роли ещё 5 нельзя, хотя фактический расход активных ролей пока неизвестен. Освобождение резерва требует подтверждённого завершения или сверки; недоступный Worker ещё может выполнять запрос модели.

Помимо стоимости задайте общий deadline, число одновременно активных работ, глубину delegation и предел раундов исправления. Это разные ограничения: четыре Actors могут поочерёдно породить сотню новых работ. При остановке controller запрещает новые dispatch и сохраняет незавершённые обязательства. Сверка уже отправленной внешней записи может требовать отдельного ограниченного recovery-бюджета и участия оператора.

Долгое ожидание человека удобно хранить как состояние workflow, освобождая ненужное исполнение. Нужность suspend зависит от цены простоя и контракта восстановления роли. Когда подтверждение пришло через час, приложение заново проверяет candidate, policy, срок согласования и актуальные права. Полученное когда-то разрешение не следует восстанавливать из текста диалога.

## Архитектура 1. Исправление кода и принятие точной версии

Вернёмся к `batches(items, size)` из главы 32. Для входа `[0,1,2,3,4]` и size=2 ожидаются `[[0,1],[2,3],[4]]`. Исходная реализация возвращает только две полные пачки. Потеря возникает при построении диапазона начальных индексов; данные последней неполной пачки вообще не попадают в результат.

Условие задачи шире этого одного примера. Нужно сохранить порядок и все элементы, включая одинаковые значения, оставить входной список неизменным, поддержать пустой и короткий списки и сохранить обработку неверного size. Это и есть контракт, который владелец задачи передаёт workflow. В учебном проекте десять тестов, из которых исходно падают `test_tail`, `test_short` и `test_coverage`.

### Как распределить роли

Implementer получает исходный commit, контракт, разрешённые пути и бюджет. Он может читать код и менять выделенную копию, запускать собственные тесты и предлагать patch. Для этого маленького дефекта отдельный Researcher обычно избыточен. Он становится полезен, когда причина распределена по нескольким модулям, нужно сопоставить версии зависимости или заранее неизвестно, какую часть системы исследовать.

Tester получает зафиксированный candidate и защищённый набор проверок. Его задача — применить patch к чистой копии, запустить нужные проверки и сохранить результат. Reviewer получает base, candidate, diff и контракт: он оценивает смысл изменения, совместимость интерфейса и достаточность проверок. Исполнение тестов и смысловой review дополняют друг друга. Два диалога с одной моделью всё ещё могут повторить общую ошибку; исходный код и независимое наблюдение полезнее голосования по одному резюме.

| Участник | Доступ, необходимый для работы | Что остаётся за его границей |
| --- | --- | --- |
| Coordinator | Чтение журнала и результатов; ограниченный запрос подзадач | Расширение бюджета и самостоятельный merge |
| Implementer | Запись в свою копию и передача candidate через scoped сервис | Чужой repo, protected ref и merge credential |
| Tester | Исполнение candidate в disposable среде | Production secrets и публикация результата в main |
| Reviewer | Чтение точного diff, критериев и отчётов | Изменение проверяемого candidate |
| Merge gate | Принятые доказательства, решение человека и ограниченная запись | Произвольные действия от имени агента |

Git branch ведёт историю изменения, но ограничение доступа обеспечивают права backend и отдельные credentials. Общая writable копия опасна для воспроизводимости: Implementer способен изменить её, пока Tester уже исполняет файлы. Раздельные checkout и immutable candidate позволяют повторить проверку и объяснить, какие байты видел каждый участник.

CI запускает код candidate, поэтому ему нужна отдельная среда без прав merge/release и без возможности записывать в caches доверенных pipelines. Сам доверенный сборщик отчёта должен находиться вне изменяемой кандидатом логики. Полезно иметь защищённые acceptance checks из base или отдельной policy: тогда удаление теста из patch не превращает дефект в успех. У GitHub Actions особенно внимательно разбирайте privileged triggers и checkout недоверенного кода. [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use) описывает эту границу; конкретный workflow требует собственной проверки permissions и секретов.

README, комментарии к коду и логи входят в исследуемые данные. В них может оказаться инструкция удалить тесты или отправить исходники на другой сервер. Harness сохраняет границу между заданием владельца и содержимым проекта, а tools независимо ограничивают пути и назначения. Контрольный опыт из главы 32 должен показать фактический отказ лишнего действия; обещание Reviewer проигнорировать такую строку не проверяет backend.

### Один раунд исправления

Обозначим исходный base как B0, первый candidate как C1. Это поясняющие имена; журнал хранит полные реальные revisions. Implementer сначала воспроизводит три ошибки, затем исправляет функцию и фиксирует C1. После этого workflow параллельно запускает тесты C1 и review diff B0→C1. Сохранённый результат каждой проверки относится к этому subject и версии policy.

Перед переходом дальше controller выполняет join — собирает обязательные результаты в одно согласованное решение. Join нужен даже тогда, когда все участники по отдельности завершились успешно. Отчёт тестов C1 и review C0 относятся к разным предметам проверки. Если Reviewer вернул замечание, следующий candidate C2 открывает новый раунд; поздний report C1 сохраняется для истории, но не закрывает проверки C2.

Для исправленной функции важно проверить именно сохранность хвоста, а не просто число прошедших тестов. Например, замена на один большой список сохранила бы элементы, но нарушила максимальный размер пачки. Проверки порядка, размера и обработки неверного size защищают разные части контракта. Число «10 passed» удобно для обзора; подробные результаты позволяют понять, что действительно исполнялось.

Положительный join означает готовность к следующему шагу приёмки. Право merge выдаётся отдельной доверенной границей. Человек видит точный diff и ограничения проверки; backend применяет правила protected branch и проверяет ожидаемое состояние ref. У Coordinator нет необходимости хранить широкий GitHub token ради этого перехода.

### Что меняется, когда main продвинулся

Пока проверяли C1, в main мог появиться B1. Будущий результат объединения M1 содержит уже другую комбинацию изменений. Проверки C1 на B0 не устанавливают работоспособность M1: например, соседний patch изменил тип входа или загрузку модуля. Даже без текстового merge conflict поведение программы может измениться.

Простой controller строит candidate для нового base, запускает обязательные проверки полученного результата и заново устанавливает, какое review покрывает итоговый diff. Более развитая policy может обоснованно переиспользовать часть результатов, но должна явно определить условия такого reuse. Подмена метки base в старом отчёте не создаёт новый тестовый запуск.

В репозитории, где доступна GitHub merge queue, эта задача частично передаётся очереди объединения: checks запускаются для группы изменений поверх актуальной целевой ветки. Для GitHub Actions требуется обработка `merge_group`; зелёный PR workflow без этого события не даёт результат для merge group. Проверьте доступность функции и её настройку в своём репозитории по [руководству merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue). Очередь организует приёмку конкретной комбинации, а полнота тестов и качество review остаются вашей ответственностью.

### Что сохранять при отказе

Если Tester завершился до загрузки отчёта, workflow видит незавершённую проверку и назначает ограниченную новую попытку того же candidate. Несколько результатов одного вида не стоит молча сводить к последнему зелёному. Controller выбирает допустимую попытку по policy, сохраняет историю повторов и причину выбора. Для flaky-теста заранее определяются предел повторов и критерий нестабильности.

После потери ответа merge API дальнейшее действие принадлежит сервису публикации: он сверяет PR, ref и доступный receipt. Доказательства, что запрос не выполнился, требует именно эта граница; перезапуск coding agent его не даёт. Журнал intent и контракт повторов разобраны в главе 31. Здесь важно сохранить одного владельца продолжения, чтобы Coordinator и adapter независимо не выполняли один merge.

Итог coding workflow — связь исходной задачи с принятым diff, проверенной комбинацией revisions и записью публикации. Если бюджета на review не хватило, patch остаётся полезным промежуточным результатом со статусом «не принят». Такой исход позволяет продолжить работу позже без повторного исследования и без ложного объявления готовности.

## Практический пример согласования отчётов

В `examples/ch33_evidence_join.py` находится offline-модель join. Она исполняет только заранее заданные Python-fixtures главы 32: исходная функция даёт три ошибки из десяти, эталонное исправление проходит эти десять проверок. Затем модель соединяет test report с отдельным учебным review. Она не вызывает агентов, модели, Git или сеть.

```
# Из корня локальной копии книги:
python3 examples/ch33_evidence_join.py
python3 -m unittest discover -s examples \
  -p test_ch33_evidence_join.py -v
```

`Subject` связывает run, target, base, candidate, digest содержимого, policy и стадию. `Artifacts` хранит реальные байты JSON и проверяет SHA256 при чтении. Вне JSON находится учебный `Receipt` с источником и временем получения отчёта. Функция `join` проверяет совпадение предмета, происхождение, допустимое время и полный набор обязательных checks. Повторная доставка того же receipt не меняет решение; две разные попытки одного вида требуют явного выбора со стороны workflow.

| Случай из упражнения | Результат | Что он объясняет |
| --- | --- | --- |
| `code_ok` | `ready_for_next_step` | Тесты и review относятся к одному candidate и policy |
| `missing_review` | `waiting:missing_evidence` | Завершение одного участника ещё не закрывает join |
| `new_candidate` или `new_base` | `rejected:subject_mismatch` | Прежние результаты не переносятся сменой revision |
| `artifact_changed` | `rejected:artifact_missing_or_changed` | Замена сохранённых байтов обнаруживается при чтении |
| `real_tests_fail` | `rejected:checks_failed` | Исходный дефект действительно воспроизведён тестами |
| `producer_substitution` | `rejected:producer_mismatch` | Источник сверяется с policy; его identity в модели уже считается установленной |
| `trusted_lie` | `ready_for_next_step` | Согласованная ложь доверенного источника остаётся за пределами этой проверки |

Последняя строка намеренна. В ней создаётся корректный receipt с ложным утверждением об успешных тестах неисправной функции. Join его принимает: hash и совпадение контекста проверяют согласованность, а достоверность отчёта зависит от проверяющего исполнителя. Это причина защищать источник CI и путь получения результата, а не добавлять ещё один hash к тому же утверждению.

В упражнении identity и время — доверенные входы, без аутентификации и подписей. Хранилище находится в памяти; долговечность, конкурентные coordinators и запись во внешний backend не моделируются. Выполнение fixture использует обычный Python-процесс без sandbox и подходит только для встроенных примеров, не для чужого patch. Результат `ready_for_next_step` не выдаёт approval и не исполняет действие. Для реальной приёмки Subject нужно дополнить условиями окружения, а результат проверки сохранить в журнале переходов.

## Архитектура 2. Диагностика сети и ограниченная запись

В работе 14 проверялась простая связь: неправильный backend port мешал HTTP-запросу. Теперь рассмотрим учебную сеть с edge-устройством и двумя upstream. Трафик к тестовому префиксу идёт через B и испытывает потери; A рассматривается как альтернатива. Задача — обоснованно выбрать изменение, применить его только в выделенном scope и проверить, что пользователю действительно стало лучше.

![Практика: инфраструктурная диагностика с контролируемым изменением](.gitbook/assets/diagrams/33-30.png)  
*Практика: инфраструктурная диагностика с контролируемым изменением*

Coordinator открывает incident с target `lab-edge-1`, VRF `LAB`, префиксом `192.0.2.0/24`, направлением трафика и временным интервалом. VRF отделяет таблицу маршрутизации конкретной сети; одинаковый префикс в другой VRF относится к другому объекту. Выделенный scope одновременно ограничивает исследование и определяет, какие данные подходят для решения.

### Как собрать доказательства для следующего решения

Telemetry collector получает потери, counters интерфейсов и контрольные потоки. Network Diagnostics читает BGP paths и фактический выбранный маршрут. Config Analyst сопоставляет import policy, версии конфигурации и последние изменения. Сборщик может быть обычной программой: модель нужна при выборе следующей гипотезы и объяснении неоднозначных результатов, а не при переносе каждого counter в JSON.

Read-only инструменты тоже требуют ограничений. Дорогая диагностическая команда, вызванная сотню раз, способна перегрузить устройство; конфигурация может раскрыть секреты. Adapter задаёт допустимые операции, rate limit, timeout и максимальный объём результата, маскируя секреты до передачи модели. Полный обезличенный артефакт сохраняется отдельно, а в контекст попадает относящаяся к гипотезе часть.

Validator сопоставляет время, target и происхождение наблюдений. Например, потери вчера и рабочий путь сегодня не устанавливают причину сегодняшней жалобы. Если три роли процитировали один лог, это один источник, прочитанный трижды. Для изменения пути нужны как минимум актуальное наблюдение проблемы, подтверждение текущего forwarding и пригодности альтернативы. При противоречии данных controller назначает конкретное дополнительное чтение или передаёт случай оператору.

### Почему здесь рассматривается local preference

BGP сообщает о достижимых префиксах и атрибутах путей. Local preference задаёт предпочтение маршрута внутри автономной системы: среди рассматриваемых допустимых путей большее значение предпочтительнее. В обычном eBGP этот атрибут не передаётся внешним соседям. Изменение local-pref управляет нашим выбором пути к назначению, а не командует чужой автономной системе, как направлять обратный трафик. Это следует из [RFC 4271, раздела 5.1.5](https://datatracker.ietf.org/doc/html/rfc4271#section-5.1.5).

Зададим учебное исходное условие: у допустимого пути A local-pref=100, у B — 120. Planner предлагает повысить A до 150 только для выбранного префикса в конкретной import policy. До этого нужно проверить, что A действительно доступен и его пропускной способности достаточно. Сам атрибут не измеряет потери и не исправляет канал; он может лишь изменить выбор пути. Учитывайте остальные правила вашей реализации BGP и проверяйте результат на нужных узлах.

После применения надо различать таблицу маршрутов с выбранным путём и реально установленное правило пересылки пакетов. Затем нужен тест самого трафика в заданном направлении. Если жалоба относится к входящему трафику из внешней сети, изменение нашего local-pref может вообще не воздействовать на проблемный участок. Эта проверка предмета задачи должна предшествовать записи.

### Как выглядит ограниченное предложение

Planner передаёт доменную операцию, а не строку произвольного CLI. Для неё можно проверить target, список префиксов, старое и новое значения и ожидаемую revision. Ниже учебный формат request; имена операций не являются готовыми AX/MCP resources или универсальной командой сетевого устройства.

```
{
  "change_id": "lab33-net-001",
  "target": {"device": "lab-edge-1", "vrf": "LAB"},
  "operation": "set_import_local_pref",
  "arguments": {
    "policy": "LAB-UPSTREAM-A",
    "prefixes": ["192.0.2.0/24"],
    "from": 100,
    "to": 150
  },
  "preconditions": {"config_revision": "config-17"},
  "evidence_ref": "lab33-evidence-017",
  "rollback_ref": "lab33-rollback-017",
  "observation": {"duration_seconds": 120}
}
```

Точные критерии результата задаются рядом с request до approval. Для учебного опыта можно выбрать потери ниже 1% в 120-секундном окне после стабилизации пути, сохранение BGP sessions и отсутствие ухудшения контрольных потоков. Это выбранные пороги, не измеренные результаты и не универсальный SLO. Укажите частоту probes, точки отправки/приёма, baseline и момент начала окна; иначе одинаковое значение процента скрывает разные эксперименты.

Approval service нормализует request и связывает подлинное разрешение с его digest, исполнителем, target, arguments, preconditions, policy version и сроком. Проверочный план и rollback также входят в согласованный scope. Человек видит evidence, предлагаемое изменение и последствия отказа. Если Planner меняет префикс или значение после approval, executor получает другой запрос и требует новое согласование.

Restricted MCP server предоставляет узкий adapter к executor. MCP определяет обмен tool calls; правила конкретной записи проверяет backend. Долгоживущая device credential остаётся у доверенного исполнителя. Agent получает возможность запросить согласованную операцию, а не произвольный административный доступ. Для HTTP transport отдельно соблюдается authorization соответствующей negotiated версии MCP.

### Почему проверка revision должна быть частью записи

Пока человек читал предложение для `config-17`, другой администратор мог применить `config-18`. Последовательность «прочитать revision, сравнить, отправить безусловную команду» оставляет промежуток для ещё одного изменения. Исполнитель должен использовать условную запись backend, транзакцию либо механизм блокировки с проверенными границами. Блокировка только внутри вашего controller не остановит другого администратора с прямым CLI-доступом.

При конфликте controller сохраняет причину, заново собирает нужные сведения и предлагает новый план. Автоматически подставить свежую revision в прежнее approval нельзя: человек согласовал действие относительно другого состояния. Без поддерживаемой устройством защиты от конфликтующих записей такой сценарий лучше оставить оператору или выполнять в управляемом окне с явно обеспеченной исключительностью доступа.

### Как установить исход действия

После записи `config-18` executor сохраняет receipt, а Verification читает новое состояние и проверяет эффект. Успешное применение local-pref ещё не означает смены forwarding или уменьшения потерь. Если данных пока нет, результат проверки остаётся `inconclusive`. Controller следует заранее выбранной процедуре ожидания, отката или передачи оператору и не расширяет scope для получения положительного ответа.

При потере ответа записи появляется `OUTCOME_UNKNOWN`. Сервис сверки ищет операцию по operation ID и доступному receipt, читает внешнее состояние и устанавливает, что известно достоверно. Одного похожего текущего config иногда недостаточно: то же значение мог записать другой администратор. До выяснения исхода сервис запрещает свои конфликтующие действия над тем же объектом; возможность остановить остальных writers определяется отдельной системой доступа и блокировок.

```
APPROVED -> EXECUTING -> VERIFYING -> VERIFIED
EXECUTING -> OUTCOME_UNKNOWN -> RECONCILING
RECONCILING -> VERIFYING | MANUAL_REVIEW
VERIFYING -> INCONCLUSIVE -> MANUAL_REVIEW | ROLLBACK_REQUIRED
VERIFYING -> ROLLBACK_REQUIRED -> ROLLED_BACK
```

Это состояния прикладного workflow. До них находятся валидация и согласование плана; они не являются phases AX Task. Повтор команды зависит от контракта получателя, а не от названия transport error. Durable журнал помогает найти намерение, но не образует общую транзакцию с устройством. Механизм idempotency и поведения после timeout должен быть проверен у конкретного backend.

Сетевая ветка offline-упражнения проверяет именно согласованность отчётов: `old_telemetry` даёт `rejected:stale`, `before_change` — `rejected:outside_window`, `no_traffic_verdict` — `manual_review:inconclusive`. Время здесь синтетическое, наблюдения и их происхождение заданы fixture. Модель не измеряет 120 секунд трафика, не проверяет сходимость BGP и не доказывает реальную работоспособность сети. Она позволяет воспроизвести ошибку, когда старый отчёт принимают за post-change проверку.

### Как выбрать способ отката

План возврата готовится одновременно с прямым изменением: нужный pre-state, обратная операция, ожидаемая post-change revision, независимый путь доступа и критерий завершения. Если только наша запись перевела `config-17` в `config-18`, ограниченная обратная операция может вернуть прежний local-pref с проверкой версии. Если появился чужой `config-19`, безусловное восстановление полного старого config способно удалить чужую работу.

Устройство с NETCONF candidate и capability `:confirmed-commit:1.1` может поддерживать временное применение с последующим подтверждением. Без подтверждения в установленный срок оно возвращает прежнюю конфигурацию. Для общего datastore RFC рекомендует использовать locking: автоматический возврат тоже может затронуть параллельные изменения. Без `persist` важна исходная session; с `persist` действуют правила `persist-id`. Проверьте capabilities, клиент и поведение при потере связи по [RFC 6241, разделу 8.4](https://datatracker.ietf.org/doc/html/rfc6241#section-8.4), прежде чем выбирать этот путь.

Другой вариант — scoped обратная операция через versioned API, если устройство предоставляет нужные preconditions. При отсутствии надёжного возврата или независимого доступа оставьте запись человеку. Ограничьте повторные попытки rollback и заранее назначьте эскалацию. Неуспешный откат не добавляет агенту право очистить policy или перезапустить устройство. Завершение устанавливается новой проверкой config и трафика; snapshot Actor на состояние внешней сети не воздействует.

## Как выбирать реализацию и расширять систему

Начните с одного проверяемого перехода. Для исправления маленькой функции достаточно обычного кода управления раундом, CI, Git и человека. Очередь нужна, когда задания следует распределять и повторно доставлять; транзакционный журнал — когда прогресс должен переживать потерю процесса. Одна очередь без журнала принятых результатов не сообщает, выполнен ли предыдущий шаг.

| Потребность | Вариант реализации | Цена и условие выбора |
| --- | --- | --- |
| Короткий фиксированный процесс | Python/Go controller, транзакционная БД, CI | Простота старта; собственные переходы, повторы и восстановление |
| Цикл модели с checkpoint и возвратом человека | Harness на графе, например LangGraph с подходящим checkpointer | Нужно проверить backend сохранения и продолжение внешних действий |
| Долгие ожидания, таймеры и много связанных исполнений | Durable workflow engine, например Temporal | Дополнительная платформа, правила replay и сопровождение версий workflow |
| Повторное использование тяжёлой рабочей среды | AX Task/Workspace на Substrate Actor | Интеграционный допуск, runtime и проверенный state contract |
| Работа с repository | Git, isolated CI и scoped merge service | Защищённые проверки, точный merge result и минимальные credentials |
| Изменение инфраструктуры | Узкий доменный API/MCP adapter и безопасный backend | Проверенная условная запись, receipts и доступный rollback |

LangGraph предоставляет checkpoints состояния графа; Temporal восстанавливает выполнение по сохранённой истории. В обоих случаях отдельно проектируются side effects, граница доверия и повтор внешнего вызова. Выбирать их стоит по времени жизни работы, числу ожиданий и требованиям восстановления. Смена framework не освобождает команду от приёмки конкретного patch или проверки конкретной сетевой операции. Для выбранной версии изучите [persistence LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence) и [Workflow Execution Temporal](https://docs.temporal.io/workflow-execution), затем проверьте нужный сценарий отказа.

Сравните два варианта на одинаковых задачах: один агент с проверками и система с дополнительной ролью. Считайте успешные принятые результаты, общий расход всех ролей, время до приёмки и вмешательства человека. В сетевом сценарии отдельно учитывайте ошибочную рекомендацию, запрещённое действие, остановленное executor, и реально выполненное ошибочное изменение. Эти события требуют разных исправлений системы.

Перед расширением полезны четыре отказа: поздний report прежнего candidate, смена base/config во время согласования, потерянный ответ записи и отсутствие post-change наблюдения. Пройдите каждый по журналу: где остановился переход, кому разрешено его продолжить и какие данные нужны для решения. Если ответ можно получить лишь из памяти Coordinator, уточните протокол передачи результатов и восстановления.

Архитектура становится полезной, когда по ней можно назначить владельца действия, повторить результат и безопасно остановить работу. Дополнительный Researcher оправдан отдельным исследованием; Reviewer — независимой проверкой; durable engine — необходимым восстановлением долгого процесса. В главе 34 соберём эти отношения в mental models и шпаргалки. Их краткие формулировки будут опираться на конкретные переходы, которые мы только что разобрали.
