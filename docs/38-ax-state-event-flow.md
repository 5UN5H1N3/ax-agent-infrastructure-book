# AX control plane: state, event flow и operational truth

Утром инженер открывает карточку Task `lab/network-017`. Фаза - `Running`, HTTP-проверка runner проходит, но отчёта о результате нет. В журнале приложения операция `op-17` уже имеет состояние `APPLIED`. Нужно ли перезапустить задачу? Для ответа пока не хватает двух вещей: что случилось с командой внутри Actor и проверен ли результат сетевого изменения.

Продолжим пример главы 37. После потери ответа приложение нашло квитанцию: на учебном устройстве применена конфигурация `config-18`, повторной записи не было. Проверка исходной инженерной цели осталась `NOT_EVALUATED`. Теперь добавим отказ: команда приложения завершилась до проверки цели, а runner продолжает обслуживать запросы. Эти факты могут одновременно быть верными. Разобрав их, инженер сможет восстановить работу с нужного шага, сохранив уже совершённое действие.

В этой главе разберём, как AX хранит принятую конфигурацию, когда обновляет статус и как доставляет уведомления. Затем соберём небольшой наблюдатель, который сопоставляет сведения из нескольких источников и предлагает следующий диагностический запрос. К концу главы вы должны уметь объяснить каждый индикатор в карточке Task: какое утверждение он подтверждает, когда это наблюдалось и чего ещё недостаточно для решения.

## Какие вопросы решает управляющий контур

Control plane, или управляющий контур, принимает запросы на создание, запуск, приостановку и удаление Task. Он хранит описание задачи и обращается к Substrate, который управляет Actor и его размещением на Worker. Runner подготавливает рабочее окружение и запускает команду внутри Actor. Harness организует работу приложения: шаги, инструменты, ожидания, контрольные точки и проверку результата.

Слово «состояние» используется на каждом из этих уровней, но вопросы разные. «Какую команду приняли?» относится к записи Task. «Где сейчас Actor?» - к Substrate. «Завершилась ли команда?» - к наблюдению за процессом. «Применена ли конфигурация?» - к квитанции операции. «Выполнена ли цель?» - к независимой проверке приложения. При расследовании полезно сначала сформулировать вопрос и только затем выбрать источник.

| Вопрос | Основной источник | Чего из него одного не узнать |
| --- | --- | --- |
| Какая Task spec принята, какой статус сохранён? | AX API и запись в Redis | Жив ли процесс сейчас |
| Существует ли Actor, каково его текущее назначение? | Substrate API и runtime inventory | Завершён ли прикладной шаг |
| Что сохранилось на диске или в snapshot? | Хранилище соответствующего типа | Можно ли безопасно повторить внешний эффект |
| Подготовлен ли workspace, что случилось с командой? | Runner, setup logs, сведения о процессе | Достигнута ли бизнес- или инженерная цель |
| Применена ли `op-17`, пройдена ли проверка цели? | Operation ledger, квитанция, проверка приложения | Здоров ли весь управляющий контур |

Источник истины здесь выбирается для конкретного утверждения. Подтверждённый ledger остаётся полезным после остановки Actor. Читаемый Redis может содержать старый статус работающего Actor. Чтобы понять инцидент, эти сведения соединяют по идентичности и времени, сохраняя их первоначальный смысл.

## Как устроен фактический путь AX

Далее рассматривается срез **AX `ac233282`**, указанный в паспорте книги. В нём `ax-server` выполняет reconciliation непосредственно из lifecycle handler. Reconciliation означает приведение ресурса к запрошенному состоянию через проверку и необходимые действия. Имя пакета `internal/controller` само по себе не означает отдельный постоянно работающий сервис. В этом пути нет отдельного `ax-controller` и очереди заданий на Redis Streams.

Для нового Task последовательность в [CreateTask](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/server/server.go) такова: проверить запрос, получить resource lock, убедиться, что имени ещё нет, сохранить Task с фазой `Suspended`, вызвать reconciler, затем сохранить итоговый статус. Следовательно, запись может появиться раньше Actor. При аварии между этими действиями инженер увидит принятую Task, для которой runtime ещё не создан.

При resume handler читает Task, задаёт `Running` в объекте в памяти, вызывает reconciler и сохраняет результат после его выполнения. Внутри reconciliation вызывается `ResumeActor`, получается адрес Worker и выполняется readiness-проверка. Ошибка сохранения после успешного изменения Actor оставляет две системы с разными сведениями: runtime уже изменился, Redis ещё содержит прежний статус.

Это две независимые записи - в управляющее хранилище AX и в runtime Substrate. Единой транзакции между ними нет. Даже Redis-транзакция, объединяющая изменение записи и публикацию уведомления, не охватывает создание или возобновление Actor. После timeout запроса выясняют, какие границы операция успела пройти. Новый `GetTask` помогает прочитать запись; запрос к Substrate помогает установить судьбу Actor. Только после этого выбирают дальнейшее действие.

![AX control path at ac233282: direct reconciliation and Pub/Sub watch](.gitbook/assets/diagrams/38-36.png)  
*AX control path at ac233282: direct reconciliation and Pub/Sub watch*

Представим три остановки одного запроса. До сохранения Task запись может отсутствовать. После сохранения, но до создания Actor - запись есть, Actor отсутствует. После изменения Actor, но до записи статуса - Actor уже работает, AX показывает прежнюю фазу. При восстановлении сохраняйте atespace/name и сведения о запуске: создание новой Task под другим именем способно запустить второй экземпляр работы, пока первый ещё существует.

Тот же принцип действует при suspend и delete. У suspend есть дополнительная особенность: ошибку `SuspendActor` reconciler записывает как warning, затем всё равно формирует фазу `Suspended`. Поэтому даже успешный ответ требует проверки runtime, если остановка важна для безопасности. Delete сначала сохраняет `Terminating`, выполняет cleanup Substrate и только затем удаляет запись Task. Авария между cleanup и удалением способна оставить `Terminating` уже без Actor.

Ответ API - важное свидетельство о выполнении handler, но при его потере результат устанавливают чтением обеих сторон. Успешная transport-проверка `/healthz` эту неопределённость не снимает: в данном [HTTP handler](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/server/server.go) маршрут просто возвращает 200, не проверяя Redis, Substrate или работу приложения. Кроме того, entrypoint допускает работу без reconciler при ошибке инициализации Substrate client. При расследовании проверьте конфигурацию и startup logs: доступный AX API сам по себе ещё не подтверждает включённое управление runtime.

## Что означает Running и как стареют conditions

Фаза - крупное состояние жизненного цикла. Condition уточняет отдельное свойство. Например, Task может иметь `phase: Running`, но condition `WorkspaceReady` со строковым статусом `"False"` и причиной `Initializing`. Это позволяет выразить ситуацию «Actor возобновлён, подготовка workspace ещё не подтверждена».

Упрощённый фрагмент AX JSON выглядит так; остальные поля опущены:

```
{
  "status": {
    "phase": "Running",
    "actor": "network-017",
    "workerIP": "192.0.2.20",
    "conditions": [
      {
        "type": "WorkspaceReady",
        "status": "False",
        "reason": "Initializing"
      }
    ]
  }
}
```

Написание `workerIP` задано protobuf-контрактом. `status` внутри condition - строка, а не JSON boolean. Сохранённый Worker IP пригоден как подсказка для маршрутизации; перед диагностикой после перемещения Actor его сверяют с текущим assignment в Substrate. Адрес может остаться доступным, но уже не относиться к интересующему нас размещению.

В [reconciler](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/controller/reconciler.go) стандартное окно ожидания workspace readiness составляет 15 секунд, интервал проверки - 500 миллисекунд. Сначала используется прямой путь, при настроенном router возможен маршрут через него. Когда окно заканчивается без готовности, reconciler может вернуть Task без ошибки вызова, сохранив `WorkspaceReady=False`. Само по себе это ещё не доказывает окончательный провал setup.

Если setup завершился на двадцатой секунде, сохранённая condition способна остаться прежней: `GetTask` читает запись, а фонового цикла, который постоянно опрашивает готовность всех Tasks, в этом пути нет. И обратная ситуация: после `WorkspaceReady=True` последующие reconciliation пропускают первоначальную readiness-проверку. Такое закреплённое значение удобно для результата подготовки, но плохо подходит для непрерывного контроля здоровья.

Особого внимания заслуживает `lastTransitionTime`. Функция `setCondition` записывает время при каждом обновлении найденной condition, даже если её значение не изменилось. Поэтому поле нельзя без проверки реализации читать как время первого перехода или heartbeat. Для отображения «подготовка подтверждена 10 секунд назад» нужен источник времени именно такого наблюдения.

Разделяйте время получения ответа и время факта. В 12:10 можно прочитать запись, последний раз обновлённую в 12:00. Запрос свежий, сведения о readiness - исторические. Для runner probe фиксируют момент самой проверки. Для записи AX фиксируют момент чтения и отдельно показывают, что condition является сохранённым утверждением. Если возраст факта неизвестен, так и пишут; назначать ему время HTTP-ответа опасно.

![Readiness hierarchy: each green light proves only its own layer](.gitbook/assets/diagrams/38-37.png)  
*Readiness hierarchy: each green light proves only its own layer*

Сведения о команде собирают отдельно. В [runner](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/runner/runner.go) после завершения дочернего процесса вызывается обработка exit, а сам runner продолжает ждать остановки. Так окружение остаётся доступным для исследования. Из этого следует практическая польза: инженер может забрать логи и файлы после падения команды. Одновременно HTTP-доступность runner перестаёт быть проверкой жизни приложения. Даже exit code 0 сообщает об успешном завершении команды по её соглашению, а проверку сетевой цели приложение должно зафиксировать самостоятельно.

## Watch: как обновлять экран и не терять смысл событий

Polling - периодическое чтение состояния. Он прост, но добавляет запросы даже тогда, когда ничего не меняется. Watch позволяет быстро узнавать об изменениях. В AX store использует Redis Pub/Sub: при записи Task публикуется её представление, а WatchTask подписывается на соответствующий канал. Здесь уведомление помогает обновить наблюдение; оно не заменяет журнал истории.

В [server WatchTask](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/server/server.go) подписка устанавливается до чтения первоначального объекта. Затем клиент получает `INITIAL`, если чтение удалось, и `MODIFIED` из подписки. Это уменьшает окно потери изменений при старте. Но изменение способно оказаться и в initial read, и в уже ожидающем сообщении; более старый payload из очереди может прийти после более нового initial snapshot. В Task API нет `resourceVersion`, позволяющей клиенту упорядочить эти представления как версионированный поток.

Redis описывает доставку Pub/Sub как [at-most-once](https://redis.io/docs/latest/develop/pubsub/#delivery-semantics): пропущенное при отключении подписчика сообщение не воспроизводится из истории канала. Watch handler также завершает поток при получении события с фазой `Failed` или `Completed`. Клиенту нужны обработка закрытия и повторное чтение. Само наличие проверки `Completed` в handler не означает, что runner автоматически выставляет эту фазу при выходе команды.

Для диагностической карточки разумна следующая схема. Уведомление помечает кеш устаревшим и планирует чтение Task. Несколько уведомлений объединяют в один запрос. После reconnect выполняют новое чтение и runtime-сверку там, где она нужна. Периодический опрос ограничивает возраст показанного состояния, даже если уведомления потерялись. Содержимое watch-сообщения не следует безусловно присваивать карточке как «самое новое».

Есть ещё одна гонка: пока выполняется чтение, приходит уведомление. Локальный счётчик invalidation позволяет отбросить результат такого чтения и повторить его. Этот счётчик описывает только работу клиента. Он не превращает AX в версионированное хранилище и не делает снимки Redis и Substrate атомарными. В работающем клиенте дополнительно нужны ограничение частоты повторов, backoff, jitter и предел числа одновременных запросов, иначе частые события сами перегрузят API.

Для расследования последовательности «кто запросил suspend, что успело выполниться, какое подтверждение было получено» нужен отдельный долговременный operation/audit journal. Если требуется воспроизведение событий, выбирают транспорт с хранением и подтверждением обработки, например Redis Streams, и проектируют retention, дедупликацию и повторную доставку. Подключение Streams само по себе не восстанавливает пропущенную запись о внешнем действии: границы сохранения событий и обработки всё равно придётся определить.

## Практика: собрать заключение по одному инциденту

В репозитории находится [examples/ch38\_state\_observer.py](https://github.com/5UN5H1N3/ax-agent-infrastructure-book/blob/main/examples/ch38_state_observer.py). Это локальная учебная модель, которая принимает четыре подготовленных наблюдения и составляет отчёт. Она не подключается к AX, Redis или Substrate и не выполняет repair. Все идентификаторы и времена в примере - доверенные входные данные, подготовленные для упражнения.

Каждое наблюдение содержит `observed_at` - время наблюдения факта, `fetched_at` - время получения его коллектором и привязку к рассматриваемому запуску. Для AX «факт» означает содержание прочитанной записи, для runner - результат свежей проверки и отдельно собранные сведения о команде. В реальной интеграции exit logs, process inspection и readiness endpoint потребуют своих коллекторов; приведённый словарь не является ответом стандартного endpoint runner.

Ключ привязки включает Task name, экземпляр запуска, Actor UID, назначение, root run и operation ID. **Экземпляр запуска и идентификатор назначения здесь введены нашим приложением**. У AX ObjectMeta в этом срезе есть name, atespace и creation timestamp, но нет собственного Task UID, generation или observedGeneration. Нельзя выдать учебные поля за штатные AX-гарантии.

В настоящем наблюдателе такую привязку формируют при запуске и проверяют через доверенный журнал корреляции и актуальный Substrate inventory. Ledger может пережить несколько Actor: связь ledger с текущим запуском берут из истории приложения, а не переписывают старую квитанцию новым Actor UID. При отсутствии надёжной связи наблюдение остаётся непривязанным. Совпадения имени Task недостаточно после её удаления и повторного создания.

Запуск из корня репозитория:

```
python3 examples/ch38_state_observer.py
python3 -m unittest discover -s examples -p 'test_ch38_state_observer.py'
```

В первом сценарии часы показывают 100, наблюдения сделаны в 96 и получены в 99. Допустимый возраст - 10 условных секунд. Числа выбраны для воспроизводимого теста; это не рекомендация использовать такой SLO в production.

| Наблюдение | Что заключает модель | Следующее полезное чтение |
| --- | --- | --- |
| AX: `Running`, сохранённая `WorkspaceReady=False` | Запись содержит такую фазу и condition; текущая готовность из неё неизвестна | Сопоставить со свежей проверкой runner |
| Substrate: Actor существует | Inventory подтвердил существование для связанного Actor и назначения | Проверить процесс и приложение |
| Runner: workspace ready, команда `EXITED`, code 1 | Подготовка и выход команды совместимы с доступным runner | Exit log и application checkpoint |
| Ledger: `APPLIED`, цель `NOT_EVALUATED` | Запись уже применена, проверка цели ещё не зафиксирована | Независимая проверка результата |

Выход сохраняет эти утверждения по отдельности. В нём нет общего `healthy=true`, а `automatic_mutations` всегда равен 0. Для данного инцидента появляются рекомендации `read_command_exit_log_and_application_checkpoint` и `read_independent_goal_verification`. Такой результат даёт оператору предметный следующий шаг: найти границу завершения приложения и доказательство цели. Повторять `op-17` из-за умершего процесса оснований нет.

Второй сценарий подставляет runner observation от прежнего назначения Actor. Программа возвращает `identity_mismatch` и не использует его в заключении. Это защищает от типичного ложного спокойствия: старый адрес отвечает, хотя нужный Actor уже перемещён. Третий сценарий сохраняет `fetched_at=99`, но меняет время факта на 50. Наблюдение отклоняется как `stale_observation`, несмотря на недавнее получение.

Наконец, `DirtyCache` показывает работу локальной invalidation. Уведомление во время чтения делает его результат непригодным для кеша; reconnect требует нового чтения. При полностью потерянном уведомлении кеш истекает по сроку опроса. Упражнение предполагает только одно незавершённое чтение за раз: счётчик invalidation не упорядочивает параллельные ответы. Модель проверяет правила принятия данных, но не выполняет сетевой цикл watch, не синхронизирует потоки и не реализует production backoff.

В тестах отдельно проверяются отсутствие источника, отрицательный результат успешного inventory-запроса, строка вместо boolean, неверный exit code, будущие и несогласованные времена. Отсутствующий ответ получает `UNKNOWN`, а достоверное `actor_exists=False` остаётся отрицательным фактом. Когда inventory сообщает отсутствие Actor, но runner недавно отвечал, программа предлагает повторную сверку: наблюдения могли попасть по разные стороны удаления или перемещения. Выбирать удобный ответ и скрывать второй было бы преждевременно.

### Что этот пример доказывает

Он воспроизводимо проверяет локальные правила сопоставления: неверная привязка и старые сведения исключаются, состояние операции не выводится из phase или exit code, пропажа watch не делает кеш вечным. Для разбирательства это небольшая, но полезная часть решения: результат чтений становится проверяемым, а не зависит от интуитивного толкования зелёных индикаторов.

Границы у упражнения существенные. Коллекторы считаются доверенными, общий искусственный clock не имеет рассинхронизации, входные квитанции не проверяются криптографически. Два наблюдения допустимого возраста всё ещё могли быть сделаны по разные стороны перехода. Свежесть ограничивает старение данных, но не доказывает, что факт сохраняется сейчас. Живой стенд и совместимость AX/Substrate здесь не испытываются.

Для переноса подхода в сервис понадобятся аутентифицированные read-only клиенты, разграничение доступа, контроль часов и интервалов наблюдения, проверка происхождения данных, ограничение нагрузки и хранение диагностических отчётов. Автоматическое восстановление потребует отдельного согласованного протокола с полномочиями, проверкой внешних эффектов и защитой от конкурирующих исполнителей. Его нельзя безопасно получить, заменив в конце observer `next_reads` на команды restart.

## Почему блокировка не устраняет все расхождения

Resource lock AX сериализует конфликтующие lifecycle handlers для одного kind/atespace/name, пока действует блокировка. В [RedisLocker](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/lock/lock.go) срок аренды по умолчанию - 30 секунд. Продление lease и fencing token в рассматриваемой реализации отсутствуют. Случайный token проверяется при освобождении, чтобы старый владелец не удалил чужую блокировку.

Предположим, запрос A получил lock, затем завис во внешнем вызове дольше срока аренды. Запрос B может получить новый lock, пока A ещё продолжает работу. Проверка token при unlock защищает запись блокировки, но не заставляет Substrate отвергать позднее действие A. Fencing, разобранный ранее в книге, требует монотонного поколения владения и проверки этого поколения принимающей стороной. Поэтому для долгих операций измеряют длительность, задают deadlines и отдельно проверяют поведение на границе истечения lease.

Локальный observer тоже не решает эту проблему: он читает последствия. Его полезность в том, что расхождение сохраняется как диагностический материал. Перед repair инженер выясняет, закончились ли прежние запросы и кому разрешено менять ресурс. Без этого новый «исправляющий» запрос может столкнуться с ещё работающим старым.

## Как выбирать инструменты наблюдения и восстановления

Начните с частоты решений. Для единичного инцидента часто достаточно AX API/CLI, Substrate inventory, exit logs и ledger. Сохраните ответы с временем и привязкой к запуску. Такой комплект быстро отвечает, какой слой требует следующей проверки; разворачивать новый event pipeline ради одного чтения обычно незачем.

Для операторского экрана полезна комбинация watch и ограниченного polling. Watch уменьшает задержку отображения, polling ограничивает срок незамеченного расхождения. Выбирая интервал, оцените число наблюдаемых Tasks и стоимость runtime-проверок: опрашивать Redis-record и выполнять глубокую проверку каждого Actor с одинаковой частотой обычно слишком дорого. Разделяйте дешёвое чтение карточки и диагностику по требованию.

Метрики подходят для поиска масштаба проблемы. Измеряйте latency create/resume/suspend/delete отдельно, ожидание lock, длительность Substrate calls и readiness wait, число активных lifecycle RPC и расхождений inventory. Это план инструментирования вашей системы, а не перечень обещанных встроенных AX metrics. Хвостовые p95/p99 важны рядом с API deadlines и lease TTL: среднее время может выглядеть приемлемо, пока отдельные операции уже пересекают опасную границу.

Трассировка помогает связать этапы одного запроса; долговременный журнал сохраняет сведения о принятом действии и восстановлении после сбоя. У них разные обязанности. По отсутствующему span нельзя заключать, что внешняя операция не выполнялась: trace мог быть потерян или не выбран sampling. Для права повторить запись нужен operation contract главы 37 и подтверждение принимающей стороны.

При росте нагрузки помните, что direct path выполняет lifecycle work внутри API handler. Дополнительные API replicas увеличивают параллелизм разных Tasks и нагрузку на зависимости; они не ускоряют конфликтующие операции одного ресурса. Сначала ограничивают admission rate и concurrency, затем измеряют узкое место. Отдельный асинхронный reconciler имеет смысл, когда переходы должны переживать API deadline и crash. Это изменение архитектуры: ему нужны durable intent, повторная обработка, ownership, отмена и правила работы со старой конфигурацией. Очередь становится одним из компонентов такого решения.

## Сохранность Redis и изменение общей конфигурации

В этом контуре Redis хранит принятую Task spec, Workspace и Model. Потеря записи может оставить работающий Actor без обычной точки управления в AX. Поэтому требования к Redis определяются допустимой потерей управляющих данных, а не только скоростью ответа.

Пример [deploy/redis.yaml](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/deploy/redis.yaml) задаёт одну replica Deployment без PVC, volume mount и явной настройки persistence. Для production нужно отдельно выбрать и проверить сохранность. RPO задаёт допустимое окно потери изменений, RTO - время до оговорённого восстановления. [RDB и AOF](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/) дают разные компромиссы: RDB сохраняет снимки, поэтому изменения после последнего пригодного снимка можно потерять; AOF записывает команды изменения, а выбранная политика fsync влияет на задержку и окно возможной потери. Их наличие ещё не заменяет проверку backup и restore. Восстановление должно включать последующую сверку с живыми Actor: возвращённый из backup Redis может описывать прошлое состояние runtime.

Для управляющих записей политика [`noeviction`](https://redis.io/docs/latest/develop/reference/eviction/#eviction-policies) позволяет предпочесть ошибку новой записи скрытой потере старой из-за вытеснения. За это платят необходимостью резерва памяти, alerts и ограничения приёма новых операций. Политика кеша вроде `allkeys-lru` требует иной модели: потерянные значения должны откуда-то восстанавливаться.

Expiry - ещё одна отдельная граница. Store поддерживает optional Task TTL; entrypoint использует default options без заданного срока, Workspace и Model сохраняются без expiry. Если в своей сборке вы включили TTL, исчезновение Task key само по себе не вызывает DeleteTask. Потребуются правила очистки Actor, индексов и сохранения ownership. Аналогично backup Redis не содержит файловую систему Actor и внешний ledger приложения.

Обновление Workspace или Model также требует проверки фактического результата. Соответствующие handlers сохраняют ресурс, но не запускают автоматический обход всех работающих Tasks. Workspace spec участвует в подготовке launch configuration; уже материализованные файлы не меняются от одного update записи. Следующий reconcile способен получить новую spec, а `EnsureActor` при этом может вернуть существующий Actor. Закреплённая readiness condition не проверит, что его окружение теперь соответствует новой конфигурации.

Для управляемого rollout фиксируйте версию Workspace, Git revision, image digest и фактическую конфигурацию приложения. Новую canary Task проверяйте отдельно, затем переводите новые runs. Продолжение прежнего run требует решения о checkpoints и незавершённых operations. Для Model проверяйте способ использования ресурса конкретным harness: он может читать конфигурацию заново или сохранять её при запуске. Запись нового model ID в Redis ещё не доказывает смену модели в живом процессе.

## Как завершить расследование

Вернёмся к `lab/network-017`. Сохранённый `Running` объясняет состояние управляющей записи. Свежая проверка подтверждает подготовленный workspace, exit evidence - остановленную команду, а ledger сохраняет `APPLIED` для `op-17`. Следующая работа - прочитать checkpoint, установить, почему приложение остановилось, и выполнить разрешённую проверку цели. Решение о продолжении принимают после этого; повторное сетевое изменение в диагностический план не входит.

В incident record запишите факты с источниками и временем, исключённые наблюдения и оставшиеся вопросы. Формулировка «Task сломалась» почти не помогает следующему инженеру. «Команда завершилась с code 1 после подтверждённой записи config-18; runner доступен; проверка цели не выполнена» даёт понятную точку продолжения.

Перед доверием к работающему наблюдателю проведите отдельные стендовые испытания: остановку handler между сохранением Task и созданием Actor, потерю ответа после ResumeActor, setup дольше окна polling, разрыв watch и операцию дольше lock TTL. Проверьте также потерю Redis Pod, перемещение Actor и update Workspace уже работающей задачи. Для каждого испытания заранее определите ожидаемые чтения и запрещённые автоматические действия. Локальные тесты этой главы эти отказы в AX не воспроизводят.

Теперь предположим более тяжёлый случай: Worker потерян, прежнего runner уже нет, а Task record и ledger читаются. Чтобы продолжить приложение, потребуется установить, какое сохранённое состояние Actor существует, кому принадлежит snapshot и с каким окружением его можно восстановить. Эти вопросы разберём в главе 39. Навык этой главы пригодится и там: каждая сохранённая запись отвечает на свой вопрос, а безопасное решение строится из проверенных связей между ними.
