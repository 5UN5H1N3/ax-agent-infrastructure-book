# Приложение C. Карта источников

После учебного запуска вы хотите освободить место в хранилище. Новые Actors созданы из Tag и уже видны в API. Прежде чем удалить исходный Tag, нужно выяснить, что появилось у каждого Actor: собственные файлы снимка или только запись с адресом общих данных. От этого зависит возможность восстановления.

Ниже собраны маршруты от инженерного вопроса к нужному документу и участку кода. Выберите тему в C.2–C.7, а затем проверьте условия своего случая. В C.8 подробно разберём зависимость Actor от Tag: найдём поле API, проследим запись адреса и объясним, почему удаление данных требует отдельной проверки.

## C.1 Как выбрать источник и сохранить контекст

Сначала сформулируйте действие, для которого ищете ответ: удалить Tag, выбрать клиент MCP или изменить лимит контекста. Затем найдите подходящий маршрут в C.2–C.7. Например, для удаления Tag нужно понять, кто ещё использует его данные, а для клиента MCP — какие сообщения и возможности он должен поддерживать.

| Что нужно выяснить | С чего начать |
| --- | --- |
| Устройство компонента и обычный путь настройки | Руководство и README |
| Допустимые поля и обязательства сторон | Схема API или спецификация протокола |
| Обработка конкретного случая | Код нужной версии: условие, вызванная функция, запись результата |
| Поведение установленной системы | Тест с известными входами и проверяемым результатом |

Для повторного чтения сохраните репозиторий, полный commit, путь и имя функции или поля. Для вывода о работающей системе понадобятся также digest установленного образа, его связь с исходниками и значимая конфигурация. Если прочитан только код, вывод относится именно к этому коду. Полный метод и образец карточки находятся в [приложении A](appendix-a-audit.md), критерии допуска — в [приложении B](appendix-b-production-readiness.md).

В таблицах C.2–C.3 закреплены AX `ac233282` и Substrate `v0.3.0` / `ccecc788`; разбор C.8 использует тот же срез Substrate. Профили других глав, отдельного практикума и inference собраны в [карте версий главы 0](00-reading-guide.md). Открывая ссылку, сверяйте профиль своей задачи. Указатель `main`, `master` или `latest` может измениться; для повторения закрепите commit или версию документа. Если страница переехала, найдите тот же файл в выбранном дереве или архиве выпуска.

Для одного поля обычно достаточно браузера и ссылки на закреплённый файл. Для поиска по нескольким файлам удобнее [git grep](https://git-scm.com/docs/git-grep), для чтения файла без переключения ветки — [git show](https://git-scm.com/docs/git-show), для сравнения версий — [git diff](https://git-scm.com/docs/git-diff). В C.8 эти операции складываются в один воспроизводимый поиск; повторять вводный аудит A для каждого маршрута не нужно.

Прочитайте, кто прекращает новые попытки и что происходит с уже отправленным действием. Такой маршрут показывает, нужен ли контроль внутри harness и какой failure case включить в тест. Одного поля с названием budget для этого решения мало.

Для смены архитектурного профиля откройте [дерево AX v0.3.1](https://github.com/google/ax/tree/e70162a34037c221fe6fadefd98308c05a4ad8f3) и сравните его с `ac233282`. В первом есть отдельный controller; во втором reconciliation выполняет server. Поэтому старый runbook поиска зависшей очереди нужно сопоставить с новым путём обработки. [Issues AX](https://github.com/google/ax/issues) помогают найти обсуждение и fix; включение fix в используемую сборку устанавливается по commit и сведениям о её происхождении.

Для готовности приложения выберите наблюдение его полезного результата: отчёт, изменение объекта или проверку цели. Ответ probes и exit code процесса относятся к своим контрактам. В главе 43 показано, как связать эти наблюдения в приёмку, сохраняя отдельный статус каждого case.

## C.3 Substrate и зависимости восстановления

В Substrate различайте Actor, место его исполнения и сохранённые данные. Actor может сменить Worker. Метаданные указывают на снимок, а правила хранения определяют, кому принадлежат его данные и когда их удаляют. Поэтому вопросы о жизненном цикле, вычислительных ресурсах и сроках хранения ведут в разные части проекта.

Перед выбором изоляции прочитайте принятые допущения об угрозах и найдите место проверки нужного запроса. В закреплённом руководстве по аутентификации обычные доверенные providers получают широкий доступ к RPC. Наличие JWT не означает готовой системы детальных ролевых прав. Это условие влияет на границу установки. Для экспериментов с авторизацией из главы 24 используйте именно её срез и отдельно опишите доступ.

В коде хранилища различайте создание новой копии данных и сохранение их адреса. Затем проверьте удаление и смену текущей точки. Для Full важно также восстановить совместимую среду выполнения; для Data — получить среду запуска и сохранить нужные golden-зависимости. Механизмы разобраны в [главе 39](39-substrate-snapshot-ownership.md). В C.8 проследим один случай: зависимость нового Actor от исходного Tag сразу после создания.

Development quickstart главы 26 закреплён в [README df788825](https://github.com/agent-substrate/substrate/blob/df788825e6fc13dd7aa5fd283c8f14bd4c818247/README.md). Выбирайте его для воспроизведения того lab, а release-документы - для механизма своей версии. При обновлении [Substrate releases](https://github.com/agent-substrate/substrate/releases) дают список изменений, по которому выбирают schema diff и затронутые restore cases. Перенос snapshots требует проверки совместимости формата, runtime assets и зависимостей.

## C.4 MCP и выбор совместимой пары

Сначала запишите, какую операцию должно уметь приложение: короткое чтение, запись с approval, получение промежуточного результата или продолжение долгой работы. Затем установите revision протокола, transport и нужные возможности. SDK делает вызовы удобными, но выбор его версии следует из этого профиля. Поддержка одного простого tool не отвечает на вопросы о всех остальных сценариях.

| Вопрос интеграции | Первичный источник | Что сопоставить со своей парой |
| --- | --- | --- |
| Что обязательно в сообщениях? | [Base protocol 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/index) | Самодостаточный запрос, его метаданные и схему |
| Как узнать возможности и вызвать tool? | [Discover](https://modelcontextprotocol.io/specification/2026-07-28/server/discover) и [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) | Возможности, входы и выходы, обработку ошибок и аннотации |
| Что требует HTTP transport? | [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) | Заголовки, контекст аутентификации и поведение соединения |
| Откуда взялся другой порядок сообщений? | [Legacy lifecycle 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) и [контекст изменений 2026](https://blog.modelcontextprotocol.io/posts/2026-07-28/) | Редакцию протокола сохранённого trace и правила каждой стороны |

Например, в trace виден `initialize`. Для revision `2025-11-25` это часть handshake. В модели `2026-07-28` request несёт собственные protocol metadata и client capabilities. Чтобы оценить trace, выясните заявленную revision, а затем сравните сообщение с её требованиями. Перестройка современного клиента по старому примеру могла бы внести ошибку в исправную интеграцию. Подробный разбор сообщений находится в главе 36.

На разрешённом fixture проверьте корректный read, ошибочный input и понятную ошибку несовместимому запросу. Для доступа добавьте разрешённый контрольный вызов и ожидаемый отказ чужому principal. Для write заранее выберите способ выяснить outcome после потери ответа. В integration record сохраните revision, версии и builds client/server SDK, transport и нужные capabilities.

Аннотация инструмента описывает действие для клиента; право выполнить его проверяется отдельно. Чтобы не повторить внешний эффект после потери ответа, нужны соответствующий контракт адаптера и исполнителя и проверка H4 из приложения B. Учитывайте это, выбирая клиент с автоматическими повторами.

## C.5 Kubernetes и выбор границы изоляции

Неуспешный запрос может означать, что приложение не готово, маршрут запрещён или конечный сервис отказал в доступе. Определите, где должно проверяться нужное условие, и найдите этот механизм. [Kubernetes Concepts](https://kubernetes.io/docs/concepts/) служит удобной отправной точкой.

| Решение | Руководство | Следующий инженерный шаг |
| --- | --- | --- |
| Разделить startup, liveness и readiness | [Pod probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/) | Установить, что измеряет проверочный адрес и какое действие следует за отказом |
| Ограничить сетевую достижимость | [NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/) | Проверить поддержку правил сетевым модулем, выбор объектов и контрольный разрешённый путь |
| Хранить credentials | [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/) | Определить доступ, защиту хранения и способ отзыва у конечного поставщика |
| Разобраться с расширением API | [Custom resources](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/) | Найти API своего объекта и управляющий им контроллер |
| Выбрать sandbox | [gVisor architecture](https://gvisor.dev/docs/architecture_guide/intro/) | Сопоставить угрозы, совместимость нагрузки, ограничения и стоимость исполнения |

Перед применением NetworkPolicy выясните, по какому пути идёт трафик агента: через сеть обычного Pod, из гостевой среды или через исходящий прокси. Затем найдите механизм, который контролирует этот путь. Проверьте оба случая: разрешённый запрос проходит, запрещённый не достигает тестового адресата. Ошибка DNS без исправного контрольного запроса не позволяет установить причину. Ограничения сетевого модуля сверяйте с его документацией.

Выбирая sandbox, определите, что считаете недоверенным: исполняемый код, его зависимости или доступные ему данные. Изоляция ограничивает последствия захвата среды, а права на внешние системы задаются отдельно. Если учётной записи разрешена опасная операция, граница вокруг процесса не запретит её. При выборе нужны оба слоя защиты.

Среду для обучения выбирайте по опыту, который хотите провести. [Kind](https://kind.sigs.k8s.io/docs/user/quick-start/) удобен для локальной работы с Kubernetes API и manifests. [K3s architecture](https://docs.k3s.io/architecture) помогает оценить компактную установку на выделенных nodes. [kubeadm guide](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/) полезен, когда учебная задача включает устройство и подготовку самого кластера. Возможность запустить выбранный sandbox backend проверяют по его host requirements и вашей topology.

Для nested lab главы 26 начните также с [Proxmox Nested Virtualization](https://pve.proxmox.com/wiki/Nested_Virtualization). Расширения CPU должны быть доступны гостевой VM, а нужные runtime interfaces - среде исполнения. В протоколе опыта разделите «кластер установлен» и «нужный sandbox path испытан». Так результат одной проверки не подменит другую.

## C.6 Inference и выбор измеримого профиля

Агент отвечает слишком долго, и команда предлагает оптимизацию из недавнего испытания. Сначала измерьте, где проходит ожидание: в очереди, при обработке входа или при генерации токенов. Затем откройте руководство по соответствующему механизму. Проверка с коротким запросом может не описывать работу с длинным контекстом; для своей установки нужен сопоставимый опыт.

Для профиля главы 41 используйте следующие маршруты vLLM `v0.31.0`:

- [OpenAI-compatible server](https://docs.vllm.ai/en/v0.31.0/serving/online_serving/openai_compatible_server/) и [engine arguments](https://docs.vllm.ai/en/v0.31.0/configuration/engine_args/) - для endpoints, startup flags и поддерживаемых режимов. Сопоставьте client request с фактическим model/tokenizer и chat template. Совпадение формы API оставляет эти параметры существенными.
- [Conserving memory](https://docs.vllm.ai/en/v0.31.0/configuration/conserving_memory/) и [parallelism and scaling](https://docs.vllm.ai/en/v0.31.0/serving/parallelism_scaling/) - для ограничений памяти и распределения работы. Запишите weights, KV cache, длину context, concurrency и GPU topology, чтобы понять причину выбранного ограничения.
- [Metrics](https://docs.vllm.ai/en/v0.31.0/usage/metrics/) - для выбора наблюдений и единиц. Сопоставьте серверные сигналы с задержкой клиента: TTFT показывает время до первого token, ITL - интервалы последующей генерации. Границу измерения указывайте явно, особенно если между клиентом и backend есть gateway и очередь.
- [vLLM releases](https://github.com/vllm-project/vllm/releases) - для поиска изменений перед обновлением. Выделите затронутые flags, модельные пути и ограничения, затем повторите нужные capacity и quality cases на candidate.

Выбор между увеличением памяти, сокращением context и снижением concurrency зависит от задачи. Для большого документа сокращение context может убрать нужные сведения; для интерактивного помощника длинная очередь может нарушить допустимое ожидание. Сравните варианты при одинаковых входах и отдельно оцените качество результата. Рабочий итог - профиль с объяснимой ценой в памяти, задержке и качестве.

Для другого сервера начните с [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). Эта ссылка меняется вместе с проектом: перед опытом сохраните commit или сборку, хеш GGUF, квантование, шаблон запроса и параметры запуска. Релизный ориентир `v0.4.1` и непрерывно выпускаемая сборка — разные обозначения поставки. Выбирайте конкретный вариант по поддержке модели, оборудованию и нужным операциям API, затем испытывайте ту же нагрузку.

Статьи [GQA](https://arxiv.org/abs/2305.13245) и [PagedAttention](https://arxiv.org/abs/2309.06180) объясняют механизмы attention и управления KV-кешем и условия опубликованных испытаний. Параметры своей сборки ищите в её руководстве, а потребность в ресурсах и выигрыш устанавливайте измерениями. В главе 41 показано, как перейти от устройства механизма к расчёту бюджета.

## C.7 Эксплуатация и проверка полезного восстановления

В эксплуатации выбирайте источник по тому, что перестало работать. Если после восстановления недействителен секрет доступа, проверьте выдавшую его систему и правила отзыва. Если база запустилась, но агент не продолжает задачу, выясните, хватает ли ему метаданных, файлов и ключей. Событие «сервис запущен» описывает только один участок восстановления.

В [Vault leases](https://developer.hashicorp.com/vault/docs/concepts/lease) найдите срок жизни, renewal и revocation dynamic credential. Затем проследите, что соответствующий secrets engine делает у provider. Для значения, сохранённого в KV, нужны правила ротации и отзыва самого конечного credential. Сохранение старого значения в snapshot и доступ к secret store после restore - разные части этой задачи.

Для PostgreSQL начните с [continuous archiving и PITR в manual 17](https://www.postgresql.org/docs/17/continuous-archiving.html). PITR восстанавливает данные к выбранному моменту с помощью backup и журнала изменений; требуемая цепочка должна быть доступна и пригодна для вашей major version. Номер 17 обозначает версию этого руководства, а не установленную database книги. Для Redis откройте [RDB/AOF persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/) и сопоставьте описанные свойства со своей версией и фактическими settings.

Далее проверьте восстановление всей прикладной работы. Task нужны данные Workspace, ключи и контрольные точки, а незавершённой внешней записи — способ установить её исход. Выберите полезный результат, который приложение должно получить после восстановления. Потерю прогресса и время до этого результата измеряйте раздельно; пример RPO/RTO находится в B.5 и B.8. Запуск базы подтверждает только её часть восстановления.

[Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/) помогает строить проверяемые гипотезы. Например, из предположения об истёкшем credential следует конкретная проверка issuer/expiry и разрешённый контрольный запрос. [Canarying Releases](https://sre.google/workbook/canarying-releases/) помогает выбрать comparison, ограничить экспозицию и определить stop conditions. [Reliable Product Launches](https://sre.google/sre-book/reliable-product-launches/) - подготовить выпуск и передачу ответственности. Эти методы команда связывает со своим workload, SLO и доступными наблюдениями.

Итог чтения запишите как шаг инструкции дежурного: какое состояние проверить, что ожидается и кому передать открытый вопрос. Для доступа к хранилищу это может быть запрос от нужного субъекта к синтетическому объекту, для восстановления — заранее разрешённое испытание в отдельной учебной среде. Право читать руководство не разрешает проводить такой опыт в рабочей системе.

## C.8 Сквозной разбор зависимости Actor от Tag

### Поставить вопрос о конкретной операции

Проверим, можно ли удалить исходный Tag. Рассматриваем Substrate `v0.3.0` и Actor с явно заданным `sourceTag` до его первого собственного успешного suspend. Нужно выяснить, создала ли операция CreateActor независимую копию данных снимка. Если нет, исходный Tag ещё нужен для восстановления.

Для разбора нужен Git, POSIX shell, доступ к публичному репозиторию и место для исходников. Мы создадим отдельный временный bare repository - хранилище объектов Git без рабочего checkout. Загрузим один закреплённый commit и прочитаем файлы. Команды не запускают upstream-код, не подключаются к cluster API и не удаляют Tag или payload.

```
sources_dir=$(mktemp -d)
git init --bare "$sources_dir/substrate.git"
sources_rev=ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97
git -C "$sources_dir/substrate.git" fetch --depth=1 \
  https://github.com/agent-substrate/substrate.git "$sources_rev"
git -C "$sources_dir/substrate.git" rev-parse 'FETCH_HEAD^{commit}'
```

Последняя команда должна напечатать полный SHA из `sources_rev`. Так вы проверяете выбранный объект. Это ещё не проверка происхождения установленного image. Загрузка с `--depth=1` экономит историю; для поиска старого изменения потребуется отдельно получить нужные commits. Если нет Git, те же закреплённые файлы можно открыть по ссылкам из C.3 в браузере.

### Найти поле и пройти путь записи результата

```
git -C "$sources_dir/substrate.git" grep -n \
  -e source_tag -e sourceTag "$sources_rev" -- \
  pkg/proto/ateapipb/ateapi.proto docs/api-guide.md \
  cmd/ateapi/internal/controlapi/actor.go
git -C "$sources_dir/substrate.git" show \
  "${sources_rev}:cmd/ateapi/internal/controlapi/actor.go"
git -C "$sources_dir/substrate.git" show \
  "${sources_rev}:cmd/ateapi/internal/controlapi/workflow_tag.go"
```

В схеме найдите `Actor.source_tag`, в руководстве API — описание `CreateActor`. Затем прочитайте `ServiceImpl.CreateActor` в `actor.go`. После выбора исходного Tag код заполняет `outActor.Status.ExternalSnapshot`, вызывая `proto.CloneOf` для записи о снимке Tag. Посмотрите на тип аргумента: копируется protobuf-сообщение с адресом и метаданными. Файлы по этому адресу остаются прежними. Именно содержимое операции, а не слово CloneOf, объясняет результат.

Теперь откройте `workflow_tag.go` и найдите `ensureTagSnapshotCopied`. Там отдельно вызывается `objectstore.CopyPrefix`: данные копируются из исходного префикса хранилища в префикс Tag. Функция `ensureTagFinalized` публикует результат в `status.snapshot`. Этот путь создаёт новую копию данных — при создании Tag из внешнего снимка приостановленного Actor.

Для решения об удалении прочитайте также `DeleteTag`. Он вызывает `ensureTagSnapshotReleased`, где `DeletePrefix` удаляет данные снимка, принадлежащего Tag, затем удаляется запись Tag. Теперь видна вся зависимость: новый Actor получил адрес данных Tag, отдельная операция умеет копировать данные в собственность Tag, а удаление владельца освобождает их. Основание вывода — присвоенный URI, его владелец и связанный путь удаления, а не отсутствие имени CopyPrefix в одном файле.

Сверьте найденные операции с комментарием рядом с присваиванием: он описывает заимствование до первого собственного suspend. Комментарий помогает ориентироваться, а вывод подтверждают действия с метаданными и хранилищем. Если назначение вызванной функции неясно, прочитайте и её определение.

### Сформулировать решение с правильной областью действия

В рассмотренном пути новая запись Actor не создаёт отдельной копии данных. Исходный Tag остаётся зависимостью его снимка. Число созданных Actors и сам факт их запуска не разрешают удаление. Перед ним нужен перечень всех ссылок на данные, включая другие заимствующие Actors и golden-зависимости. Переход к собственной завершённой точке разобран в главе 39.

Учебная карточка фиксирует этот узкий результат. Имена полей ниже принадлежат формату отчёта команды, а не API Substrate. Полный commit и пути заданы в командах выше; в рабочую запись перенесите также immutable ссылки и дату:

```
question: independent payload immediately after CreateActor
source_revision: ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97
case: explicit sourceTag before first own suspend
symbols:
  - ServiceImpl.CreateActor
  - ActorWorkflow.ensureTagSnapshotCopied
  - ActorWorkflow.ensureTagSnapshotReleased
finding: actor initially borrows tag snapshot URI
source_claim_independent_copy: REFUTED
deployed_image_mapping: UNKNOWN
restore_test: NOT_RUN
decision: keep source tag pending dependency review
next_check: inventory payload references for selected build
```

`REFUTED` относится только к утверждению о немедленной независимой копии в прочитанном срезе. Для действующей установки сначала сопоставьте образ с исходниками и соберите актуальные ссылки на данные. Затем, в разрешённой учебной среде, проверьте восстановление с синтетическими данными и прикладным результатом. Чтение кода и этот опыт дают разные части обоснования.

### Разобрать расхождение и закончить поиск

Если руководство говорит о копировании, уточните операцию: создание Tag и создание Actor через sourceTag проходят разными путями. Затем сравните версии и условия выполнения. При различиях прочитайте изменения нужных файлов и вызванных функций. Общее слово «клонирование» не заменяет описание конкретной операции API.

Если расхождение остаётся, сохраните обе ссылки и минимальный пример. Локальная правка установки или неизвестное происхождение сборки потребуют отдельной проверки её состава. Текущий поиск на этом можно закончить: поведение исходников объяснено, опасное удаление остановлено, следующая проверка определена.

## C.9 Самостоятельная работа и обновление карты

Выберите решение из своей задачи: подобрать клиент MCP, изменить лимит context или разрешить recovery. Сформулируйте один вопрос с наблюдаемым следствием и найдите маршрут в C.2-C.7. Выполните следующие действия:

1. Запишите рассматриваемую версию, входы и существенные условия. Назовите другой профиль книги, с которым её легко перепутать.
2. Выберите объясняющий источник и точный контракт. Покажите, какие части вопроса каждый из них закрывает.
3. Найдите реализацию или тест нужной ветки. Для теста укажите, что исполняется реально и где стоят mocks; для кода - проверку условия и запись результата.
4. Составьте карточку: вывод, разрешённое сейчас действие, оставшийся вопрос и способ его проверить. Если нужен опыт, задайте ожидаемый прикладной результат и допустимую область воздействия.
5. Передайте запись коллеге. Он должен открыть те же объекты и объяснить, почему принято это решение, без угадывания версии и значения слова «работает».

При обновлении начинайте с сохранённых предпосылок решения. Смена API, snapshot format или auth policy направляет повторное чтение и тесты на соответствующие пути. Изменение ссылки на сайте сначала требует найти тот же документ; оно само по себе не меняет runtime. Обновляйте source record и результаты проверки раздельно, чтобы было видно, откуда появился новый вывод.

В итоге у инженера остаётся понятная цепочка: вопрос, источник нужной версии, объяснение механизма и проверяемое действие. Приложение A помогает провести аудит, B - принять ограниченное решение о допуске, C - найти основание для следующего шага. Этой цепочки должно хватать другому человеку, чтобы продолжить работу, не повторяя весь ваш поиск.
