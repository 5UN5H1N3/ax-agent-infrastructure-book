# Приложение B. Production readiness checklist

Команда готовит сетевого агента к работе с пользователями. Он уже выдаёт отчёты, умеет предложить изменение конфигурации и ждёт approval перед записью. На встрече перед выпуском нужно решить, какую нагрузку ему можно доверить, кто остановит rollout при ошибке и как восстановить работу после отказа. Для этого разработчику, инженеру платформы и дежурному требуется общее основание решения.

**Production readiness** - готовность конкретной системы выполнять оговорённую работу с допустимым риском и поддерживаться командой эксплуатации. Она относится к выбранной сборке, конфигурации, данным, правам и нагрузке. Checklist помогает сделать существенные вопросы видимыми и назначить для них проверки. Его практический результат - решение о допуске с понятными границами и ответственными людьми.

[Глава 43](43-operations-runbook.md) объясняет устройство приёмки и runbook, [приложение A](appendix-a-audit.md) - проверку утверждений по исходникам. Здесь сохраним 25 критериев `P1`-`G3` и научимся применять их к выпуску. Эти ID обозначают пункты инженерного review, а не поля AX API или автоматически встроенные гарантии платформы. В B.8 разберём результаты запускаемых локальных примеров и составим решение, которое они действительно позволяют принять.

## B.1 Область допуска и запись результата

### Сначала определить разрешённую работу

Начните с короткого описания сервиса: кто им пользуется, какие данные он получает, какие операции выполняет и что пользователь должен получить в итоге. Для учебного сетевого агента полезный результат - отчёт по входной конфигурации и, при отдельном разрешении, одно изменение на согласованной цели. Чтение конфигурации и её изменение получают разные границы доступа и последствия ошибки.

Зафиксируйте профиль запуска. В нём должны быть tenant, разрешённые tools и targets, характер данных, предел нагрузки, бюджеты и допустимое ожидание. Профиль «read-only анализ synthetic конфигураций» позволяет проверить часть механизмов с малым риском. Для работы с настоящими сетевыми устройствами потребуется другой профиль и дополнительные свидетельства. Слово «пилот» само по себе область разрешённых действий не меняет.

Затем сопоставьте критерии с рисками этого профиля. У каждого применимого критерия определите обязательные cases, владельца проверки и человека, принимающего остаточный риск. В маленькой команде роли могут совпадать; важно, чтобы решение имело конкретного адресата. Неприменимость фиксируют с причиной: например, отсутствие write capability исключает опыт с внешним write, но оставляет проверки прав на чтение, бюджетов и обращения с данными.

Статус результата и применимость храните раздельно. `N/A` в поле применимости означает согласованное отсутствие соответствующего сценария; в качестве результата выполненного теста его использовать не нужно. Если write обнаружился вопреки read-only профилю, пересмотрите профиль и результаты. Удалять неудобный обязательный case из списка после прогона опасно: вместе с ним исчезает вопрос, ради которого проводилась проверка.

### Что должно быть в записи

**Evidence** - проверяемые свидетельства: исходные условия опыта, наблюдения, отчёт теста, измерения и сверка результата в конечной системе. Скриншот dashboard может помочь разбору, но для повторения опыта нужны также версии, входы и критерий успеха. Чувствительные материалы хранятся отдельно; общая запись содержит разрешённые ссылки на них.

| Часть записи | Что требуется следующему проверяющему |
| --- | --- |
| Область | Профиль работы, этап допуска, нагрузка и доступные операции |
| Сборка | Фактические image digests, commits, model, adapters, policy и config revisions |
| Проверка | ID критерия и case, ожидаемое поведение, fixture, среда и допустимое воздействие |
| Наблюдение | Что произошло, когда, где лежат logs, artifacts и независимая проверка результата |
| Решение | Статус, незакрытые вопросы, владелец, предел допуска и условия повторной проверки |

Привязка к сборке охватывает зависимости, влияющие на проверяемое поведение. Замена tool adapter может изменить retries; смена model profile - качество и длительность работы; новая policy - разрешённый путь запроса. Для повторного использования прежнего отчёта проверьте именно эти предпосылки. Возраст отчёта сам по себе не заменяет такой анализ. Hash помогает сравнить содержимое; доверие к источнику отчёта обеспечивают происхождение и канал доставки.

| Статус case | Как его понимать | Обязательный case текущего этапа |
| --- | --- | --- |
| `PASS` | Ожидание выполнено в записанных условиях | Даёт свидетельство для своего критерия |
| `FAIL` | Наблюдение противоречит ожиданию | Требует исправления и повторной проверки |
| `BLOCKED` | Проверке мешает конкретная отсутствующая предпосылка | Остаётся открытым до её получения |
| `SKIPPED` | Проверку не выполняли; причина указана | Остаётся открытым, пока она обязательна |

Критерий закрывается после всех относящихся к нему обязательных cases. Зелёный deny test ещё не закрывает все требования tenant isolation. Если запись отсутствует, review показывает пробел; он не подставляет `PASS`. Долю прошедших cases можно использовать для планирования работы, но решение о безопасности нельзя получить усреднением успешных reads и одного запрещённого write.

### Выбрать средства проверки

Начать можно с версионируемого YAML или таблицы: 25 критериев, cases, владельцы и ссылки на результаты. CI удобен для повторяемых опытов и сбора artifacts. Issue tracker помогает довести открытый вопрос до решения. Когда несколько команд выпускают разные профили и нужны формальные approvals, имеет смысл отдельный сервис допуска. Он должен проверять полноту и привязку результатов; само название такого сервиса не делает evidence достоверными.

| Нужно выяснить | Подходящее средство | Что оно устанавливает |
| --- | --- | --- |
| Выполняется ли конечная задача? | Прикладной тест с oracle - независимой проверкой результата | Содержание artifact, ответ или изменение целевого объекта |
| Работает ли запрет? | Allowed control, denied request и проверка отсутствия effect | Отказ на нужной границе при исправном контрольном пути |
| Укладывается ли нагрузка в контракт? | Генератор своего workload и связанные метрики | Задержку, качество, ошибки и поведение при перегрузке |
| Восстанавливается ли сервис? | Restore drill и журнал событий | Возвращение полезной работы и фактическую потерю состояния |
| Может ли команда поддерживать сервис? | Учебное дежурство с другим оператором | Доставку alert, доступ к evidence и исполнение runbook |

Такой подбор проверок продолжает идею [launch checklist Google SRE](https://sre.google/sre-book/reliable-product-launches/): вопросы должны вести к конкретным разумным действиям и адаптироваться к запуску. Чужие пороги latency или готовый список компонентов полезны как ориентир для обсуждения. Приёмочные значения команда выводит из своего пользовательского контракта и измерений.

## B.2 Платформа и доступность зависимостей

### P1. Запущена именно проверенная сборка

Сверьте фактические digests server, runner и sandbox assets с release inventory. Сохраните provenance сборки, revisions Workspace, model artifacts и adapters. Tag помогает найти версию, digest определяет image bytes, а provenance связывает их с исходниками и входами сборки. В отчёт должны попасть и overrides конфигурации: они способны изменить поведение того же образа.

Для relocation и cold start проверьте получение нужного image из registry с правами нового Worker. Уже прогретый cache делает штатный запуск удобным, но для такой проверки нужен и непрогретый путь. Свидетельство P1 - сопоставление запущенного набора с испытанным, а не только вывод версии CLI на ноутбуке оператора.

### P2. Работает выбранная комбинация компонентов

Пройдите полезный lifecycle: create, setup, нужный model request, MCP read, suspend/resume и завершение test command. Для каждого используемого sandbox class проверьте итоговый application artifact. Зафиксируйте API/protocol revisions и optional features обеих сторон. Так выявляется ситуация, когда отдельно работоспособные компоненты расходятся в ожиданиях на общей границе.

Профиль AX `ac233282` использует direct reconciliation; его readiness runner относится к подготовке Workspace. Контракты разобраны в приложении A и главе 18. Test plan должен наблюдать используемый путь server/Substrate, а результат пользовательской работы - через прикладную проверку. Историческая controller queue относится к другому профилю версии.

### P3. Нагрузка укладывается в измеренный запас

Испытайте штатный поток, burst и предусмотренную потерю части Workers или inference capacity. Запишите hardware, active/idle Actors, concurrency, длины контекста и состояние cache. Headroom - запас для оговорённого изменения нагрузки или отказа. Его смысл задаётся сценарием: «после потери одного Worker очередь ограничена, задачи завершаются в срок» полезнее произвольного процента свободного CPU.

Наблюдайте одновременно пользовательскую задержку, ошибки и качество результата. Ограничение admission должно останавливать рост очереди и retry traffic. Слишком маленькая нагрузка подтвердит лишь простой рабочий путь; генератор, отправляющий только короткие prompts, пропустит память и задержки длинных контекстов. Метод выбора inference profile дан в главе 41, общей capacity - в главе 28.

### P4. Отказ зависимости имеет ограниченный эффект

В согласованной lab области воспроизведите недоступность используемых DNS, registry, model/tool endpoints, Redis/PostgreSQL и object storage. Для каждого опыта задайте допустимый impact, stop condition и способ вернуть зависимость. Нужны временная шкала, ограничение ожидания и результат test Task после восстановления. Fault injection выполняется с synthetic данными и разрешёнными целями.

Включите холодные пути и restore на другом Worker. Например, cache может скрыть недоступный snapshot payload до первой relocation. Если стенд не воспроизводит существенный failure domain, сохраните этот case открытым и укажите, какая среда понадобится. Это помогает планировать следующую проверку без расширения области текущего опыта.

## B.3 Границы доступа и доверие к инструментам

### S1. Control plane доступен только нужным identities

Составьте карту endpoints: AX/Substrate API, administrative interfaces, stores и runner metadata. Для каждой границы проверьте разрешённую и запрещённую identity. Сетевая достижимость, authentication и authorization отвечают на разные вопросы; в отчёте должно быть понятно, какой механизм остановил запрос.

Проверьте также прямой путь, минующий внешний proxy. Если proxy защищает вход, а Worker может обратиться к endpoint в обход, испытан только один маршрут. Для отрицательного case нужен исправный allowed control и ожидаемый отказ на выбранной границе. Неожиданный timeout оставляет причину отказа неизвестной.

### S2. Egress ограничивает фактический путь sandbox

Опишите разрешённые destinations и проверьте выход именно из Actor workload. Пройдите allowed и denied destinations, прямой путь, альтернативный proxy, существующее соединение и resume после смены policy. Для широкого исключения укажите владельца, основание и срок. Применение NetworkPolicy к Worker Pod и прикладное право Actor на tool operation проверяются на своих границах.

У [Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/) enforcement зависит от поддерживающего network plugin; базовые правила описывают сетевое взаимодействие на уровне адресов и портов. Проверка объекта через API показывает заданную конфигурацию, а опыт с traffic - действие правил. Сетевой разбор и примеры находятся в главе 40.

### S3. Sandbox и tenant isolation соответствуют угрозе

Укажите, от какого кода, доступа к данным и перехода между tenants защищает выбранный backend. Испытайте запрет чужих objects, snapshots и credentials, а также отсутствие остаточного состояния при переиспользовании Worker. Для каждого запрещённого доступа сохраните допустимый контроль и результат независимого чтения test object.

Container, gVisor и microVM выбирают по границе доверия, совместимости и эксплуатационной цене из главы 8. Прикладной deny test проверяет конкретное свойство разграничения данных. Исследование sandbox escape требует другой методики и отдельного разрешения; объём полученного свидетельства должен соответствовать методу проверки.

### S4. Credentials ограничены и действительно отзываются

Для каждого доступа определите issuer, holder, audience, scope, срок, refresh и revoke path. Испытайте rotation и отказ старому canary credential у конечного provider. Затем повторите проверку после restore, где могла сохраниться старая копия. Такой опыт связывает новое значение в хранилище с фактической потерей прежнего права.

При использовании [Kubernetes Secret](https://kubernetes.io/docs/concepts/configuration/secret/) проверьте encryption at rest и транзитивный доступ через создание Pod. Сам Secret не включает эти гарантии автоматически. Сохраняйте идентификаторы версии credential и результаты обращения, а значения tokens - только в предназначенном для них защищённом контуре. Порядок восстановления доступа описан в главе 42.

### S5. Tools, skills и writes проходят разные проверки

Закрепите происхождение и версии MCP servers, skills и repositories. На одном test object пройдите неверные arguments, запрос без права, изменённое approval и разрешённое действие. Schema validation проверяет форму, authorization - право на цель, approval - согласие на точное действие. Изменение targets или arguments требует повторной оценки binding.

Результат denied case включает отсутствие запрещённого effect; результат разрешённого write - проверку конечного объекта. Доверие к поставщику server и право конкретного tenant выполнять операцию записывайте отдельно. Инструкции в skill или tool result должны оставаться в своей границе доверия и не расширять полномочия harness.

### S6. Debug доступ и audit имеют независимый контроль

В штатном профиле зафиксируйте допустимые debug interfaces. Временный break-glass доступ имеет владельца, цель, срок, журнал и проверяемое закрытие. После опыта убедитесь, что старый вход перестал действовать. Удобство отладки нужно оценить вместе с тем, какие данные и действия открывает этот путь.

Workload может отправлять собственные logs, но история выдачи прав, решений о допуске и tool outcomes должна защищаться независимо от него. Проверьте permissions, retention и доступ расследователя. Для сбоя доставки audit задайте явную политику high-risk действий: какие операции блокируются и как затем восстанавливается история. Единственный receipt важного write требует более надёжного хранения, чем необязательная диагностическая строка.

## B.4 Harness и контракт полезной работы

Harness организует agent loop, хранит progress и определяет завершение задачи; его модель разобрана в главе 4. Эти критерии проверяют именно прикладную управляющую оболочку и adapters. AX/Substrate предоставляют lifecycle исполнения, а смысл правильного отчёта, допустимого действия и штатного ожидания задаёт приложение.

### H1. Бюджеты ограничивают всю работу

Определите limits для steps, model tokens, tool attempts, wall time, стоимости и числа/depth child tasks. Превысьте существенные лимиты и отмените parent. Проверьте прекращение выдачи новой работы и новых попыток, передачу отмены descendants и их наблюдаемый исход. Для предусмотренного ожидания задайте конечный срок. Суммарный учёт охватывает retries и делегирование; outcome уже отправленного write устанавливается по H4.

Ожидание approval выделите явно: что показывается пользователю, какие ресурсы удерживаются и когда задача закрывается без ответа. Проверяйте срабатывание бюджета в исполнении, включая границы между шагами. Строка ограничения в prompt может помогать поведению модели; принудительный предел реализуется и наблюдается отдельно.

### H2. Запуск и завершение имеют прикладной результат

После setup проверьте входы, доступность необходимых tools и действительность credentials. Прогоните корректную задачу, ошибку child command, exit 0 без требуемого artifact и штатное ожидание approval. У каждого случая свой ожидаемый outcome. Oracle проверяет содержание результата, а UI и monitoring должны различать эти состояния.

У [default runner AX этого среза](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/runner/runner.go) процесс остаётся доступным после завершения command. Это удобно для inspection, а готовность Workspace проверяется своим контрактом. В B.8 запустим локальный пример, где probes отвечают 200 при отсутствии отчёта, и разберём решение приёмки.

### H3. Ошибки tools имеют ограниченную стратегию обработки

Испытайте malformed input/result, schema mismatch, authorization deny, rate limit и transport timeout. Adapter должен сохранить различимую причину, а harness - выбрать предусмотренное действие: исправление входа, разрешённый refresh, ожидание или остановку. Для каждого разрешённого retry нужны общий бюджет и предел времени.

Проверьте историю попыток. Новый tool, identity или approval не должны становиться способом обойти прежний deny. Backoff регулирует частоту повторов; конечность работы задаёт бюджет всей операции. Для timeout write сначала устанавливается внешний outcome по H4.

### H4. Неизвестный outcome удерживает write gate закрытым

В simulator или разрешённом lab target подтвердите effect, затем потеряйте receipt на пути к исполнителю. Восстановите outcome по stable operation ID и прежнему idempotency key. Независимое состояние target должно показать один logical effect. Повторите case с недоступным lookup: операция остаётся `OUTCOME_UNKNOWN`, write gate - закрытым.

Отдельно выясните scope и retention deduplication provider. Запись ключа в локальном ledger не добавляет атомарность удалённому устройству. Если provider не позволяет надёжно выяснить результат и безопасно повторить запрос, ограничьте автоматический replay и предусмотрите ручное разбирательство. Для некоторых targets придётся выбрать другой adapter или более узкий контракт действия. Механизмы и выполняемый пример находятся в главе 37.

### H5. Durable progress достаточен для продолжения

Восстановите harness после потери процесса и из более раннего checkpoint. Проверьте шаг, schema/version state, pending operations и действующие права. Опишите, какие данные являются durable, откуда они читаются и какие части приложения создаются заново. Ожидание незавершённого approval тоже должно иметь однозначное продолжение.

Затем выполните фиксированный eval набор для выбранной задачи: correctness, safety и допустимые изменения качества после restore или смены model/tools. Для свободного ответа модели критерий задают содержанием и допустимыми действиями. Буквальное совпадение tokens подходит детерминированному fixture, но обычно сужает проверку реального агента не тем способом.

## B.5 Восстановление данных и внешней истории

### R1. Backup возвращает согласованный набор зависимостей

Составьте inventory реально используемых resource records, Actor/Tag metadata, Workspace payload, snapshots, keys, policy и operation ledger. Для каждой зависимости задайте retention и способ проверить целостность и references. Учтите borrowed и golden dependencies главы 39: новый Actor record может продолжать ссылаться на общий исходный payload.

Согласованный recovery point означает, что нужные части набора пригодны для совместного восстановления. Известный hash файла помогает проверить bytes, но соответствие metadata этому payload проверяется отдельно. Сохраните manifest набора и защищённые references на необходимые key versions. Результатом R1 должен стать читаемый набор для следующего restore drill, а не только запись об успешном backup job.

### R2. Restore из чистой среды укладывается в цели

**RPO** - допустимое окно потери данных перед отказом. **RTO** - предельно допустимое время от нарушения сервиса до оговорённого восстановления. Сначала согласуйте цели, класс отказа и границы измерения, затем сравните с ними фактическую потерю состояния и время возвращения полезной работы. Такой порядок соответствует определению recovery objectives в [AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_planning_for_recovery_objective_defined_recovery.html).

Другой оператор начинает из подготовленной чистой среды без локального cache автора runbook. Он получает artifacts и ключи, восстанавливает stores/payloads, проходит gates и получает проверенный application result. В RTO входят обнаружение и реакция в пределах выбранного контракта, а не только время работы restore command. Для RPO важен последний восстановимый согласованный progress приложения. Свежая запись database и старый application checkpoint могут давать разные границы потери.

Пример расчёта приведён в B.8. Отдельно испытайте получение backup и runbook при недоступности основной площадки. Если нужный ключ или payload остался только там, опыт должен выявить эту зависимость до аварии. Повторный drill требуется после существенного изменения формата состояния, runtime или recovery procedure.

### R3. Восстановление сохраняет текущие права и единственного writer

Пройдите порядок главы 42: fencing старых writers, изолированный restore, проверка mappings и прав, reconciliation внешних операций, ограниченный допуск. Fencing означает действительное лишение прежнего исполнителя возможности писать. Проверьте это запросом от старой identity после выдачи права новому исполнителю; смена DNS сама такого запрета не устанавливает.

Испытайте restore до receipt, сохранённый stale credential и недоступный dependency. Full snapshot может вернуть прежнее execution state, но действующие права задаются сегодняшней policy. Data snapshot использует свой boot path и не содержит индивидуальную RAM. H4 проверяет семантику одной операции, R3 - её сохранность через восстановление системы. Общий опыт может дать свидетельства обоим пунктам, если отчёт явно показывает каждое нужное свойство.

## B.6 Наблюдаемость и готовность дежурного

### O1. Историю можно собрать по logical run

Свяжите user/job, Task incarnation, Actor UID, Worker assignments, model requests и logical tool operations. Возьмите один run с relocation и найдите события до и после переноса в центральном backend. Запишите возраст наблюдений и контекст попыток, чтобы случайно не присоединить старый log к новому исполнителю.

В [Substrate v0.3.0 observability](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/docs/observability.md) attribution помогает находить workload; полнота доставки и прикладной trace context зависят также от вашей интеграции. Logs, traces и ledger выполняют разные задачи. Sampling diagnostic spans допустим по выбранной политике, а единственный receipt важного write должен пережить отсутствие такого span.

### O2. Измеряются результат пользователя и причины задержки

Выберите SLI - измерение полезной работы, и SLO - согласованную цель для него. Например, SLI может учитывать долю корректно завершённых задач до срока. Зафиксируйте знаменатель: какие задачи включены, как учитываются ошибки, отмена и штатное ожидание approval. Плохие результаты нельзя незаметно исключать из популяции, которую сервис обещает обслуживать.

Для диагностики добавьте model queue, TTFT, ITL, KV pressure, setup/resume time и storage/tool latency. Эти сигналы помогают объяснить нарушение SLO, но смысл пользовательского успеха остаётся прикладным. Пороги и владельцев действий согласуйте вместе с командой продукта и эксплуатации; процесс обсуждения описан в [SRE Workbook об SLO](https://sre.google/workbook/implementing-slos/). Зафиксируйте blind spots и альтернативные probes, включая store без подходящей metric.

### O3. Alert приводит к проверяемому действию

На разрешённом synthetic сбое проверьте всю цепочку: detection, notification, обращение дежурного к runbook и восстановление полезного результата. Сохраните timestamps, escalation и предел времени реакции. Контрольное событие должно пройти тот же маршрут доставки, на который рассчитывает дежурство.

Иногда агент продолжает потреблять ресурсы и отвечает на probes, но уже не создаёт нужный artifact. Такой сбой должен быть заметен через пользовательский сигнал или progress contract. Для самого monitoring path назначьте владельца и контроль доставки: оператору нужен способ отличить спокойную систему от потерянного канала наблюдения.

### O4. Операторы получают нужные данные без раскрытия secrets

Пусть другой инженер по run ID найдёт logs, receipt и версию runbook, имея обычные права дежурного. Повторите доступ к инструкции и важным свидетельствам при отказе основной площадки. Проверьте redaction так, чтобы сохранялись IDs, timestamps и причины ошибки, необходимые для диагностики.

Retention должен покрывать расследование, recovery window и обязательства выбранной системы. RAM snapshot, environment и authorization headers могут содержать credentials; их нельзя автоматически прикладывать к общему ticket. Защищённые ссылки и отдельные уровни доступа позволяют сохранить полезное evidence для расследования без лишнего распространения значений.

## B.7 Решение о выпуске и повторная проверка

### G1. Отчёт закрывает обязательные критерии текущего этапа

Review проверяет полноту cases, их привязку к candidate и применимость условий. Заранее разделите этапы: до canary нужны проверенный lab path, границы доступа, способ остановки и план наблюдения; перед расширением нужны ещё и результаты самой canary. План G2 можно принять до опыта, а фактическое поведение candidate в canary оценивается после него. В карточке отмечайте этап и обязательные для него subcases. Полный G2 остаётся открытым, пока необходимые наблюдения не получены.

Такое разделение устраняет замкнутый круг «для начала canary нужны её завершённые результаты». Допуск к ограниченному опыту разрешает только согласованную группу и операции. Он не даёт автоматического права расширить traffic или включить write path. В выпускном отчёте сохраните оба решения и основания перехода между ними.

Для обязательного case текущего этапа нужен `PASS`. Отсутствие, `FAIL`, `BLOCKED` и `SKIPPED` оставляют решение на `HOLD`. Отдельно можно принять документированный остаточный риск там, где правила выпуска это допускают: с владельцем, компенсирующей мерой, сроком и пределом rollout. Исходный результат сохраняется. Жёсткий запрет текущего профиля нельзя отменить такой заметкой; если профиль меняется, это новое решение с пересмотром затронутых проверок.

### G2. Canary даёт относящиеся к работе сервиса наблюдения

Выделите ограниченную candidate группу и сопоставимый control. Наблюдайте одинаковые классы задач и абсолютные SLO: обе группы могут оказаться одинаково плохими. Для долгих agent runs окно должно охватывать полезную работу и существенные переходы - например, ожидание approval, resume и завершение. Пара быстрых reads мало говорит о поведении того же candidate на длинной задаче.

До старта задайте объём воздействия, stop conditions, владельца решения и способ остановить выдачу новой работы. Учитывайте shared stores, tool accounts и другие общие failure domains: canary способна повлиять на control через них. Эти ограничения сравнения разобраны в [SRE Workbook о canary](https://sre.google/workbook/canarying-releases/).

Shadow evaluation подходит для read-only fixtures или simulator. Реальный write, отправленный обеим версиям ради сравнения, меняет сам опыт и может удвоить effect. Для mutation path выделите единственного владельца разрешённого изменения и отдельный план проверки его результата. Если задач нужного класса ещё не было, продлите опыт или оставьте соответствующий case открытым.

### G3. Обратный путь и эксплуатационная передача выполнимы

До rollout испытайте чтение state старой сборкой после работы candidate, обратную migration и восстановление приложения. Возврат binary имеет смысл только вместе с совместимыми данными и текущими правами. Если обратная migration невозможна, заранее подготовьте и испытайте forward recovery - исправление состояния новой совместимой сборкой с ограничением ущерба.

Назначьте владельца stop/rollback решения и проведите handoff дежурному: inventory, runbook, доступ, alerts и открытые риски. Внешний effect разбирается отдельно от версии процесса. Rollback агента не отменяет уже отправленное изменение router; для него нужен проверяемый compensating action либо другая согласованная процедура. Дежурный должен понимать, какие действия разрешены в каждом состоянии.

## B.8 Сквозной разбор решения о допуске

### Сначала получить наблюдения в безопасном упражнении

Для самостоятельной работы используйте существующие примеры глав 43 и 37. Запускайте из корня репозитория в POSIX-среде с Python 3.13 - окружением проверки этой редакции. Первый пример создаёт собственные дочерние процессы, временные файлы и HTTP probes на `127.0.0.1`; второй использует две временные SQLite databases. Credentials, cluster API, модель и внешние сетевые устройства не нужны.

```
python3 examples/ch43_release_acceptance.py
python3 examples/ch37_operation_ledger.py
```

В JSON первого примера найдите следующие поля. Это сокращённый фрагмент вывода; полная программа показывает также отрицательные cases проверки отчётов:

```
{
  "incident": {
    "health": 200,
    "ready": 200,
    "child_exit": 0,
    "result_present": false,
    "probe_only": "PASS",
    "application_case": "FAIL"
  },
  "gates": {
    "exit_zero_no_result": "HOLD",
    "valid_result": "LOCAL_CONTRACT_PASS"
  },
  "production_ready": false
}
```

В первом сценарии command завершилась с exit 0, но требуемого отчёта нет. Прикладной case получает `FAIL`, gate - `HOLD`. Затем тот же suite проверяет корректный локальный fixture и выдаёт `LOCAL_CONTRACT_PASS`. Этот результат закрывает ровно два обязательных cases suite главы 43. Для полного H2 сервиса ещё понадобятся реальные входы, tools, approval path и проверка пользовательского outcome в выбранной установке.

Во втором примере проследите потерю ответа после commit и восстановление результата. В сокращённом фрагменте вывода:

```
{
  "after_lost_reply": "OUTCOME_UNKNOWN",
  "after_recovery": "APPLIED",
  "dispatch_attempts": 1,
  "effects_before_lookup": 1,
  "effects_after_lookup": 1,
  "goal_verification": "NOT_EVALUATED",
  "network_calls": 0
}
```

Новое состояние executor прочитано из файлов, а target lookup установил outcome без второй отправки. Write approval к этому моменту истекло, но lookup в доверенном fixture остаётся разрешённым: выяснение результата и новая запись имеют разные права. Это полезный локальный case для H4. В учебном Target конфигурация и idempotency receipt сохраняются одной SQLite transaction, а receipts не истекают. Реальный provider может иметь другие атомарность, scope и retention; эти свойства надо установить и испытать отдельно. Поле `NOT_EVALUATED` напоминает о следующем вопросе: применённая конфигурация ещё требует проверки инженерной цели.

### Превратить материалы в карточку review

Пусть команда принесла только эти два локальных результата на проверку готовности сетевого сервиса. Тогда запись review может выглядеть так. `network-agent-review` - условное имя учебного профиля, а не идентификатор испытанного AX deployment. Формат карточки также учебный:

```
profile: network-agent-review
phase: pre_canary
evidence_scope: local_fixtures_only
local_cases:
  H2_result_oracle: PASS
  H4_receipt_recovery: PASS
deployment_criteria:
  P1: BLOCKED
  H2: BLOCKED
  H4: BLOCKED
  R2: SKIPPED
  G2_plan: SKIPPED
next_action: collect_inventory_and_run_integration_cases
decision: HOLD
```

Карточка сокращена до обсуждаемых пунктов; рабочий реестр должен сохранять все 25 ID и относящиеся к этапу cases. У P1 отсутствует inventory deployment, H2/H4 требуют интеграционной проверки, R2 и план G2 пока не выполнялись. Зелёные локальные cases позволяют принять их код как учебную опору и подготовить соответствующие integration tests. Для canary этих материалов недостаточно.

Теперь рассмотрим **отдельные заданные условия упражнения по R2**, не результаты исполнения команд выше. Цель RPO равна 5 минутам, RTO - 30 минутам. Нарушение полезной работы начинается в 12:00. Последний проверенный согласованный progress, доступный после restore, относится к 11:43. Восстановленный сервис получает правильный контрольный отчёт в 12:23.

| Измерение по заданным условиям | Расчёт | Решение по case |
| --- | --- | --- |
| Окно потери состояния | 12:00 - 11:43 = 17 минут при цели 5 минут | Условие по потере данных нарушено |
| Время полезного восстановления | 12:23 - 12:00 = 23 минуты при цели 30 минут | Условие по времени выполнено |
| Итог R2 для этого опыта | Должны выполняться оба обязательных условия | `FAIL`; решение остаётся `HOLD` |

Быстрое восстановление не компенсирует потерю большего объёма progress. Команда выясняет, почему пригодный checkpoint оказался старым, исправляет backup/replay contract и повторяет drill. Если опыт вообще не удалось начать, поскольку оператору не предоставили обязательный lab key, это `BLOCKED`. Если проверяемый recovery contract обещал получение ключа при отказе площадки, а этот механизм сломался, это уже `FAIL`. Причину и границу проверяемого свойства нужно записать, чтобы недостатки системы не скрывались среди проблем подготовки опыта.

### Решить что делать после исправления

После исправления повторите затронутые cases на согласованном candidate и обновите запись, сохранив историю предыдущей оценки. Если все обязательные условия этапа `pre_canary` закрыты, ответственный может разрешить ограниченную canary в заданных пределах. Затем её наблюдения закрывают оставшиеся обязательные cases G2, и отдельное решение определяет расширение нагрузки.

Переход к read-only работе потребует нового явно ограниченного профиля: write capability отсутствует или надёжно запрещена, UI и tools соответствуют этому контракту. Проверки чтения, изоляции данных, восстановления и дежурства сохраняются по своей применимости. Так команда может выпустить полезную ограниченную функцию, не маскируя открытые вопросы mutation path.

## B.9 Практикум проверки собственной готовности

Начните с одного workflow и заполните реестр всех 25 критериев. Для каждого укажите применимость, этап, cases и владельца. Возьмите только разрешённый lab tenant, synthetic данные и targets с ограниченным воздействием. Recovery и fault injection выполняются в отдельно согласованной области; запуск локальных примеров выше её не создаёт.

1. Определите правильный пользовательский результат, нагрузку и разрешённые действия. Разделите решение до canary и решение о расширении.
2. Сопоставьте сборки и policy с inventory. Для открытых prerequisites запишите конкретного владельца и следующий шаг.
3. Пройдите полезный путь и различающие отрицательные cases. Сохраните прикладной oracle, allowed control, logs и состояние конечной цели.
4. Проведите разрешённый restore drill и учебное дежурство. Убедитесь, что другой инженер может восстановить полезный результат по инструкции.
5. Намеренно удалите одну копию обязательного report из пакета review, не меняя саму систему. Проверяющий должен заметить пробел и оставить решение на `HOLD`. Верните report и проверьте его привязку к candidate.
6. Передайте материалы коллеге без устных подсказок. Он должен объяснить решение, его пределы, stop conditions и оставшиеся вопросы.

Хороший итог review - команда понимает, какую работу можно доверить системе сейчас и как поддерживать её в этих границах. Открытый case становится конкретной инженерной задачей с владельцем. Приложение C поможет найти первичные источники для следующей проверки; результаты остаются привязаны к испытанной системе и выбранному профилю.
