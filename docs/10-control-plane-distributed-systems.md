# Control plane и distributed systems: как проектировать операции, которые переживают сбои

В главе 9 мы научились различать размещение Pod, готовность процесса и результат теста. Продолжим тот же пример: нужно проверить `total(items)` тестом `test_empty_list` на условной ревизии `demo-fixture-v1`. Запрос на создание задания отправлен. Ответ не пришёл. Что делать дальше: повторить запрос, проверить существующее задание или объявить ошибку?

Если сервис успел создать задание, повтор может запустить второй тест. Если не успел, отказ от повтора оставит работу невыполненной. Таймаут не сообщает, какой из этих случаев произошёл. Это не редкая особенность плохой сети: процесс может остановиться сразу после действия, клиент может закрыть соединение, а балансировщик - потерять ответ вполне исправного сервера.

Управляющая система должна продолжать работу и в такой ситуации. **Control plane, или управляющий контур, хранит намерение, наблюдает исполнение и решает, какой следующий шаг допустим.** Его задача - не выполнить длинную функцию без единой ошибки, а сохранить достаточно сведений, чтобы после ошибки не действовать наугад.

Здесь мы проектируем учебный сервис вокруг тестового задания, не расширяем API AX. Журнал операций, outbox, собственная версия записи и описанные ниже гарантии вымышленного исполнителя - части этого проекта. В AX `ac233282` нет показанного API operation ledger и Kubernetes-полей `metadata.generation`, `resourceVersion`, `observedGeneration`; его сервер вызывает reconciliation напрямую, а watch использует Redis Pub/Sub. Substrate `ccecc788` имеет собственные `uid/version`, но это не обещание дедупликации произвольного запроса по нашему operation ID. Фактические границы разберём отдельно ближе к концу главы.

## Что читатель сможет сделать после главы

- Объяснить, почему потерянный ответ не равен невыполненному действию.
- Разделить намерение, запись операции, наблюдение и пользовательский результат.
- Спроектировать повтор с устойчивым ключом и проверить границу его действия.
- Сохранить обязанность выполнить работу независимо от сообщения в очереди.
- Выбрать транзакцию, условное обновление, lease или fencing для конкретного конфликта.
- Ограничить повторы по времени и нагрузке, не скрывая неопределённый результат.
- Составить протокол восстановления и испытать его на точках разрыва.

## Где заканчивается управление и начинается исполнение

Control plane решает, что должно существовать и в каком состоянии. Исполнитель создаёт окружение, запускает процесс и производит результат. Часто говорят о control plane и data plane: например, первый публикует маршрут, а второй передаёт по нему трафик. Это роли в архитектуре, а не обязательные имена двух сервисов.

В нашем примере API принимает просьбу проверить конкретную ревизию, журнал сохраняет эту просьбу, reconciler добивается появления задания у исполнителя. Сам тест относится к исполнению. Оценка «исправление действительно устраняет ошибку» принадлежит приложению и harness. Даже идеально восстановленный управляющий контур не может вывести этот вывод из существования задания.

Простой request handler тоже может быть частью control plane. Длинный асинхронный механизм не нужен для каждой операции. Если обновление полностью укладывается в одну короткую транзакцию и не вызывает внешних действий, достаточно понятного API и ограничений базы. Отдельный reconciler становится полезен, когда исполнение длится дольше запроса, зависит от других систем или требует продолжения после перезапуска.

### Почему длинная функция плохо восстанавливается

Представьте функцию: записать просьбу, создать задание, дождаться теста, сохранить отчёт, отправить уведомление. После падения на третьем шаге новый процесс не знает, был ли выполнен второй. Перезапуск функции с начала не является восстановлением: он может создать ещё одно задание и ещё одно уведомление.

Нужна не копия стека вызовов, а устойчивый контракт каждого шага. Что он должен изменить? По какой identity найти результат? Какие сведения сохраняются до действия и какие после? Когда повтор безопасен? Ответы позволяют продолжить с нужного места, даже если исходный процесс никогда не вернётся. В главе 5 это было важно для продолжения harness; здесь тот же принцип распространяется на API, очередь и несколько управляющих исполнителей.

## Что хранить как намерение и что считать доказательством

Desired state - состояние, которого хочет владелец ресурса. Например, «сессия должна быть активна». Команда просит совершить действие: «возобновить сессию». Событие сообщает факт: «исполнитель подтвердил создание задания». Наблюдение описывает то, что мы прочитали в определённый момент. Эти сущности связаны, но не заменяют друг друга.

Для конечного теста удобно хранить запись операции с неизменяемыми входами: ревизия, имя теста и идентификатор задания. Для долгоживущей сессии удобнее хранить желаемое состояние и отдельно операции перехода к нему. Не стоит превращать любой конечный запрос в вечный spec, равно как не стоит управлять долгоживущим ресурсом только цепочкой одноразовых команд.

| Сведение | На какой вопрос отвечает | Чего из него нельзя заключить |
| --- | --- | --- |
| Запрос принят и сохранён | Система помнит обязанность выполнить работу | Исполнитель уже запущен |
| Задание найдено у исполнителя | Внешний объект существует с нужными входами | Тест начался или прошёл |
| Процесс готов | Он способен обслуживать свой контракт сейчас | Конечная операция завершена |
| Есть отчёт теста | Получен результат конкретной попытки и ревизии | Исправление принято инженером |
| Запрос завершён ошибкой | Вызывающая сторона не получила обычный успех | Внешний эффект отсутствует |

В учебном API можно ответить `202 Accepted`, когда операция и обязанность её обработать сохранены. Клиент получает operation ID и адрес чтения состояния. Это контракт нашего API, не формат ответа текущего AX. Если процесс погибнет до ответа, клиент повторяет ту же просьбу с тем же ключом и получает прежнюю запись.

**Unknown - характеристика наших знаний.** Внешний объект может существовать, хотя состояние операции у нас unknown. Исполнение может завершиться неуспешно, а cleanup остаться неподтверждённым. Поэтому в серьёзной системе полезно раздельно хранить ход работы, наблюдение внешнего эффекта и обязанность cleanup, а не помещать всё в одну колонку `phase`. Учебный пример использует четыре состояния, чтобы показать одну узкую границу.

### Какие идентификаторы переживают повтор

Ключ идемпотентности выбирает клиент для одного намеренного действия. Operation ID адресует запись этого действия в нашей системе. External ID адресует объект у исполнителя. Message ID адресует доставку сообщения в брокере. Trace ID связывает диагностические события. Совпадение их строк случайно; назначение у них разное.

Для `job-42` клиент сохраняет ключ `review-42:test-empty-list` до первой попытки отправки. Сервер связывает его с tenant и точными входами. При потере ответа ключ не меняется. Изменение ревизии или намеренный второй запуск требует нового ключа. Если после таймаута создавать случайный ключ заново, сервер не сможет отличить повтор от нового задания.

Входы лучше хранить в нормализованном представлении и проверять при повторе. Тот же tenant и ключ с тем же содержимым возвращают существующую операцию; с другим содержимым - конфликт. Fingerprint, то есть отпечаток запроса, позволяет быстро сравнивать входы, но не отменяет определения, какие поля значимы. Поле времени отправки не должно случайно превращать повтор в другой запрос; ревизия и целевой тест, напротив, должны участвовать в сравнении.

Уникальность обеспечивает хранилище. Проверка «сначала поискать, затем вставить» оставляет промежуток, в который второй клиент тоже увидит отсутствие записи. Unique constraint на `(tenant, key)` закрывает эту гонку внутри базы. Проверка конфликта по содержимому всё равно остаётся обязанностью приложения. PostgreSQL предоставляет `ON CONFLICT` для работы с такими ограничениями; это не дедупликация внешнего API. [PostgreSQL INSERT](https://www.postgresql.org/docs/18/sql-insert.html).

Запись ключа нельзя удалять раньше максимального срока повтора. В него входят очередь, offline-клиенты, ручной replay и восстановление из backup. Если запись уже удалена, наш контракт повторяемости прекращает действовать. Нужны явные retention и tombstone, то есть сохраняемая отметка использованной identity, либо запрет повторного использования старых ключей после определённого срока.

## Reconciliation как восстановимый протокол

Reconciliation означает повторное согласование желаемого и наблюдаемого состояния. Каждый проход читает актуальную запись, собирает нужное свидетельство и выполняет допустимый шаг. Он может быть вызван сообщением, таймером или периодической сверкой. Источники запуска не должны определять истину о ресурсе. Это общий принцип; устройство Kubernetes controllers разобрано в главе 9. [Kubernetes Controllers](https://kubernetes.io/docs/concepts/architecture/controller/).

В нашем сервисе reconciler сначала читает операцию. Если создание внешнего задания уже подтверждено, повторная доставка ничего не создаёт. Если состояние незавершённое, он ищет задание по устойчивому ключу, сверяет входы и сохраняет внешний ID. Если поиск достоверно показывает отсутствие, допустимо вызвать создание с тем же ключом при условии, что исполнитель атомарно дедуплицирует такие вызовы.

Здесь важны обе оговорки. Поиск в запаздывающем индексе может не увидеть только что созданный объект. А атомарность означает, что два одновременных вызова с одним ключом не создадут два объекта. Тег на объекте и предварительный поиск сами по себе этой гарантии не дают. Для реального API нужно проверить семантику ключа, область tenant, окно хранения и поведение при конкурентных вызовах.

### Какие свойства мы хотим сохранить

Инвариант - условие, которое должно оставаться истинным при всех допустимых переходах. Для примера выберем четыре:

1. Один tenant и ключ соответствуют одной записи с неизменяемыми входами.
2. Принятая операция не исчезает только из-за потери сообщения.
3. Одному operation ID соответствует не более одного внешнего задания при установленном контракте исполнителя.
4. Подтверждение создания задания не выдаётся за результат теста или завершение ревью.

Первые два свойства находятся в границе нашего хранилища. Третье требует участия исполнителя. Четвёртое принадлежит прикладной семантике. Так проще увидеть, где локальная транзакция достаточна, а где нужно договориться с другой системой.

Корректность и продвижение тоже различаются. Система может не создавать дублей и при этом вечно оставаться unknown. Для продвижения нужны доступная сверка, повторный запуск reconciler, ограничение перегрузки и маршрут к оператору. «Не испортить состояние» и «в конечном итоге закончить работу» - два отдельных требования.

## Журнал операций и outbox

Журнал операций, или operation ledger, хранит принятую просьбу и подтверждения её исполнения. Это не обычный лог: от него зависит решение, можно ли создать внешний объект. Сэмплированный trace и строка в журнале контейнера для этой роли не подходят. Они могут исчезнуть раньше, чем понадобится восстановление.

Outbox - таблица обязательств отправить сообщения. При принятии просьбы сервер одной транзакцией создаёт операцию и запись outbox. Если транзакция откатывается, нет ни операции, ни обещания публикации. Если commit прошёл, обязанность отправки переживает падение процесса. Само отправленное сообщение не входит в эту транзакцию: брокер - другая система.

Publisher читает неотправленные записи, отправляет operation ID, затем ставит отметку публикации. Между отправкой и отметкой снова есть точка разрыва. После падения сообщение будет отправлено повторно. Это нормальное свойство протокола, а не скрытый дефект, который можно устранить перестановкой строк.

Если отметить запись **до** отправки, появится другой дефект: падение между отметкой и отправкой потеряет работу. Поэтому мы выбираем возможный повтор и проектируем consumer так, чтобы повтор не умножал эффект. Outbox устраняет потерю обязанности на локальной границе, но не даёт «ровно одну доставку».

### Сверка незавершённых операций

Даже успешная отправка не равна вечному хранению сообщения. Очередь может потерять данные при неправильно выбранной persistence, а оператор - удалить записи слишком рано. Периодическая сверка читает незавершённые операции из журнала и снова запускает согласование. Ей не обязательно повторно публиковать весь backlog: можно вызывать обработку небольшими порциями с rate limit.

Цена этого механизма - нагрузка на хранилище и время обнаружения. Нужны индекс, выборка по времени следующей проверки, ограничение размера batch и защита от того, чтобы все replicas сканировали одно и то же каждую секунду. Сверка не должна объявлять незавершённую работу ошибкой только из-за возраста; возраст помогает приоритизировать расследование.

Отметка outbox `published` означает именно публикацию, не обработку и не завершение операции. Retention outbox, дедупликации и журнала проектируется совместно с восстановлением из backup. Восстановленная старая копия базы может забыть подтверждение уже выполненного внешнего действия. Даже после успешного restore сначала нужна сверка, а не массовый новый запуск.

## Практический пример с двумя независимыми хранилищами

Программа `examples/ch10_control_plane_demo.py` использует Python 3.10+ и стандартную библиотеку. Первая SQLite-база хранит операции и outbox. Вторая изображает сервис заданий. Они открыты отдельными соединениями и фиксируются независимо: общей транзакции между ними нет. Список в памяти изображает доставку сообщений; это не реализация Redis Streams.

SQLite выбрана, чтобы пример запускался без инфраструктуры. Внутри одной базы transaction позволяет проверить совместное сохранение операции и outbox. Это не измерение PostgreSQL, репликации, fsync-политики или устойчивости диска. Вставка при конфликте не должна заменять прежнюю запись: `REPLACE` в SQLite удаляет конфликтующую строку, что разрушило бы нужную нам историю. [SQLite ON CONFLICT](https://www.sqlite.org/lang_conflict.html), [Atomic Commit](https://www.sqlite.org/atomiccommit.html).

### Что обещает учебный исполнитель

Класс `Provider` задаёт намеренно сильный учебный контракт: поиск по operation ID достоверен, а создание атомарно связывает этот ключ с входами и единственным job ID. Повтор с другими входами отклоняется. При включённой потере ответа исполнитель сначала фиксирует объект в своей базе, затем выбрасывает `TimeoutError`.

Это не клиент Kubernetes и не адаптер Substrate. Настоящие APIs могут иметь другой контракт. Если у них нет дедупликации или достоверной сверки, нельзя получить наши гарантии простым копированием reconciler. Нужно использовать поддерживаемую стабильную identity, договориться о протоколе с исполнителем или оставить неизвестный результат на ручное разбирательство.

`confirmed` в программе означает только «создание задания подтверждено». Программа не запускает `test_empty_list`, не проверяет `total(items)` и не принимает исправление. Название состояния специально не заменено на `completed`: завершение шага создания и завершение прикладной работы различаются.

### От принятия к восстановлению

| Точка разрыва | Что уже сохранено | Что делает следующий проход |
| --- | --- | --- |
| До commit операции и outbox | Ни одной принятой записи | Клиент повторяет тот же запрос |
| После commit до отправки | Операция и обязанность публикации | Publisher или сверка найдёт работу |
| После отправки до отметки | Операция, outbox и возможная доставка | Publisher отправит повторно |
| После внешнего commit до ответа | Внешнее задание, локально unknown | Поиск подтвердит прежнее задание |
| После внешнего commit до локального status | Внешнее задание, локально dispatching | Поиск и запись подтверждения |
| Сверка исполнителя недоступна | Незавершённая операция | Сохранить unknown и назначить проверку |

Основная функция из программы:

```
def reconcile(local, provider, op_id, crash_after_effect=False):
    row = read(local, op_id)
    if row["state"] == "confirmed":
        return "confirmed"
    if row["state"] == "accepted":
        if not cas(local, row, "dispatching"):
            return "recheck"
        row = read(local, op_id)
    try:
        found = provider.lookup(op_id)
        if found is None:
            found = provider.ensure(op_id, row["payload"])
    except (TimeoutError, Unavailable):
        return "unknown" if cas(local, row, "unknown") else "recheck"
    if found["payload"] != row["payload"]:
        raise Conflict("provider evidence has different payload")
    if crash_after_effect:
        raise Crash("provider committed, journal not confirmed")
    saved = cas(local, row, "confirmed", str(found["id"]))
    return "confirmed" if saved else "recheck"
```

`cas` - compare and swap, условное обновление: запись меняется только при той версии, которую мы прочитали. Если другой проход уже изменил строку, функция возвращает `recheck`, а не затирает его результат. Эта проверка защищает локальную запись, но не мешает двум проходам обратиться к исполнителю. Единственность внешнего объекта обеспечивается отдельно его ключом.

Поиск стоит перед созданием. При недоступной сверке пример не вызывает `ensure`: он предпочитает сохранить неопределённость. При найденном объекте сравниваются входы. Это защищает от ложного подтверждения чужой работы. Если процесс прервался после внешнего commit, состояние `dispatching` не считается доказательством отсутствия задания; следующий проход снова начинает с поиска.

`Conflict` не превращается в автоматический retry. Входы и найденное свидетельство противоречат друг другу, поэтому нужно расследование. В production потребовались бы отдельные reason, quarantine, время следующей проверки и история попыток. В программе они опущены, чтобы основной протокол помещался на одной странице.

Запуск из корня репозитория книги:

```
python3 examples/ch10_control_plane_demo.py
python3 -m unittest discover -s examples -p 'test_ch10_*.py'
```

Программа сама создаёт временный каталог. Сначала сохраняется операция, publisher прерывается после отправки и затем повторяет доставку. Исполнитель фиксирует задание, но «теряет» ответ. После закрытия и повторного открытия соединений reconciler находит существующее задание. Получается такой результат:

```
{
  "source": "local_sqlite_model",
  "cluster_contacted": false,
  "operation_records": 1,
  "unfinished_after_accept": 1,
  "deliveries_for_one_outbox_row": 2,
  "after_lost_response": "unknown",
  "after_reopen": "confirmed",
  "duplicate_delivery": "confirmed",
  "provider_jobs": 1,
  "external_id": "1",
  "test_result": "not_executed",
  "review_completed": "not_established"
}
```

Прочитайте вывод как рассказ о границах: две доставки не создали два задания; потерянный ответ оставил неизвестность; новые соединения восстановили подтверждение из сохранённых данных. Но ни один из этих успехов не говорит, что тест прошёл. Отчёт теста должен иметь собственный контракт с revision, attempt и результатом, как мы обсуждали в главах 8 и 9.

### Что именно проверяют тесты

Тесты проверяют конфликт ключа и входов, совместный rollback операции и outbox, повтор после отправки, потерю сообщения, неизвестный результат после внешнего действия, восстановление с новыми соединениями, устаревшую версию и отклонение чужого результата. Два независимых соединения также одновременно принимают один ключ: в SQLite остаётся одна операция. Это локальная проверка ограничения базы, не испытание распределённого владения.

Точки «падения» реализованы исключениями после выбранных commit. Процесс не убивается, питание не отключается, настоящая сеть не рвётся. Пример не реализует lease, fencing, периодический scheduler, watchdog, удаление, business deadline, tenant authorization или хранение отчётов. Эти ограничения существенны: по результату нельзя объявить систему production-ready или перенести гарантии на любой другой provider.

## Как читать старое наблюдение и не потерять новый intent

Версия записи отвечает на вопрос «изменилось ли то, что я прочитал». Версия намерения отвечает на вопрос «какую просьбу оценивал исполнитель». Identity экземпляра отвечает на вопрос «это всё ещё тот же объект или его создали заново». Для долгоживущего ресурса нужны все три различия; один timestamp не заменяет их.

Представим условную сессию `session-42`: intent 7 просил активировать её, intent 8 просит остановить. Запоздавшее подтверждение activation 7 - полезный факт: оно объясняет, какой объект мог появиться и что надо убрать. Но оно не делает текущий intent 8 готовым. Старый результат следует сохранить в записи старой операции и при необходимости назначить cleanup, а не просто отбросить вместе с identity внешнего объекта.

В Kubernetes generation помогает связать spec с наблюдением контроллера, а UID отличает пересозданный объект. Применение конкретных полей разобрано в главе 9. В собственном API можно определить аналогичный intent version, но нужно отдельно установить правила его увеличения. Обновление статуса не обязано означать новую просьбу пользователя. Наш учебный `version` увеличивается при обновлении записи операции и является только локальным CAS-счётчиком.

Готовность желательно описывать с reason, временем наблюдения и той версией intent, к которой она относится. `Ready=True` для старого intent не подтверждает новый. При этом даже свежая версия не делает наблюдение вечным: ресурс может перестать отвечать сразу после проверки. Для критичного действия нужен свежий operational check или контракт исполнителя, а не только давно зелёный status.

Watch ускоряет получение изменений. После разрыва соединения нужна новая сверка. Периодический read не должен приписывать наблюдение с новым UID прежней попытке. Для восстановимого list/watch Kubernetes существуют свои правила cursor и восстановления; они не автоматически применяются к Pub/Sub AX или к произвольному gRPC stream. [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/).

## Когда нужен lock и когда нужен fencing

Управляющие replicas могут прочитать один status, выбрать один следующий шаг и выполнить его одновременно. Сначала определите, что нельзя делать дважды: обновление строки, выдачу владения или внешний эффект. Это разные конфликты.

Условное обновление удобно для коротких изменений. Два процесса прочитали version 4; первый обновил строку и получил version 5, второй изменил ноль строк и должен перечитать состояние. Но оба могли до этого вызвать внешний API. CAS не делает этот вызов транзакционным, как и в нашем примере.

Row lock нужен, если решение зависит от нескольких связанных строк в одной базе. Не стоит удерживать его во время медленного сетевого вызова: это расширяет область задержки и не даёт откатить уже совершённое внешнее действие. Уровень isolation тоже имеет значение: наличие слова «транзакция» не означает serializable для всех инвариантов. При serialization failure повторяют всю короткую транзакцию на свежих данных, не сетевое действие внутри неё. [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html), [Explicit Locking](https://www.postgresql.org/docs/18/explicit-locking.html).

Lease - временно выданное владение с ограниченным сроком и продлением. Оно помогает выбрать одного активного исполнителя, но не останавливает процесс физически после истечения срока. Реплика A могла замереть, lease истёк, реплика B получила новое владение, а A вернулась и продолжила работу. Проверки lease только на стороне A недостаточно.

Fencing token - упорядоченный номер владения, который проверяет сам получатель действия. Допустим, B получил token 42 и storage уже атомарно принял его для ресурса. Последующий запрос A с token 41 отклоняется. Сравнение и запись должны находиться в одной границе получателя; иначе снова появляется гонка. Token нельзя независимо увеличивать в памяти каждой replica.

У этой защиты есть важное условие: если новое владение ещё не доведено до получателя, он может не знать, что старый token устарел. Для строгого запрета после смены владельца нужен протокол публикации новой границы или проверка актуального владения при записи. Нельзя обещать, что любой lease с числовым полем уже исключил все действия старой replica.

Повтор с тем же token тоже возможен. Fencing запрещает устаревшее владение, а ключ идемпотентности связывает повтор с одним намеренным действием. Эти механизмы дополняют друг друга. Если внешнее API не принимает fencing token, локальная блокировка не придаст ему эту способность.

## Повторы должны быть безопасны и ограничены

Сначала решите, можно ли повторить действие, затем - когда. Идемпотентность означает, что повтор сохраняет тот же intended effect, а не что все ответы, audit records и длительности одинаковы. Доставка at-least-once допускает несколько обработок сообщения. «Exactly once» имеет смысл только с указанной границей состояния; гарантия брокера не охватывает произвольную отправку email или создание объекта в другой системе. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2).

Отсутствие объекта в неполном поиске не доказывает отсутствие эффекта. Если API предоставляет только «создать ещё один объект», без ключа и достоверного поиска, общий алгоритм не может одновременно гарантировать отсутствие дублей и автоматическое завершение после потерянного ответа. Выбор становится прикладным: ручная сверка, допустимый duplicate с последующим cleanup либо другой интерфейс исполнителя. Называть это просто «retryable error» опасно.

### Таймаут ожидания и срок полезности работы

RPC timeout ограничивает ожидание одного вызова. Business deadline ограничивает время, когда пользователь ещё хочет результат. Они могут отличаться: создание задания ожидается две секунды, а тест полезен ещё десять минут. Остановка ожидания не должна молча удалять принятую durable операцию, если API обещал её дальнейшее исполнение.

Для RPC по цепочке передают оставшийся бюджет, а не запускают исходный timeout заново на каждом hop. Пусть учебный общий бюджет составляет десять секунд: локальная работа заняла 1,2, первый вызов - 2, backoff - 0,8. Перед следующим вызовом осталось шесть секунд, не новые десять. Даже если локальный timeout больше, вызов нельзя растянуть за общий deadline. [gRPC Deadlines](https://grpc.io/docs/guides/deadlines/).

Cancellation означает просьбу прекратить вычисление. Она не откатывает commit внешней системы. После отмены может остаться обязанность найти задание и остановить его; остановка тоже имеет свой неизвестный результат и собственную запись. Если работа уже завершилась, операция отмены может закончиться как «слишком поздно», а не стирать полученный отчёт. [gRPC Cancellation](https://grpc.io/docs/guides/cancellation/).

`UNAVAILABLE` и `DEADLINE_EXCEEDED` описывают RPC, не историю внешнего объекта. Возможность автоматического повтора определяется методом и его контрактом. У gRPC есть различие между transparent retry до обработки сервером и настроенной политикой повтора; включённая поддержка retries сама по себе не определяет безопасную business policy. [gRPC Retry](https://grpc.io/docs/guides/retry/).

### Как не превратить сбой в лавину запросов

Backoff увеличивает паузу между попытками, jitter разносит их случайным образом. Один вариант full jitter выбирает паузу между нулём и `min(cap, base * 2**attempt)`. Но даже хорошо распределённые повторы могут перегрузить зависимость, если их слишком много. Ограничение числа попыток относится к одной операции, retry budget - ко всей нагрузке, а concurrency limit - к числу одновременно занятых слотов.

Если SDK, RPC-прокси и приложение независимо разрешают по три попытки, один запрос способен породить до 27 вызовов нижнего уровня. Нужен выбранный владелец retry и видимость суммарного числа попыток. Значения budget подбирают по нагрузочным испытаниям и требованиям сервиса, не по примеру из книги.

Circuit breaker временно прекращает новые обращения к явно деградировавшей зависимости и допускает ограниченные пробные вызовы для проверки восстановления. Он не удаляет незавершённые операции и не превращает unknown в failure. Если работа принята, её обязанность остаётся в журнале, даже когда следующий вызов отложен.

Permanent validation error не лечится задержкой; конфликт входов требует расследования; нехватка capacity может требовать ожидания или смены решения. Истёкший retry budget означает «сейчас больше не создаём нагрузку», а не «внешнее действие точно не случилось». Возраст unknown и путь к ручной сверке должны оставаться видимыми.

## Как выбирать инструменты под этот протокол

Начните с самой маленькой архитектуры, которая сохраняет нужные инварианты. Если один сервис и одна SQL-база обслуживают умеренное число коротких операций, отдельный брокер может быть не нужен. Таблица работ, условное получение batch и периодический проход способны дать понятное восстановление. Нужно измерить задержку и contention, а не выбирать очередь только потому, что слово control plane звучит распределённо.

Если нужна быстрая независимая доставка к нескольким consumers, очередь добавляет полезную границу. Если появляются многочасовые процессы, таймеры, ветвления и ручные ожидания, стоит рассмотреть workflow runtime. Он может взять на себя расписание и историю исполнения, но контракт внешних действий, retention и версионность workflow всё равно необходимо проверить.

| Потребность | Разумный кандидат | Что остаётся спроектировать |
| --- | --- | --- |
| Связанные записи и устойчивые инварианты | PostgreSQL | Isolation, constraints, backup и восстановление |
| Распределение работы и повторная доставка | Redis Streams или другой брокер | Claims, persistence, retention и идемпотентность |
| Короткие уведомления подписчикам | Redis Pub/Sub | Сверка после пропуска события |
| Typed RPC и потоки между сервисами | gRPC с Protobuf | Deadline, retry, auth и совместимость |
| Большие отчёты и snapshot bytes | Object storage | Ownership, checksum и атомарная публикация ссылки |

### PostgreSQL как граница атомарного решения

В нашем проекте SQL-база отвечает за операции и outbox. PostgreSQL уместен, когда нужны связанные обновления, ограничения уникальности и контролируемая конкуренция нескольких клиентов. Но commit этой базы не включает Redis, Kubernetes или object storage. После восстановления базы по старому backup внешние эффекты тоже не откатываются: протокол сверки остаётся нужен.

Advisory lock полезен для именованной прикладной блокировки, но требует согласованного использования всеми writers. Он не является constraint для кода, который его игнорирует. Session-level и transaction-level lock имеют разное время жизни; не следует рассчитывать, что rollback освобождает любой advisory lock. [PostgreSQL Explicit Locking](https://www.postgresql.org/docs/18/explicit-locking.html).

### Redis Streams и ответственность consumer

Consumer group распределяет stream entries между consumers. Неподтверждённые entries учитываются в Pending Entries List, PEL. `XACK` убирает подтверждение ожидания для этой группы; это не свидетельство окончания прикладной операции и не удаление внешнего объекта. Ack после durable фиксации шага допускает повтор при потере ответа, поэтому обработка должна выдерживать его. [Redis XACK](https://redis.io/docs/latest/commands/xack/).

Смерть consumer не запускает наш бизнес-протокол автоматически. Pending работу нужно обнаруживать и передавать другому consumer по выбранной политике, например через `XAUTOCLAIM`, доступный начиная с Redis 6.2. Idle time сообщения не доказывает, что прежний consumer уже остановился; claim не является fencing для его внешних вызовов. [Redis XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/).

Streams не обещает сохранность данных независимо от конфигурации. Persistence, replication, failover и trim должны соответствовать допустимой потере. Следите за возрастом pending, количеством доставок и lag, не только за длиной stream. Poison message, то есть запись, которая стабильно ломает обработку, требует ограниченного числа попыток и отдельного quarantine с причиной и прежним operation ID. Dead-letter маршрут и безопасный replay проектирует приложение.

### Pub/Sub для уведомлений и gRPC для вызовов

Pub/Sub не хранит replay-историю для отключившегося подписчика. Он подходит как подсказка «состояние изменилось», если пропущенное уведомление компенсируется чтением актуального состояния. Он не становится durable очередью оттого, что Redis уже используется как база. В документации Redis доставка Pub/Sub описана как at-most-once. [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/).

gRPC полезен, когда команда готова поддерживать типизированный контракт и нуждается в соответствующих RPC/streaming возможностях. HTTP с хорошо определёнными ключами и статусами тоже способен реализовать наш протокол. Transport выбирается по потребностям клиентов и эксплуатации, а не как источник идемпотентности.

Protobuf требует аккуратной эволюции schema: удалённые номера полей нельзя использовать для нового смысла, их резервируют. Отсутствующее значение и значение по умолчанию должны интерпретироваться согласно модели presence. При rollout старые и новые клиенты какое-то время существуют одновременно. [Protobuf Language Guide](https://protobuf.dev/programming-guides/proto3/).

Streaming не отменяет ограничений памяти. Flow control регулирует данные транспортного потока, но собственную очередь приложения нужно ограничить отдельно. Успешная запись в поток не означает, что получатель применил действие; business acknowledgement относится к другой границе. Большой отчёт лучше передавать по ссылке с identity и checksum, если контракт клиента это позволяет. [gRPC Flow Control](https://grpc.io/docs/guides/flow-control/).

## Удаление и компенсация тоже являются работой

Если удалить запись операции до освобождения внешнего ресурса, исчезнет обязанность cleanup. Полезнее сначала сохранить intent удаления, затем подтверждать освобождение зависимостей и только после этого окончательно удалять запись либо оставлять tombstone. Cleanup должен выдерживать повтор и состояние «объект уже отсутствует».

В Kubernetes finalizer задерживает окончательное удаление объекта, пока ответственная логика не снимет отметку. Он не выполняет cleanup сам и может оставить объект terminating при недоступной зависимости. Ручное снятие означает принятие риска orphaned ресурсов, а не доказанный успешный cleanup. Этот механизм не следует приписывать каждому API, который умеет delete. [Kubernetes Finalizers](https://kubernetes.io/docs/concepts/overview/working-with-objects/finalizers/).

Компенсация, или saga step, исправляет последствия отдельным действием. Отмена бронирования может компенсировать резерв, но не сделать так, будто уведомление никогда не отправлялось. Компенсация тоже может упасть или повториться. Ей нужны identity, журнал, проверка результата и правила для случая, когда действие уже невозможно отменить.

Для нашего задания разумно различать «больше не нужен новый запуск» и «существующее задание остановлено». Второе нельзя вывести из первого. Если отмена и создание пересеклись, reconciler ищет существующий job и приводит его к выбранному контракту, сохраняя историю обеих операций.

## Что фактически реализовано в AX и Substrate

В AX `ac233282` `CreateTask` сохраняет Task, затем сервер напрямую вызывает reconciler Substrate и обновляет статус. При повторном создании существующего неизменяемого Task возвращается `FailedPrecondition`, а не сохранённый результат по нашему клиентскому ключу. Это конкретное поведение, отличное от учебного API. Детальный execution path начинается в главе 16. [AX server.go](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/server/server.go).

Redis store этого среза публикует уведомления watch через `Publish` и подписывается через `Subscribe`. Комментарий о «reconcile event to the stream» в коде не заменяет чтение этих вызовов и direct path сервера. Нельзя объяснять отказ такого watch через PEL и `XAUTOCLAIM`: это механизм другого вида доставки. [AX Redis store](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/store/redis/store.go), [AX API schema](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/pkg/apis/v1alpha1/ax.proto).

В Substrate `ccecc788` metadata содержит server-managed UID и version; для `UpdateActor` они служат preconditions. `CreateActorRequest` содержит Actor, не поле нашего operation ID. В проверенном create path уже существующее имя приводит к `AlreadyExists`, а не к возврату прежнего результата по журналу операций. После неизвестного исхода устойчивое имя помогает найти объект, но необходимо сравнить identity и значимые входы; сам конфликт существования не является доказательством успеха нужного запроса. [ateapi.proto](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/pkg/proto/ateapipb/ateapi.proto), [Actor create path](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/cmd/ateapi/internal/controlapi/actor.go).

Следовательно, историю «AX повторил op-73, а Substrate вернул сохранённый результат операции» нельзя использовать как описание этого среза. Если приложению нужен такой контракт, его надо реализовать и проверить на подходящей границе. API version, server validation и storage implementation читают вместе; названия из проектного примера не являются готовыми полями manifest.

Сильная runtime isolation из главы 8 не решает проблему повторов. Правильно размещённый Worker Pod из главы 9 не подтверждает текущий Actor lifecycle. А корректный журнал создания задания не доказывает, что тест завершился. Эти слои работают совместно, но их доказательства нельзя обменивать одно на другое.

## Как расследовать незавершённую операцию

Начните с устойчивой identity и точных входов: tenant, operation ID, revision, объект и его UID, если он есть. Сопоставьте локальное состояние с внешним, не меняя ключ для удобства. Затем определите, какое свидетельство отсутствует: принятие просьбы, доставка, создание объекта, готовность или конечный результат.

Если операция accepted, а сообщения нет, проверьте outbox и механизм сверки. Если сообщение pending, узнайте, кто его получил и когда последний раз работал; claim не является доказательством остановки прежнего consumer. Если состояние unknown после создания, ищите объект по поддерживаемой identity и сверяйте входы. Если он найден, не нужно создавать второй только ради получения «чистого» ответа.

При конфликте версий перечитайте свежую запись. При результате от старого intent сохраните информацию об эффекте и выясните, нужен ли cleanup. Если сверка не даёт достоверного ответа, оставьте неизвестность видимой и выберите ручной путь. При диагностике не копируйте credentials или полные чувствительные payloads в публичные logs.

Операционные метрики должны показывать возраст незавершённых операций, время до внешнего подтверждения, долю unknown, повторные вызовы и задержку cleanup. Процесс `up` не доказывает продвижение. Operation ID хранится дольше trace; при большом числе операций его обычно оставляют в структурированных logs и журнале, а не превращают в label каждой метрики с неограниченной cardinality.

## Что испытать перед реальным внедрением

Локальные тесты проверяют небольшой контракт. Интеграционные испытания должны разрывать именно реальные границы: после commit перед отправкой, после внешнего действия перед ответом, после ответа перед локальной записью и после записи перед ack. Каждый раз проверяйте инварианты, а не только отсутствие исключения.

Отдельно нужны два одновременных consumer, пауза старого holder после истечения lease, запоздавший результат прежнего intent, пропуск watch и восстановление базы из старой копии при живом внешнем объекте. Для provider проверяют конкурентное создание с одним ключом, время жизни дедупликации и достоверность поиска. SQLite-модель не отвечает за эти свойства внешней инфраструктуры.

Проверка безопасности должна установить, кто вправе читать и повторять операцию. Знание operation ID не является разрешением. Повтор с прежним ключом должен пройти актуальную authorization, а возвращаемый сохранённый результат не должен раскрывать чужой tenant. Rate limit, quota и журнал ручных действий остаются частью эксплуатационного контракта.

## Практика для самостоятельного решения

Первое упражнение: замените учебный достоверный lookup запаздывающим индексом. Почему предварительный поиск больше не гарантирует отсутствие задания? Какие свойства `ensure` всё ещё позволяют безопасный повтор, а какие придётся проверять у реального API?

Второе: операция получила confirmed, а затем клиент прислал те же входы под новым ключом. Должно ли появиться второе задание? Ответьте из смысла ключа, а не из желания любой ценой получить один объект. Добавьте тест для своей policy.

Третье: отмена intent 8 пришла раньше ответа от activation intent 7. Что сохранить из старого результата, что нельзя записать в текущий status и где оставить обязанность cleanup? Нарисуйте или опишите два независимых перехода, не называя timeout успешной отменой.

Четвёртое: publisher пометил outbox, но брокер позже потерял сообщение. Найдите операцию без очереди и объясните, почему повторный проход не создаёт дубль. Затем удалите дедупликацию provider и покажите, какой инвариант исчез.

Пятое: A вернулся со старым fencing token после того, как B получил новый. Достаточно ли выдачи token, если storage ещё не видел B? Укажите момент, когда получатель начинает отвергать A, и как проверяется граница владения.

## Итоги главы

Управляющий контур хранит просьбу дольше одного RPC и умеет сверить исполнение после сбоя. Таймаут означает потерю подтверждения, не обязательно отсутствие действия. Ключ операции связывает повторы, журнал сохраняет обязанность, outbox связывает её с доставкой, а reconciler читает свежие сведения и выбирает допустимый шаг.

Транзакция защищает свою базу. CAS защищает условное обновление. Lease выбирает временного владельца. Fencing требует проверки у получателя. Идемпотентность внешнего действия требует соответствующего внешнего контракта. Ни один из этих механизмов не следует автоматически из выбора Redis, PostgreSQL, gRPC или Kubernetes.

Хороший протокол сохраняет и неопределённость: можно честно сказать «объект создан, но тест ещё не выполнен» или «результат создания неизвестен, нужна сверка». Это полезнее ложного failure и безопаснее слепого повторного запуска.

**Дальше.** В главе 11 соберём identity, состояние и последовательность решений вокруг Actor. Логическая сущность может жить дольше своего Worker и процесса, но Actor model не отменяет разобранные здесь повторы, внешние эффекты и обязанности восстановления.

### Источники и дальнейшее чтение

- RFC 9110, gRPC Deadlines, Cancellation, Retry и Flow Control - значение повторов, временных границ и передачи данных; ссылки приведены в соответствующих разделах.
- PostgreSQL 18 Transaction Isolation, Explicit Locking и INSERT - локальная транзакционная граница и конкурентные изменения.
- Redis Pub/Sub, XACK и XAUTOCLAIM - различия уведомлений, pending и подтверждения доставки. Конкретную версию, persistence и retention выбирают для своего развёртывания.
- SQLite ON CONFLICT и Atomic Commit - механика локального примера, не гарантия распределённой системы.
- Kubernetes Controllers, API Concepts и Finalizers - сверка состояния и двухфазное удаление в границе Kubernetes.
- Закреплённые AX `ac233282` и Substrate `ccecc788` - API и code paths, перечисленные в разделе о фактической реализации.
