# Local inference sizing: память GPU, parallelism и эксплуатационные SLO

Продолжим сценарий главы 40 и предположим, что сетевой путь уже проверен: Actor доходит до модели, TLS работает, разрешённая операция получает ответ. Теперь несколько Tasks возобновляются одновременно. Один агент передаёт длинную историю, остальные ждут короткий tool call. Сервер продолжает отвечать, но шаги агентов начинают пропускать deadline. Чтобы выбрать исправление, нужно понять, чего именно не хватает: памяти для истории, скорости вычислений или возможности обслужить пришедший поток.

**Sizing** - выбор ресурсов и ограничений сервиса под конкретную работу. На выходе нужен понятный ответ: какие запросы сервис принимает, сколько таких запросов он успевает обслужить и что сохраняется при отказе части оборудования. Глава 20 помогла выбрать runtime и проверить интерфейс модели, глава 21 - измерить полезную производительность. Здесь соберём из этих сведений план размещения и допуска нагрузки.

Начнём с обычной text-only decoder-модели с full attention. На учебном примере посчитаем память, затем разберём batching, распределение модели и резерв мощности. Расчёт можно выполнить без GPU. Измеренную скорость он не подменяет: архитектуру и лимиты берём из config и выбранного artifact, а capacity под SLO получаем испытанием сервиса.

## Сначала определите какую работу должен успеть сервис

Пятнадцать агентов не означают пятнадцать постоянно работающих генераций. Агент может ждать tool, обращаться к модели несколько раз за шаг или запускать несколько ветвей одновременно. После общего resume обращения сближаются во времени. Для сервера важны сами arrivals - моменты поступления запросов, их длины и допустимое время выполнения.

Возьмём короткий профиль из главы 20: общий context до 8192 tokens, ответ до 512 tokens. Тогда на сериализованный prompt остаётся не более 7680 tokens. В prompt входят инструкции, schemas tools, история, результаты tools и оформление chat template. Считайте длину tokenizer именно того deployment, который будет обслуживать запрос; число символов и длина исходного списка messages этого не заменяют.

Для каждого класса сохраните совместные примеры input и output, arrival rate, burst и deadline. Отдельные p95 длины prompt и ответа не показывают, встречаются ли длинные значения вместе. Кроме того, длинная генерация дольше остаётся активной. Поэтому набор запросов, одновременно удерживающих память, отличается от распределения входящих запросов.

Короткий выбор инструмента и большой анализ документа удобно принять как разные классы. Их можно направить в отдельные pools - группы replicas с общими лимитами. Это защищает интерактивную работу от длинного prefill, но добавляет отдельную очередь, routing и требование к запасу каждого pool. Для редкого длинного запроса сначала сравните такую изоляцию с ценой простоя выделенной мощности.

Сохраните смысл SLO из главы 21. В нашем коротком сценарии полезен полный допустимый tool call в пределах учебного deadline 2000 ms. Для читаемого человеком stream могут понадобиться другие цели: время до первого содержательного фрагмента и плавность продолжения. Ограничения памяти обслуживают эти обещания, но сами по себе их не доказывают.

## Из чего складывается память одного устройства

**VRAM** - память accelerator. В ней размещаются веса, состояние активных запросов и рабочие данные runtime. Для каждого устройства составьте отдельный баланс:

```
executor budget >= resident weights + KV cache
                   + прочие allocations + явный запас
```

Executor budget - часть памяти, которую разрешено использовать этому исполнителю. Остальная память устройства не обязана быть свободна для него. Resident weights - tensors после загрузки на device. Прочие allocations включают activations, временные buffers вычислительных kernels и служебное состояние runtime. Например, CUDA graphs сохраняют подготовленную последовательность GPU-операций для уменьшения overhead запуска и требуют дополнительной памяти.

Разделите startup peak и установившийся режим. При загрузке могут одновременно существовать разные представления весов; длинный prefill создаёт другой пик, чем короткий decode. Если runtime уже включил workspace и graph capture в отчёт о памяти вне KV, не вычитайте их повторно. Запас нужен для известных колебаний и неопределённости, а его размер уточняется наблюдением этих режимов. Настройки такого компромисса разобраны в [руководстве vLLM по памяти](https://docs.vllm.ai/en/v0.31.0/configuration/conserving_memory/).

У GPU-сервиса есть и host RAM: tokenizer, frontend, загрузчик artifacts, pinned buffers и offload тоже занимают ресурсы. CUDA OOM и Kubernetes OOMKill из-за RAM host требуют разных исправлений. CPU offload переносит часть хранения или работы с accelerator, но добавляет доступ к более медленной памяти и обмены в критический путь. Его выбирают под измеренный deadline.

Для однородных весов начальная арифметика проста: число parameters умножается на bytes на parameter. Ровно 8 миллиардов BF16-значений занимают 16 миллиардов bytes, около 14.90 GiB. При 4-bit packed representation сами значения занимают 4 миллиарда bytes, около 3.73 GiB; к ним прибавляются scales, возможные zero points, tensors другой precision и дополнительные resident representations. Размер скачанного файла не обязательно равен расходу VRAM после загрузки.

Quantization представляет значения меньшим числом bits; scale задаёт, как интерпретировать компактный числовой код. Такое приближение меняет точность, а способ группировки и поддержка kernels влияют на практический выигрыш. Сравнивайте не только освобождённые GiB, но и качество полного tool roundtrip на своих задачах. Меньшие weights полезны сервису, когда выбранное представление сохраняет нужную функцию модели.

В расчёте используйте bytes: `1 GB = 10^9 bytes`, `1 GiB = 2^30 bytes`. Название карты с числом «24» ещё не задаёт доступные 24 GiB. Нужны фактический объём device, занятые другими consumers ресурсы и выбранный executor budget.

У MoE, Mixture of Experts, router выбирает для token часть подсетей - experts. Это уменьшает активные вычисления по сравнению с использованием всех experts, но не определяет объём всех размещённых весов. Считать нужно resident experts и общие слои на каждом устройстве. Expert parallelism добавляет собственный обмен activations; число активных parameters нельзя подставлять вместо числа хранимых.

## Зачем модели нужен KV cache

Во время attention текущая позиция формирует query и сопоставляет её с keys предыдущих позиций. Полученные веса используются для смешивания values. Когда начинается следующий шаг генерации, старые keys и values снова нужны. Runtime сохраняет их в **KV cache**, чтобы не пересчитывать историю целиком при каждом новом token.

Веса модели одинаковы для разных запросов, а KV зависит от их последовательностей tokens. Два независимых диалога используют одну загруженную модель, но удерживают разное состояние attention. Кэш растёт на входной истории и во время генерации. Поэтому успешная загрузка весов отвечает лишь на первый вопрос о памяти.

Для одинаковых full-attention слоёв с одинаковой размерностью K и V:

```
KV bytes на token position = 2 × L × Hkv × D × B

L   - число attention layers
Hkv - число key/value heads
D   - размерность K/V head
B   - bytes на элемент cache
2   - отдельные tensors key и value
```

Пусть `L = 32`, `Hkv = 8`, `D = 128`, а cache хранится в BF16, то есть `B = 2`. Получается 131072 bytes на позицию, или 128 KiB. Одна sequence из 8192 сохранённых positions требует 1 GiB сырых K/V. Sequence здесь - отдельная последовательность генерации; один HTTP request с несколькими вариантами ответа может создать несколько sequences.

В multi-head attention у query heads есть соответствующие K/V heads. **GQA**, grouped-query attention, позволяет группе query heads использовать общие K/V; у **MQA** такая группа одна. В нашем примере замена восьми KV heads на 32 увеличила бы расход в четыре раза. Поэтому нужен именно `Hkv` из архитектуры, а не только число query heads. Это различие объясняется в [работе о GQA](https://arxiv.org/abs/2305.13245).

Для heterogeneous layers суммируйте расходы по слоям. MLA с compressed latent state, sliding-window, hybrid state-space, encoder-decoder и multimodal architecture требуют своей модели состояния и проверки backend. В частности, окно может ограничивать историю только части слоёв. Простая формула выше относится к указанному full-attention случаю.

## Посчитаем бюджет до выбора concurrency

Зададим условное устройство с фактическими 24 GiB. Для executor выделим 21 GiB, resident BF16-веса займут ровно 16 миллиардов bytes, прочие allocations - 3 GiB. Добавим отдельный запас 0.5 GiB внутри executor budget. Эти величины - входные допущения упражнения, не характеристики какой-либо модели GPU.

| Часть бюджета | Значение | Как учитывается |
| --- | --- | --- |
| Память устройства | 24 GiB | Верхняя физическая граница |
| Executor budget | 21 GiB | Внешние 3 GiB в расчёт KV не входят |
| Resident weights | 16000000000 bytes | Около 14.90 GiB внутри executor |
| Прочие allocations | 3 GiB | Без KV и без следующего резерва |
| Явный запас | 0.5 GiB | Дополнительная граница упражнения |
| Остаток для KV | 2790481920 bytes | Около 2.60 GiB |

Для учебного allocator примем block из 16 token positions. При 128 KiB на позицию он занимает 2 MiB. Из остатка помещаются 1330 полных blocks; неполный block отбрасываем. Одна sequence на 8192 positions требует 512 blocks. Значит, по этому консервативному бюджету одновременно помещаются две такие sequences, а третья потребовала бы уже 1536 blocks.

Размер block в упражнении выбран явно. Для настоящего runtime прочитайте его фактическую организацию cache. PagedAttention разбивает состояние на blocks и уменьшает потери от крупных непрерывных резервов, но не отменяет стоимость данных. Например, две независимые sequences по 17 positions требуют по два blocks при размере 16, а не один общий block на их суммарный остаток. Организация описана в [работе о PagedAttention](https://arxiv.org/abs/2309.06180).

Без отдельного резерва 0.5 GiB арифметический предел нашего примера был бы равен трём sequences по 8192. С резервом он равен двум. Это не изменение формулы KV, а следствие выбранного допустимого риска. В реальном deployment размер резерва обосновывают пиками и режимами отказа, вместо того чтобы считать лишнюю sequence бесплатной.

Для sequence на 32768 positions потребовались бы 4 GiB сырых K/V. Увеличение context limit само по себе не создаёт эти bytes. Веса можно уменьшить quantization, а cache - отдельным выбором KV dtype. Если менять только weights, стоимость одной BF16 KV position останется прежней. FP8 KV уменьшает сырые данные относительно 16-bit, но добавляет требования к scales, kernels и проверке качества, особенно на длинной истории и tool calls. Поддержку сверяют с [документацией KV quantization](https://docs.vllm.ai/en/v0.31.0/features/quantization/quantized_kvcache/).

Prefix caching позволяет переиспользовать уже вычисленный общий prefix. Например, одинаковые инструкции и длинный документ могут не потребовать повторного полного prefill. Это зависит от совпадения prefix и наличия его состояния у выбранной replica; после eviction или cold start путь будет другим. Новые output tokens всё равно нужно вычислять. Эти границы важны при выборе warm и cold сценариев приёмки, как показано в [руководстве prefix caching](https://docs.vllm.ai/en/v0.31.0/features/automatic_prefix_caching/).

## Практика расчёта и допуска запросов

Программа [examples/ch41\_inference\_budget.py](https://github.com/5UN5H1N3/ax-agent-infrastructure-book/blob/main/examples/ch41_inference_budget.py) воспроизводит этот memory sheet и простой admission gate - решение, принять ли запрос в работу. Для запуска достаточно Python 3.13 и стандартной библиотеки:

```
python3 examples/ch41_inference_budget.py
python3 -m unittest discover -s examples -p 'test_ch41_inference_budget.py'
```

Gate резервирует верхнюю границу `prompt_tokens + max_new_tokens` для каждой sequence, округляя каждую отдельно. Это консервативная политика без sharing: запрос с prompt 7680 и output cap 512 получает резерв на 8192 positions, даже если ответ в итоге окажется короче. У настоящего serving scheduler cache может выделяться постепенно; он способен принять больше работы, затем столкнуться с ростом cache и preemption. Упражнение выбирает простую проверяемую границу, а не воспроизводит алгоритм vLLM.

Ключевой расчёт в примере:

```
blocks = blocks_for_tokens(
    request.prompt_tokens + request.max_new_tokens,
    memory.block_tokens,
) * request.sequences
```

В demo получаются следующие решения. Limit числа sequences установлен в 3 специально, чтобы третий короткий запрос упёрся именно в память, а не в число slots.

| Событие | Решение | Объяснение |
| --- | --- | --- |
| Первый короткий запрос | `ACCEPT` | Занято 512 из 1330 blocks |
| Второй короткий запрос | `ACCEPT` | Занято 1024 blocks |
| Третий короткий запрос | `REJECT_KV` | Требовалось бы 1536 blocks |
| Завершить первый, принять новый | `ACCEPT` | Освобождённый резерв можно использовать снова |
| Запрос на 32768 positions в interactive pool | `REJECT_CONTEXT` | Превышен контракт 8192 |
| Тот же запрос при context limit 32768 | `REJECT_KV` | В пустом pool всё ещё не хватает памяти |

Часть вывода `memory`:

```
{
  "kv_bytes_per_token": 131072,
  "block_bytes": 2097152,
  "kv_budget_bytes": 2790481920,
  "kv_blocks": 1330,
  "max_8192_sequences": 2,
  "without_reserve_8192_sequences": 3
}
```

Отклонение не меняет занятый бюджет. Освобождение происходит отдельным `release` после подтверждённого окончания backend work. Отключение клиента само по себе не доказывает, что генерация остановилась и cache уже освобождён. В распределённом admission нужны согласованный учёт, обработка потери владельца и повторов; здесь gate однопоточный, локальный и без очереди.

Пример проверяет целочисленную арифметику, округление, несколько sequences и освобождение резерва. Он не загружает weights, не токенизирует текст и не исполняет attention. В нём нет GPU, временной модели decode, prefix sharing, TP/PP, offload или vLLM. Поэтому `ACCEPT` означает прохождение учебных memory limits; поле `slo_proven` остаётся `false`.

## Почему вместимость и скорость измеряют отдельно

Prefill обрабатывает входную историю, decode последовательно добавляет tokens. Full attention при длинном prefill выполняет работу над парами позиций, а при decode каждый следующий шаг обращается к накопленной истории. Следующий token обычной autoregressive generation зависит от предыдущего, поэтому дополнительные GPU не превращают один ответ в произвольное число независимых вычислений.

При небольшом decode batch заметную роль может играть чтение весов и KV из памяти. Для проверки порядка величины: чтение 14.90 GiB при условной эффективной bandwidth 600 GiB/s заняло бы около 25 ms. Это время одного предполагаемого компонента, не прогноз latency модели. В реальном шаге есть другие kernels и обмены, а характер чтения определяется backend. Выбор устройства нельзя завершить по этой оценке.

Batch позволяет использовать одно вычисление для нескольких sequences. Поэтому суммарные tokens/s могут расти, хотя отдельный пользователь не получает ответ быстрее. Continuous batching включает новую работу по мере освобождения места; длинный prefill при этом способен повлиять на decode остальных запросов. Chunked prefill делит входную работу на части и позволяет scheduler чередовать её с другой работой. Размер iteration budget выбирают по TTFT и плавности stream, а не по одному aggregate throughput. Механизм настройки разобран в [руководстве vLLM по производительности](https://docs.vllm.ai/en/v0.31.0/configuration/optimization/).

Посмотрите, какой ресурс исчерпан первым. Рост очереди при свободном KV требует другого опыта, чем регулярная cache preemption. Если время уходит в collectives, увеличение batch limit может не исправить interconnect. Если CPU не успевает подготовить вход, свободная GPU не объясняет проблему сама по себе. Этот разбор определяет следующий эксперимент.

## Как выбрать между replicas и распределением модели

Если модель уже помещается на одном устройстве и проходит single-request SLO, первым кандидатом для увеличения обслуженного потока становятся независимые replicas. Каждая содержит свою модель, cache и очередь и получает отдельные запросы. Понадобится routing: длинные запросы и тёплые prefixes могут распределиться неравномерно. Приёмка должна показать полезный результат всего pool.

**Tensor parallelism, TP**, распределяет tensors и вычисления внутри поддерживаемых слоёв одной replica. **Rank** - участник распределённой группы, обычно процесс со своим устройством. Результаты участников приходится согласовывать во время исполнения слоёв. Например, [all-reduce](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html) суммирует частичные результаты и возвращает итог каждому участнику. Такие collectives входят в критический путь генерации и повторяются, а не выполняются один раз после ответа.

![Tensor parallelism: sharded layer and communication repeat during decode](.gitbook/assets/diagrams/41-40.png)  
*Tensor parallelism: sharded layer and communication repeat during decode*

Схема показывает фрагмент слоя, а не все операции конкретного backend. TP может помочь разместить weights и изменить время вычисления. Цена зависит от раскладки tensors и связи устройств: быстрый NVLink/NVSwitch, PCIe и сеть между hosts дают разные условия. Перед cross-node размещением измерьте доступную topology и communication profile. Поддерживаемые варианты размещения описаны в [руководстве vLLM по parallelism](https://docs.vllm.ai/en/v0.31.0/serving/parallelism_scaling/).

Память всех ranks нельзя получить простым делением на TP size. Часть tensors и buffers остаётся replicated. В частности, в [ModelConfig v0.31.0](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/model.py) при TP больше числа KV heads предусматривается их replication, чтобы на GPU оставалась как минимум одна KV head. Совместимость split и фактический cache проверяйте по architecture и каждому rank. Самый тесный участник ограничивает группу.

**Pipeline parallelism, PP**, размещает группы слоёв на разных stages. Данные одного запроса проходят stages последовательно. При достаточном потоке работу можно перекрывать; при дисбалансе stages и малом потоке часть устройств простаивает - возникают pipeline bubbles. PP стоит сравнить, когда модель не помещается, а частые TP collectives слишком дороги. Возможно сочетание TP внутри быстрой группы и PP между группами, если это поддерживает выбранный runtime.

| Исходная проблема | Что сравнить первым | Какой результат нужен |
| --- | --- | --- |
| Одна replica помещается, очередь растёт | Независимые replicas | Рост goodput при сохранении SLO |
| Одна replica не помещается | Поддерживаемые TP или PP | Память каждого rank и приемлемая задержка |
| Редкие длинные запросы мешают коротким | Отдельный pool или scheduling limits | Изоляция без чрезмерного простоя |
| Нужно пережить потерю host | Полные replicas в разных failure domains | Capacity после потери всей затронутой группы |

В MoE режим data parallel конкретного engine может взаимодействовать с размещением experts. Поэтому флаг DP и несколько независимых deployments не всегда описывают одну конструкцию. Называйте топологию явно: сколько полных обслуживающих групп существует и какие устройства обязательны для каждой.

## Свяжите настройки vLLM с расчётом

Для конкретного примера сохраняем профиль книги **vLLM v0.31.0**. Команда ниже предназначена для собственного лабораторного listener. Каталог `/srv/models/agent-release` заранее содержит проверенный text-only artifact, config, tokenizer и chat template; model revision и container digest фиксируются в описании deployment. Перед запуском замените учебный memory budget расчётом и profiling для этого artifact и устройства.

```
vllm serve /srv/models/agent-release \
  --host 127.0.0.1 --port 8000 \
  --served-model-name ax-agent-lab \
  --max-model-len 8192 \
  --kv-cache-memory-bytes 2790481920 \
  --max-num-seqs 2 \
  --max-num-batched-tokens 2048 \
  --enable-chunked-prefill \
  --max-num-queued-reqs 4 \
  --tensor-parallel-size 1 \
  --pipeline-parallel-size 1
```

Здесь явный KV budget связан с учебным расчётом. Он ограничивает cache, а не весь расход VRAM: weights, рабочая память и startup peaks по-прежнему должны поместиться. Альтернативный путь - позволить runtime вывести KV budget из `--gpu-memory-utilization`. Эти два режима не складываются: заданный `--kv-cache-memory-bytes` заменяет соответствующий расчёт по utilization. Значение utilization относится к экземпляру executor и не создаёт эксклюзивную reservation на GPU; поведение фиксирует [CacheConfig этой версии](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/cache.py).

Context limit 8192 относится к общей длине запроса и продолжения, а output cap задаётся в model request. `--max-num-seqs` ограничивает sequences за iteration и размерность runner, `--max-num-batched-tokens` - token budget работы scheduler. Поэтому batch budget 2048 не означает context limit 2048. В команде chunked prefill включён явно: модель и backend должны его поддерживать. Без этого режима указанное соотношение limits не годится.

`--max-num-queued-reqs 4` в этом срезе считает waiting и running requests в API server, а не только длину очереди. Даже четыре in-flight запроса могут ждать слишком долго. Отдельный admission должен учитывать deadline, tenant quota и доступный ресурс pool. Детали и проверки сочетаний limits находятся в [SchedulerConfig](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/config/scheduler.py). Loopback listener также не организует защищённый доступ из Actors: его маршрут и authorization проверяются отдельно по главе 40.

## Какими инструментами проверить гипотезу

Для арифметики нужны config архитектуры, dtype tensors и точные bytes. Затем нужны сведения runtime о resident allocations и cache. Сравнивайте три состояния: startup, обычная работа и стрессовый длинный prefill с допустимым output. Сохраняйте model revision, runtime/image digest, driver, GPU topology и arguments рядом с результатом, иначе следующий запуск может оказаться другим опытом.

`nvidia-smi` удобен для проверки устройства, процессов и общей занятой памяти; его поля описаны в [руководстве NVIDIA](https://docs.nvidia.com/deploy/nvidia-smi/index.html). Большая allocation может быть заранее выделенным KV pool. Для понимания его использования добавьте telemetry runtime: cache occupancy, active/waiting requests, preemption и timings. Для разбора CPU/GPU timeline и обменов можно использовать [Nsight Systems](https://docs.nvidia.com/nsight-systems/UserGuide/index.html) с нужными tracing options. Он помогает найти участок ожидания; клиентский нагрузочный опыт показывает, выполняется ли обещание пользователю. Profiling может менять latency, поэтому финальный SLO проверяют в обычном режиме сервиса.

Сделайте sweep с одним изменяемым фактором: например, sequence limit 1 и 2 при неизменном artifact и trace. По методике главы 21 зафиксируйте отправленные попытки, queue age, TTFT, ITL или inter-chunk latency, E2E, failures и качество. В report оставляйте и отклонённые запросы. Быстрый отказ может защитить уже принятую работу, но не становится своевременным правильным ответом.

Отдельно проверьте cache-cold запуск, burst после resume, длинный prompt, максимальный output и cancellation. Проверка prefix reuse не заменяет cold path. Выбирайте последнюю нагрузку, при которой выполняется весь контракт: независимые p95 latency и доля валидных ответов не задают автоматически долю запросов, одновременно правильных и своевременных. Для этого нужна совместная проверка результата каждой попытки и goodput.

## Как рассчитать мощность после отказа

Вернёмся к размещению, а не к модели cache. Предположим для отдельного арифметического опыта, что одна replica обслуживает 2 requests/s при выбранном SLO, а требуемый поток равен 3 requests/s. В настоящем плане первое число берут из приёмки нужного workload. В demo оно задано как fixture и не измеряется.

| Размещение полных replicas | Номинально | После худшей потери одного host |
| --- | --- | --- |
| Две на одном host | 4 requests/s | 0 |
| Две на двух hosts | 4 requests/s | 2 requests/s |
| Три на трёх hosts | 6 requests/s | 4 requests/s |

Третье размещение проходит только арифметическую проверку заданного потока после отказа. В эксперименте `placement` программа исключает все replicas одного domain и берёт худший остаток. Она не испытывает реальную балансировку, correlated failures или обслуживание burst. Даже при подходящей сумме мощностей перегруженная отдельная очередь может нарушить SLO.

Одна replica с TP=2 остаётся одной обслуживающей группой. Потеря обязательного rank выводит её из работы; два GPU не означают два независимых резерва. Failure domain выбирается по обещанию сервиса: device, host, rack или зона. Испытание должно исключать соответствующую группу целиком.

Учтите время до готовности замены: placement, загрузку weights, подготовку kernels, health и безопасный probe. Autoscaling помогает следующей нагрузке, но не обязан успеть к текущему burst. Rollout тоже потребляет запас. Укажите, какой SLO требуется при одновременном обновлении и отказе, а при недостатке мощности определите явный degraded mode и приоритет классов.

## Как оформить решение и связать его с агентом

Capacity plan должен позволить другому инженеру повторить выбор. Запишите допустимые request classes и token limits, memory sheet с источником каждого значения, topology и результаты приёмки. Рядом укажите normal/degraded SLO, допуск перегрузки, failure domains и время подготовки replacement. Изменение artifact, KV dtype, runtime или topology требует новой проверки затронутых свойств.

Harness отвечает за допустимый context, output cap, deadline и продолжение agent step. Inference runtime управляет kernels, batching и cache; deployment предоставляет capacity, а admission и routing должны иметь явного владельца. AX Task обращается к стабильному логическому endpoint. В срезе AX `ac233282` это требует явной настройки пользовательского harness; ресурс `Model` не подключает его автоматически, как разобрано в главах 17 и 20.

При перегрузке harness может отложить background step, собрать более короткий допустимый context или применить заранее проверенный fallback. Сокращение истории проходит context policy главы 35: случайное удаление instructions и tool results меняет задачу. Более слабая модель требует capability/quality tests главы 20. Дополнительные physical attempts расходуют общий retry budget и наблюдаются отдельно от logical call.

Частичный stream с tool arguments ещё не является готовым разрешённым действием. Если внешняя mutation уже началась, неизвестный outcome разрешается по operation ledger и reconciliation главы 37, а не повторной генерацией команды. Suspend Actor также не сохраняет KV cache общего model server как backup: продолжение run опирается на durable logical state.

Итог для инженера - объяснимый выбор: две sequences допускаются по заданному memory budget, replicas выбираются для нужного потока, TP/PP - для поддерживаемого совместного исполнения, резерв распределяется по нужным failure domains. Дальше остаётся вернуть к этому сервису актуальные права и безопасное состояние после аварии. Этому посвящена глава 42: запас мощности и восстановление доверия решают разные части production readiness.
