# Практикум: 14 последовательных лабораторных работ

В предыдущих главах мы разбирали устройство агентной платформы и причины её отказов. Теперь соберём учебную систему и попробуем объяснить каждое её поведение. В конце маршрута важно уметь ответить на вполне рабочие вопросы: почему задача не получила код, что сохранилось после suspend, кто разрешил сетевой запрос и окупилось ли добавление второго агента.

Практикум начинается с отдельной VM, проходит через Kubernetes и Substrate, затем добавляет AX, модель и два прикладных сценария. По дороге используются два небольших приложения. Counter показывает разницу между памятью и файлами; Python-проект с потерей записей даёт одну понятную задачу для сравнения harness и способов координации. Так изменения поведения можно связать с конкретным слоем системы.

## Маршрут, версии и правила эксперимента

**В этой главе отдельный профиль AX `v0.3.1`.** Здесь работает отдельный controller, Task применяется через `UpdateTask`, а намерение приостановить его хранится в `spec.suspend`. В главе 26 использован другой срез, `ac233282`, с immutable `CreateTask`. CLI, server, runner и manifest должны соответствовать выбранному профилю. В обеих схемах отсутствуют Task→Model reference и Gateway kind: выбор модели делает вызывающий её компонент приложения.

Если у вас остался стенд главы 26, сохраните его и выделите отдельную VM для этого маршрута. Смена CLI поверх прежнего server не воспроизводит другой профиль. Практикум содержит опорные команды и критерии проверки, но не является универсальным установщиком. Значения в угловых скобках требуют замены; команды приводятся для будущего выполнения читателем на выделенном стенде.

| Компонент | Что записать в паспорт | Как это влияет на опыт |
| --- | --- | --- |
| AX | `v0.3.1`, полный SHA, CLI build, digests server/controller/runner | Определяет schema, подготовку Workspace и поведение запуска |
| Substrate | `df788825e6fc13dd7aa5fd283c8f14bd4c818247`, deployed digests | Определяет реальный Actor API, runtime и snapshot contract |
| Kind, Kubernetes, Go, ko | Требования pinned scripts и фактические версии | Позволяет отделить ошибку сборки от ошибки приложения |
| llama.cpp и модель | Выбранный commit/release, build flags, SHA256 GGUF, лицензия | Фиксирует измеряемый CPU-вариант |
| vLLM и модель | `v0.30.0`, вариант image и digest, model revision, quantization, GPU/driver | Фиксирует измеряемый GPU-вариант |

Пара AX `v0.3.1` и Substrate `df788825` остаётся **кандидатом для интеграционного испытания, не подтверждённой совместимой сборкой**. AX закреплён на `e70162a34037c221fe6fadefd98308c05a4ad8f3`; его `go.mod` использует SDK Substrate `v0.0.0-20260911232748-672533541dbf`. SDK и установленный сервер — разные версии разных частей связи. Более того, в исходниках уже виден drift: AX строит старый `SnapshotsConfig` с `onPause`, `onCommit` и `onResume.fromData=GOLDEN`, а серверный срез этой главы описывает `SnapshotConfig` с `onCommit` и `storageLocation`, где DATA восстанавливается холодным запуском контейнеров. Поля прежнего SDK нельзя механически переносить в новый manifest. Сравнение исходников показывает расхождение контрактов; конкретный результат RPC и всего жизненного цикла должен установить интеграционный тест.

Работы 1–6 можно проходить на одном Substrate. Работы 7–8 проверяют создание Task и сохранность его файлов; при несовместимости переход к AX-части останавливается. Работа 9 отдельно проверяет сетевую границу — её результаты не требуются задним числом для допуска к ней самой. В работе 10 нужен harness и один доступный модельный endpoint. Облачный маршрут необязателен: без cloud credentials сначала пройдите работу 11 и вернитесь к циклу работы 10 с локальной моделью. Работа 12 — дополнительная GPU-ветка. Для работ 13–14 достаточно одного проверенного endpoint, исправного цикла работы 10 и пройденной сетевой проверки.

Создайте журнал: `versions.txt`, `commands.md`, каталог `before-after/`, `metrics.csv` и короткий `result.md` для каждой работы. В нём должны быть исходное состояние, проверяемое предположение, действие, наблюдения и вывод. Различайте «прошло», «не прошло» и «не запускалось». Отсутствие GPU означает непроверенную GPU-ветку; отсутствие результата интеграции блокирует зависимые работы. Успешный offline-тест учебного кода подтверждает только этот код.

Секреты, bearer tokens и содержимое Secret в журнал не включаются. Сохраняйте имена ресурсов, версии policy, обезличенные reason codes и checksum артефактов. Перед каждым контролируемым сбоем определяйте точный учебный объект, ожидаемый ущерб, способ восстановления и условие остановки. Для этих опытов не нужны рабочие репозитории, сеть организации, настоящие metadata endpoints или ключи с широкими правами.

### Lab 1. Подготовка VM: получить базу, к которой можно вернуться

Начнём с отделения платформы от её хоста. Выделенная Debian или Ubuntu LTS VM позволяет менять runtime и сеть, сохраняя понятный путь возврата. Kind выбран ради локального учебного кластера, а не для доказательства production-отказоустойчивости: несколько его nodes на одной VM всё ещё зависят от одной VM и одного физического хоста.

Для планирования можно начать с 8 vCPU, 16 GiB RAM и 100 GiB диска; для одновременной сборки образов и локальной модели удобнее 16 vCPU, 32 GiB и 200 GiB. Это ориентиры, не официальные минимальные требования. Выбирайте размер после учёта модели, snapshot store и числа одновременно работающих Actors. Запас диска нужен ещё и для диагностики: нехватка места способна одновременно сломать registry, PostgreSQL и сохранение snapshots.

```
uname -a
lscpu
free -h
df -h
timedatectl status
docker version
kubectl version --client
go version
test -c /dev/kvm && ls -l /dev/kvm
```

Установите Git, Docker, kubectl, Go и ko по требованиям выбранных исходников. Проверьте DNS, доступ к registry, сборку небольшого Go-приложения и запуск тестового контейнера. Для microVM понадобится KVM по всей цепочке гипервизор → VM → runtime. Наличие device-файла ещё не показывает, что нужный процесс может его открыть. Недоступность KVM запишите сразу: она не мешает исследовать gVisor и CPU inference.

У тестового контейнера создайте один файл в его writable layer, другой — в явно подключённом volume. Остановите контейнер, затем отдельно пересоздайте его без прежнего writable layer и с прежним volume. Простая остановка обычно сохраняет оба файла; именно пересоздание показывает различие их жизненных циклов. Пользуйтесь только выделенным тестовым объектом. После возврата к чистому состоянию сделайте snapshot VM `ax-lab-base` и проверьте восстановление на учебной копии. Результат работы — паспорт хоста и понятный откат. Snapshot VM здесь не заменяет согласованный backup будущих PostgreSQL и object storage.

### Lab 2. Kind и Kubernetes: научиться читать причину отказа

До Substrate полезно увидеть обычное HTTP-приложение в Kubernetes. Deployment отвечает за экземпляры процесса, Service даёт устойчивый способ обращения к ним, readiness показывает, можно ли направлять трафик в конкретный экземпляр. Эти обязанности различаются, поэтому «Pod запущен» ещё не объясняет ответ клиента.

**В pinned `create-kind-cluster.sh` есть удаление уже существующего кластера с выбранным именем; при настройке сети затрагивается и Docker network Kind.** Выполняйте его только в выделенной VM, предварительно сверив ресурсы. Укажите отдельное имя `ax-lab32`. Один лишь новый context не изолирует общий Docker daemon или registry от других экспериментов.

```
git clone https://github.com/agent-substrate/substrate.git
cd substrate
git checkout df788825e6fc13dd7aa5fd283c8f14bd4c818247
KIND_CLUSTER_NAME=ax-lab32 hack/create-kind-cluster.sh
kubectl config current-context
kubectl get nodes -o wide
kubectl get pods -A
```

Далее все команды относятся к полученному учебному context. Подготовьте namespace `lab32`, небольшой HTTP Deployment, Service и readiness probe на существующий путь. Зафиксируйте digest образа и port/targetPort. Из другого тестового Pod проверьте DNS Service и HTTP-ответ. Сверьте selector, labels и EndpointSlice. В обычном Service неготовые backends не используются для обычной маршрутизации; специальный `publishNotReadyAddresses` в этом опыте оставьте выключенным.

Внесите две ошибки по очереди, возвращая исправный manifest между ними. Несуществующий image tag мешает получить образ: полезны Events и состояние ожидания контейнера. Неправильный readiness path оставляет работающий HTTP-процесс неготовым для Service: полезны probe, EndpointSlice и запрос непосредственно к приложению из разрешённой тестовой точки.

```
kubectl get events -n lab32 --sort-by=.lastTimestamp
kubectl describe pod -n lab32 <test-pod>
kubectl logs -n lab32 <test-pod>
kubectl get endpointslices -n lab32
```

Сохраните три диагностические карточки: ошибка получения image, ошибка процесса, ошибка готовности. Для crash выберите безопасную заведомо завершающуюся команду только в тестовом Deployment. В каждой карточке нужны симптомы, наблюдение, различающее причины, и способ возврата. Работа закончена, когда вы можете объяснить, почему одинаковый клиентский «сервис недоступен» требует разных исправлений.

### Lab 3. Substrate: увидеть отдельный control plane

Теперь добавим слой, который создаёт Actors и размещает их на Workers. Kubernetes управляет обслуживающими Pods, а Substrate — собственными объектами. В этом снимке Actors, Workers и ActorTemplates хранятся в PostgreSQL control plane. WorkerPool, напротив, является Kubernetes CRD. Этот разрез подсказывает, какой инструмент задаёт нужный вопрос: kubectl показывает Pod, kubectl-ate — состояние Actor.

Следующие команды выполняются из checkout Substrate работы 2. При выборе context сверяйтесь с выводом pinned scripts.

```
hack/install-ate-kind.sh --deploy-ate-system \
  --credential-provider='{"name":"k8s.io"}'
hack/install-ate-kind.sh --deploy-demo-counter
go install ./cmd/kubectl-ate
kubectl get pods -n ate-system
kubectl get svc api -n ate-system
kubectl get workerpool -A
kubectl ate get workers
kubectl ate create actor my-counter-1 \
  -a ate-demo-counter --template counter
kubectl ate resume actor my-counter-1 -a ate-demo-counter
kubectl ate get actor my-counter-1 \
  -a ate-demo-counter -o yaml
```

Проследите готовность template и его golden tag, создание Actor, назначение Worker и готовность приложения. PostgreSQL хранит записи control plane; RustFS в локальной конфигурации хранит объекты snapshots. Проверка Pods нужна, но подтверждение пути данных появится только после успешного suspend/resume. Credential provider `k8s.io` стартует с пустой разрешающей политикой namespaces. Для counter, не требующего внешнего ключа, оставьте её закрытой.

В отдельном терминале откройте учебный путь через router, затем отправьте запрос из второго терминала:

```
kubectl port-forward -n ate-system svc/atenet-router 8000:80
# Во втором терминале:
curl -X POST -i http://localhost:8000/ \
  -H 'ate-target-actor: ate-demo-counter/my-counter-1'
```

Router выбирает Actor по `ate-target-actor`; адрес localhost здесь ведёт к вашему port-forward. Остановите только этот port-forward и повторите запрос. Если Actor API по-прежнему доступен и показывает живой Actor, отказ относится к локальному пути клиента. Так проверяется полезность раздельных наблюдений. В отчёте нарисуйте фактическую цепочку клиент → port-forward → router → Worker → counter и подпишите, какой лог или API наблюдает каждый переход.

### Lab 4. Actor lifecycle: identity переживает размещение

Actor нужен, чтобы у приложения сохранялась идентичность, пока место исполнения меняется. Для отдельного опыта создайте atespace `lab32` и локальный template counter. Возьмите исходный manifest из `demos/counter/`, разрешите ko-ссылку в image digest по pinned пути, укажите учебный atespace, object storage и совместимый WorkerPool. Файл с суффиксом `.tmpl` содержит подстановки; его нельзя выдавать за готовый YAML после одной смены имени. Сохраните полученный `lab-counter-template.yaml` и дождитесь готовности golden tag.

```
kubectl ate create atespace lab32
kubectl ate create actor-template -f lab-counter-template.yaml
kubectl ate get actor-template counter -a lab32 -o yaml
kubectl ate create actor lab-counter -a lab32 --template counter
kubectl ate resume actor lab-counter -a lab32
kubectl ate get actor lab-counter -a lab32 -o yaml
# После подтверждённого RUNNING:
kubectl ate suspend actor lab-counter -a lab32
kubectl ate get actor lab-counter -a lab32 -o yaml
kubectl ate resume actor lab-counter -a lab32
kubectl ate get actor lab-counter -a lab32 -o yaml
```

После каждого перехода записывайте `(atespace, name)`, UID, VERSION, state и Worker assignment. Имя помогает обращаться к объекту; UID отличает его от другого объекта, созданного позднее под тем же именем. VERSION различает изменения состояния, но не заменяет checksum приложения. При suspend Worker освобождается; после resume может назначиться и тот же Worker. Его смена не является условием успеха.

В двух отдельных попытках укажите отсутствующий atespace и отсутствующий локальный template. Ответ API должен позволить исправить конкретную зависимость. Наличие template `counter` в `ate-demo-counter` не создаёт одноимённый template в `lab32`. Итог работы — timeline одного Actor с объяснением каждого перехода и двух отклонённых запросов. Позже этот timeline поможет отличить задержку placement от долгой подготовки Workspace.

### Lab 5. Snapshot/resume: проверить, какое состояние восстановлено

У counter есть счётчик в RAM и счётчик в файле `/home/counter/a.txt` на durable volume. Это два независимых наблюдаемых состояния. В pinned counter template выбран Full snapshot; при восстановлении из него ожидается продолжение обоих счётчиков. Для Data-опыта подготовьте отдельный immutable template с `snapshotConfig.onCommit=SNAPSHOT_CONTENT_SCOPE_DATA`. В Substrate `df788825` Data восстанавливает durable directories и запускает контейнеры заново. Полей выбора `onResume` и `onPause` в этой schema нет. Старый Data/GOLDEN contract SDK AX разбирается отдельно в работе 7.

Запишите исходные значения, сделайте известное число запросов и прекратите клиентский трафик перед suspend. Запрос через router способен разбудить приостановленный Actor. Пока проверяете состояние SUSPENDED, читайте его через control plane, а не опрашивайте counter. Каждый запрос к `/` меняет оба счётчика: проверочное чтение тоже входит в ожидаемую сумму.

Например, перед suspend ответ показал memory=5 и file=5. Если после resume выполнен ровно один запрос и не было другого трафика, Full должен дать 6/6; Data при холодном старте процесса — 1/6. Это расчёт ожидаемого результата, не отчёт о выполненном стенде. Неожиданное 7/7 может означать лишний probe к `/`, а не повреждение snapshot. Сопоставьте router logs и пути probes, прежде чем менять runtime.

| Что сравнивается | Full | Data в `df788825` |
| --- | --- | --- |
| Durable-файл | Содержимое из сохранённого snapshot | Содержимое из сохранённого snapshot |
| Индивидуальная RAM процесса | Восстанавливается при совместимом Full restore | Не сохраняется как продолжение процесса |
| Удалённая запись во внешнем API | Не откатывается этим snapshot | Не откатывается этим snapshot |

Выполните десять циклов для каждого исследуемого варианта. Раздельно измеряйте длительность API-вызова, достижение SUSPENDED и готовность приложения после resume. При настроенном wakeupProbe Substrate ждёт его успешного ответа; смысл этой готовности ограничен тем, что действительно проверяет probe. Содержимое файла и итог приложения проверяйте отдельно. Для дополнительного checksum-опыта используйте sandbox demo с безопасным доступом к файлам: создайте один маркер, сохраните SHA256 и сравните после восстановления.

Затем создайте Tag из остановленного учебного Actor и новый Actor из этого Tag по pinned CLI. Tag владеет своей копией snapshot; сохраните его identity и способ удаления. Отдельно обсудите восстановление после потери Worker: всё после последнего пригодного snapshot может быть потеряно. Такой сбой допустим только в выделенном pool без чужих Actors и с заранее подготовленным возвратом. Его можно оставить как непроверенную ветку. Не совмещайте его с десятью обычными циклами и не записывайте в ту же выборку latency. Результат работы — измеренная граница сохранности файлов и RAM, а не один зелёный status.

### Lab 6. Выбор runtime: проверить совместимость своей нагрузки

Используйте тот же counter и небольшой сценарий с файлами, subprocess, DNS и HTTPS. gVisor даёт sandbox с собственным слоем обработки системных вызовов; microVM добавляет аппаратную виртуализацию и гостевую среду. Эти различия влияют на доступные операции, стоимость запуска и требования к хосту. Выбор начинается с того, что требуется приложению, и с принятой модели угроз.

Создайте отдельные templates и подходящие WorkerPools по pinned руководству. Template явно задаёт sandbox class и config name; scheduler должен найти pool того же класса. Snapshot нельзя переносить из gVisor в microVM как готовое состояние. Установленный где-то Kubernetes RuntimeClass сам по себе не переключает runtime Actor.

Для сравнения сохраняйте одинаковые image, вход, ограничения CPU/RAM и прикладную проверку результата. Сравните холодный старт и suspend/resume, потребление ресурсов, поддерживаемые операции. Если subprocess или mount не работает, сохраните точную ошибку и выясните, вызвана ли она runtime, отсутствующей программой или policy. Увеличение привилегий меняет условия опыта и требует отдельной оценки безопасности.

| Результат | Инженерное решение |
| --- | --- |
| Нагрузка работает в обоих runtime | Сравнить требуемую изоляцию, latency, цену ресурсов и сопровождение |
| Нужная операция не поддержана | Оценить изменение приложения либо другой runtime и повторить прикладной тест |
| В VM нет доступного KVM | Зафиксировать непроверенную microVM-ветку; продолжить gVisor-маршрут |

В отчёте выберите runtime для этой нагрузки и назовите условие пересмотра решения. Успех counter не подтверждает совместимость всех будущих инструментов агента. Проверка KVM на физическом Proxmox-host также не подтверждает его доступность внутри node/runtime.

### Lab 7. Установка AX: найти границу интеграции

AX добавляет Task и Workspace поверх Actor API. Для него нужны доступный Substrate API, registry и корректная пара клиентского SDK с сервером. Отдельный controller этого release выполняет reconciliation; CLI лишь отправляет запросы. Поэтому успешная установка CLI и доступные Pods дают только начальную точку диагностики.

```
git clone https://github.com/google/ax.git
cd ax
git checkout v0.3.1
git rev-parse HEAD
go install github.com/google/ax/cmd/ax@v0.3.1
kubectl get svc api -n ate-system
make deploy AX_IMAGE_REPO=<lab-registry-path>
kubectl get pods -n ax-system
ax version
ax ctx
```

До deployment сверьте Makefile и manifests выбранного release с учебным context, registry и адресом Substrate API. Сохраните фактические digests Redis, server/controller и runner. Проверяйте registry из той точки, откуда image действительно загружается: localhost разработчика и localhost Kubernetes node могут означать разные машины.

Теперь сравните `internal/substrate/client.go` AX со schema установленного Substrate. Старый builder использует `SnapshotsConfig`, `ContainerReadyz` и Data/GOLDEN; новый сервер описывает другие поля snapshot и `wakeupProbe`. Одинаковое назначение поля не гарантирует совпадения wire contract и поведения. Для интеграционного журнала нужны точный RPC, обезличенный ответ, серверный лог и созданный объект, прочитанный обратно серверным CLI. При ошибке остановитесь на этом слое. Переименование YAML-поля или подстановка другого CLI не исправляют уже собранный server binary.

Если нужна адаптация SDK или другая пара версий, это отдельный вариант стенда: зафиксируйте diff, новые digests и повторите проверки жизненного цикла. Книга не назначает такую пару совместимой без запуска. Контрольная ошибка с недоступным registry допустима только для одного учебного image и после сохранения исправной настройки. Отличите её от отказа RPC по наблюдениям работы 2. Результат работы 7 — доступный AX control plane и открытый, ещё не завершённый протокол интеграции; работу 8 можно начинать лишь после устранения известных блокирующих ошибок API.

### Lab 8. Task + Workspace: проверить файлы и результат команды

Возьмём Python-проект, который должен делить список на пачки и теряет остаток. В репозитории книги есть генератор `examples/ch32_batching_exercise.py`. Он создаёт в выбранном существующем каталоге новый дочерний `ax-lab32-batching` с тремя файлами: кодом, десятью тестами и README. Каталог с таким именем должен отсутствовать; существующие файлы генератор не перезаписывает. Сеть, Git и агенты ему не нужны.

```
# Из корня локальной копии книги; каталог /tmp уже существует.
python3 examples/ch32_batching_exercise.py /tmp
cd /tmp/ax-lab32-batching
python3 -m unittest -v
```

Ожидаемый baseline — десять тестов и три failures: `test_tail`, `test_short`, `test_coverage`. Это намеренно неисправный учебный проект. Если исходный результат другой, разберитесь до запуска модели. Создайте отдельный учебный Git-репозиторий из этих трёх файлов, запишите input commit и предоставьте runner доступ к нему. Весь репозиторий книги, включая авторские тесты с эталонным исправлением, в Workspace передавать не нужно.

Ниже шаблон `lab-task.yaml` для AX `v0.3.1`. Сначала применяется Workspace, затем Task. Подставьте URL своего учебного repo, branch и runner image, содержащий `/usr/local/bin/ax-task-runner`, Git и Python. Digest выбирается из вашего паспорта. `dir: .` помещает checkout в корень `/workspace`, поэтому команды далее используют именно этот путь.

```
apiVersion: ax.io/v1alpha1
kind: Workspace
metadata:
  name: lab-code
  atespace: lab32
spec:
  git:
    - name: origin
      repo: "<lab-repository-url>"
      branch: "<lab-branch>"
      dir: .
---
apiVersion: ax.io/v1alpha1
kind: Task
metadata:
  name: lab-task
  atespace: lab32
spec:
  image: "<runner-image@sha256:digest>"
  workspaces:
    - name: lab-code
      path: /workspace
  command: ["python3", "-m", "unittest", "-v"]
  debug: true
```

Controller запускает `/usr/local/bin/ax-task-runner`; тот читает `spec.command` и запускает указанную команду дочерним процессом. Поле не заменяет container entrypoint. В этом опыте нет `WorkspaceRef.goal`: agent-assisted bootstrap добавил бы модель и credentials раньше, чем проверен простой checkout. Debug включён ради `ax ssh`; он разрешает гостевые операции и требует отдельного учебного доступа. Ошибки Git в `SetupWorkspace` этого release записываются, но не всегда возвращаются как ошибка runner: даже `WorkspaceReady` нужно сопоставлять с реальными файлами и commit.

В командах явно указан atespace `lab32`: без `-a` CLI по умолчанию ищет объект в `default`, даже если применённый manifest содержал другой atespace. Это отдельная область поиска, а не признак потери Task.

```
ax apply -f lab-task.yaml
ax -a lab32 get tasks
ax -a lab32 describe task lab-task
# Отдельный терминал; после наблюдений завершите Ctrl-C:
ax -a lab32 watch task lab-task
# После проверки готовности в основном терминале:
ax -a lab32 ssh lab-task -- git -C /workspace rev-parse HEAD
ax -a lab32 ssh lab-task -- python3 -m unittest discover -s /workspace -v
ax -a lab32 suspend task lab-task
# Дождитесь фактического завершения suspend через control plane.
ax -a lab32 resume task lab-task
```

Для Git fetch нужен реальный разрешённый сетевой путь. Если исходная policy запрещает его, получите имя созданного Actor из status и назначьте временный узкий allow только к своему Git endpoint по schema работы 9. Ошибку первого clone до выдачи policy сохраните как ожидаемое наблюдение. Затем повторите подготовку новым стартом через разрешённый жизненный цикл. Полная матрица allow/deny выполняется в работе 9; до её завершения ключ модели не выдаётся. Так bootstrap не зависит от уже якобы пройденной последующей работы и не требует открывать всю сеть.

Сравните checkout с записанным input commit. Сохраните вывод тестов и фактический exit code приложения доступным для этого runner способом. Runner остаётся жив после завершения command; phase Task не является результатом unittest. Три ожидаемые ошибки означают, что исходный дефект воспроизведён, а не что платформа исправила программу. Затем через разрешённый debug-доступ создайте в `/workspace` файл-маркер, запишите SHA256 и повторите suspend/resume. Проверьте файл, diff и UID связанного Actor. У Data-восстановления команда может запуститься заново; её побочные эффекты должны быть безопасны для повтора.

В отдельном Task укажите отсутствующую branch. Ищите Git error в runner, проверяйте отсутствие нужного checkout, сравнивайте это с conditions. Замена модели никак не помогает получить отсутствующую ветку. Такая отрицательная проверка особенно полезна из-за поведения `SetupWorkspace`.

После работ 7–8 закрывается только начальный интеграционный допуск: версии и digests записаны; custom image действительно использован; Workspace содержит ожидаемый commit; приложение даёт ожидаемый baseline; suspend/resume сохраняет marker; контрольная ошибка объяснена. Для дальнейших работ дополнительно прочитайте реальные Actor limits и sandbox class, сопоставьте их с ожидаемыми. Поле `Task.resources` само по себе не подтверждает ограничения Actor. Сетевой допуск оформляется следующей работой. Ни RAM приложения, ни история harness, ни уже выполненные внешние операции пока не объявляются восстановленными.

### Lab 9. Egress gateway: отличить запрет от недоступности

Подготовьте два собственных тестовых HTTP/HTTPS endpoint: один будет разрешён, второй останется запрещён. Сначала убедитесь из отдельной доверенной тестовой точки, что оба действительно работают. Иначе отсутствие ответа из Actor ничего не расскажет о policy. В Substrate `df788825` отсутствие egress policy означает deny. Actor name и atespace получите из фактического AX status, не выводите их из имени Task по догадке.

```
kubectl ate get egress-policy <actor-name> -a <atespace> -o yaml
kubectl ate create egress-policy <actor-name> \
  -a <atespace> -f lab-egress-policy.yaml
ax -a lab32 ssh lab-task -- <available-http-client> <allowed-url>
```

Manifest policy готовится по pinned schema Substrate; сохраните его UID/version и правило для конкретного endpoint. Выполните запрос до выдачи allow, после него и после отзыва. Проверяйте запрос из самого Actor: успешный curl с laptop не проверяет его сетевой путь. Для DNS, соединения, TLS и HTTP сохраняйте отдельные наблюдения. Timeout может означать потерянный маршрут или неработающий сервер; отказ policy должен подтверждаться решением gateway и отсутствием запроса в контролируемом приложении в соответствующем окне.

| Probe | Что проверяется |
| --- | --- |
| Разрешённое имя | Работоспособность нужного маршрута |
| Второе имя без allow | Отказ по конкретной policy |
| Прямой IP | Сохранение нужного ограничения при смене способа адресации |
| Redirect на запрещённый endpoint | Проверка нового назначения, если клиент следует redirect |
| Изолированный внутренний mock | Отсутствие доступа к закрытому служебному ресурсу |

Credential injection проверяется отдельным опытом: настройте namespace policy provider и требуемую TLS interception по pinned guide. Разрешённое назначение само по себе не подставляет секрет. Контролируемый сервер может вернуть обезличенный признак получения ожидаемого credential, но не должен печатать его значение. Для отрицательной проверки используйте тестовый mock вместо настоящего cloud metadata endpoint.

Допуск к модельным и многоагентным работам появляется после наблюдаемого allow и deny, проверки runtime/limits и устранения необъяснённых обходов. Разрешение временного Git-доступа для Workspace также входит в эту матрицу. Если для bootstrap пришлось дать широкий доступ, сузьте его и повторите проверку до подключения ключа модели. Сохранённая матрица объясняет и разрешённую возможность, и её границу.

### Lab 10. Модель и harness: проследить один полный цикл

Endpoint отвечает на запрос модели; harness управляет решением прикладной задачи. Он формирует запрос, получает предложение tool call, проверяет параметры и разрешение, вызывает инструмент, возвращает результат модели и выбирает, продолжать ли работу. AX даёт этому процессу среду исполнения. Ресурс AX `Model` не связывает автоматически Task с endpoint: adapter приложения всё равно должен знать model ID, адрес и безопасный credential path.

Для первого цикла попросите агента объяснить, почему `batches([0,1,2,3,4], 2)` теряет запись. Разрешите только tool чтения `batching.py` с ограничением пути и размера ответа. Запись файлов, shell и публикация здесь не нужны. Модель должна запросить файл через tool, получить его содержимое и объяснить дефект. Затем предложите чтение за пределами учебного каталога и проверьте отказ самого adapter. Так видна работа harness, даже если модель убедительно отвечает без инструментов.

Для малого опыта подойдёт простой явный цикл или harness, который уже умеет выбранный API и выдаёт trace переходов. Большой framework оправдан, когда нужны сохраняемые переходы, сложная координация или готовые проверенные adapters. Оценивайте возможность ограничить инструменты, обработать ошибку и остановить цикл; число встроенных интеграций само по себе этого не показывает.

Сначала проверьте прямой запрос из нужного Actor, затем тот же endpoint через harness. Облачный ключ выдавайте через проверенный broker/credential path, без raw upstream key в manifest, env и журнале. Если этого пути нет, используйте локальную ветку работы 11 или mock для проверки логики цикла, явно отделяя её от реальной генерации. Для отдельного исследования платформенного model client потребуется свой `Model.secretKey` и доказательство, какой компонент его читает.

До запуска установите общий deadline, максимум model calls, tool calls, output tokens и небольшой расходный бюджет. Например, три model calls и два чтения файла — учебные границы, не рекомендация для любой задачи. Денежный лимит требует учёта актуальной цены, in-flight запросов и авторитетного usage; локальный счётчик приблизительных tokens не даёт жёсткой гарантии стоимости. Trace должен показать вход → model → tool proposal → решение harness → tool result → итог либо причину остановки.

Двадцать коротких запросов подходят для smoke test: запишите ошибки, input/output tokens, полную latency и TTFT при streaming. Затем mock adapter последовательно возвращает 429, задержку и ошибку аутентификации. Убедитесь, что общий deadline и лимит попыток действительно действуют, а постоянная ошибка не уходит в бесконечный retry. Для операций записи отдельно применяется разбор неоднозначного исхода из главы 31. Итог — воспроизводимый trace и объяснение, кто остановил выполнение и почему.

### Lab 11. CPU inference: найти полезный рабочий диапазон

Локальная CPU-модель полезна, когда важны доступность без GPU, контроль данных или невысокая частота запросов. Вы платите собственными RAM, CPU и временем ответа. Сначала выберите небольшую GGUF-модель с подходящей лицензией, закрепите llama.cpp и checksum файла, затем проверьте сервер локально на отдельном inference host или VM.

```
llama-server -m /srv/models/lab.gguf -c 4096 \
  --host 127.0.0.1 --port 8080
# Другой терминал на том же host:
curl -i http://127.0.0.1:8080/health
curl -sS http://127.0.0.1:8080/v1/models
```

Это стартовая локальная конфигурация; допустимые параметры сверяйте с выбранной версией. Loopback внутри Actor указывает на Actor, не на inference host. Для дальнейшего доступа нужен приватный адрес, аутентификация и разрешённый маршрут из работы 9. Не открывайте сервер всем интерфейсам без этой границы.

Проверьте обычную генерацию, затем tool call того же harness из работы 10. API-совместимость, chat template и способность конкретной модели стабильно выдавать нужный формат — отдельные условия. Если tool call не разбирается, сохраните обезличенный ответ и ошибку parser; смена runtime Actor обычно не устраняет несовпадение формата модели и adapter.

Сначала при concurrency=1 сравните входы около 1k, 2k и 3k tokens с резервом на ответ, оставляя полный запрос в пределах выбранного context. Учитывайте system prompt, описание tools и tokenizer модели. При переходе к concurrency 2/4 отдельно настройте и запишите распределение context по слотам именно этой версии сервера; нельзя считать, что `-c 4096` автоматически даёт каждому параллельному запросу независимые 4096 tokens.

Разделите загрузку модели, первый и прогретые запросы. Измеряйте RAM, CPU, TTFT, output tokens/s, полную latency и ошибки при фиксированном распределении входов. Увеличивайте нагрузку только в заранее ограниченном диапазоне до нарушения выбранного SLO, а затем подтвердите восстановление после её снижения. OOM других VM не является полезной контрольной точкой. Закончите выбором: интерактивный агент, фоновая задача или учебный fallback — с условиями, при которых решение придётся пересмотреть.

### Lab 12. NVIDIA + vLLM + Qwen: измерить насыщение GPU-сервиса

Это необязательная ветка на отдельном доверенном GPU-host. Actor обращается к inference API; GPU не пробрасывается в его gVisor sandbox. Отдельный host упрощает первый опыт, потому что позволяет независимо разбирать ошибки NVIDIA driver/toolkit и работу AX. Если выбираете Kubernetes deployment, дополнительно потребуются device plugin и проверка выделения GPU resources.

Сверьте архитектуру GPU, driver, Container Toolkit и конкретный вариант image vLLM `v0.30.0`. Один release имеет разные сборки; сохраняйте полный image digest. Проверьте GPU сначала на host, затем в тестовом контейнере по руководству NVIDIA. У Qwen закрепите model ID, revision, quantization и лицензию. Память нужна и весам, и KV cache, и служебным данным, поэтому размер файла модели не является достаточным расчётом VRAM.

Шаблон ниже требует подстановки проверенных значений и сверки `vllm serve --help` в выбранном image. Service credential хранится в защищённой конфигурации deployment вне журнала.

```
vllm serve <model-id> \
  --tensor-parallel-size 1 \
  --max-model-len <tested-context> \
  --gpu-memory-utilization <tested-value>
```

Начните с одного запроса и того же tool-call сценария. Затем повышайте concurrency ступенями при неизменном распределении prompt/output. Записывайте очередь, TTFT, inter-token latency, суммарный output throughput, ошибки и доступные метрики памяти/KV cache. До опыта выберите SLO: например, предельные p95 TTFT и долю ошибок. Для каждого окна сохраните размер выборки, длительность, warm-up и метод расчёта; двадцать smoke-запросов недостаточны для надёжного p99.

В точке насыщения throughput ещё может расти, пока отдельный пользователь ждёт слишком долго. Уменьшите допуск одновременных запросов и повторите опыт, сохраняя остальные условия. Если ограничение возвращает очередь в управляемый диапазон, получен полезный capacity limit. Бесконечные retries лишь добавляют нагрузку. Без GPU оформите план измерения и отметку «не запускалось»; для итоговых работ используйте CPU или разрешённый облачный endpoint.

### Lab 13. Software-engineering multi-agent: сравнить пользу и цену

Вернёмся к потере последней пачки. Контракт проекта требует сохранить порядок и все элементы, включая повторы, не изменять входной список и отклонять некорректный size. Дефект намеренно мал: здесь удобно увидеть цену координации. Если один агент решает задачу быстрее при той же проверенной корректности, это разумный выбор архитектуры.

Сохраните исходный commit с тремя ожидаемыми failures. Подготовьте независимые копии из этого commit для single-agent и multi-agent вариантов. Условия model, endpoint, доступных tools и общего бюджета должны быть сопоставимы; бюджет многоагентного варианта суммируется по ролям. Не передавайте второй системе исправление первой или старую историю диалога. При серии опытов чередуйте порядок, чтобы не принять прогрев сервера за выигрыш архитектуры.

Для первого многоагентного варианта хватит Implementer и отдельного Tester/Reviewer под простым Coordinator. Полная схема показывает дальнейшее разделение; добавляйте Researcher, если действительно нужны поиск и анализ зависимостей. Для этого маленького локального проекта сетевое исследование обычно только увеличит цену.

| Роль | Получает и возвращает | Где ограничена |
| --- | --- | --- |
| Coordinator | Задачу, лимиты, ссылки на результаты | Создаёт ограниченное число работ; без merge credential |
| Researcher, если нужен | Вопрос и исходный commit; ссылки на код | Read-only копия, разрешённые источники |
| Implementer | Исходный проект; patch к точному base | Запись только в выделенную копию |
| Tester | Точный patch и контракт; test report | Disposable копия, без публикации |
| Reviewer | Base, diff и отчёт; замечания | Чтение, без write/merge |

В начальный запрос включите контракт, запрет менять поставленные тесты ради зелёного результата и требования к артефактам: base commit, diff, команда теста, exit code, вывод и краткое объяснение причины. После исправления независимый Tester применяет patch к чистой копии и запускает исходные проверки. Полезно добавить случаи неравного деления, списка короче size и входа с повторяющимися значениями. Авторские тесты генератора остаются вне агентского Workspace.

AX Tasks обеспечивают отдельные исполнения, но роли, передачу артефактов и остановку координации реализует harness. Общий writable checkout позволил бы Implementer незаметно менять данные Reviewer. Передавайте immutable diff и отчёты между отдельными копиями. Если Tester обнаружил дефект, Coordinator возвращает конкретное замечание Implementer с тем же общим бюджетом. Повторная проверка создаёт новый отчёт, связанный с новым digest patch.

В disposable README добавьте попытку перенаправить агента: отправить код на запрещённый mock endpoint или выполнить merge. Проверьте отказ adapter/egress и отсутствие записи у контролируемого получателя. Тест не должен содержать настоящий секрет или рабочий URL. Человек просматривает diff и принимает решение о merge в учебный repo; автоматическая публикация не входит в задание.

Сравните итоговую корректность, wall time, tokens/стоимость всех ролей, число итераций и время ручного review. Приведите фактические значения, не обещанный выигрыш. Один дефект и один прогон не позволяют объявить многоагентную систему лучше вообще. Они позволяют увидеть, добавило ли конкретное разделение независимую проверку, оправдывающую его цену.

### Lab 14. Infrastructure multi-agent: разрешить одно ограниченное изменение

Для финального опыта используйте эмулятор либо отдельный тестовый HTTP-сервис. Его frontend обращается к backend на неверный порт 8081, тогда как backend слушает 8080. Сначала подтвердите, что backend исправен, и зафиксируйте текущую config version. Это отделяет ошибку маршрутизации от ошибки самого backend. Диагностические роли получают read-only метрики, сетевые наблюдения и логи за один интервал; Validator сопоставляет target и время.

![Практика: инфраструктурная диагностика с контролируемым изменением](.gitbook/assets/diagrams/32-29.png)  
*Практика: инфраструктурная диагностика с контролируемым изменением*

Planner предлагает изменить только порт backend. Restricted MCP здесь — узкий adapter с одной разрешённой операцией, а не произвольный shell с правами администратора. Сам MCP передаёт вызов; аутентификацию, policy и привязку approval обеспечивает доверенная граница вне sandbox. Для такого малого опыта ручной последовательный workflow часто достаточен. Автоматизация полезна после того, как определены допустимый переход, наблюдения и безопасная остановка.

```
{
  "change_id": "lab32-change-001",
  "target": "test-service/backend",
  "operation": "set_backend_port",
  "arguments": {"port": 8080},
  "expected_version": "config-17",
  "rollback_ref": "lab32-before-change"
}
```

Это учебный формат, не встроенный ресурс AX/MCP. Сохраните исходную конфигурацию. Доверенный executor нормализует запрос, вычисляет digest и проверяет подлинное разрешение с нужными subject, scope, audience, сроком и policy version. Hash связывает параметры, а доверие к согласующему берётся из отдельной аутентификации и policy. Capability ограничивается одной операцией над одним target.

Backend должен условно применить изменение к `config-17` и выдать новую version одной атомарной операцией. Предварительное чтение версии с последующим безусловным write оставляет гонку. Детерминированный тест: после approval другой учебный клиент меняет config; executor получает precondition failure, сохраняет свежую конфигурацию и возвращает задачу на новый разбор. Старое approval не разрешает затереть изменение коллеги.

| Опыт | Ожидаемое наблюдение |
| --- | --- |
| Нет approval | Запись не отправлена; отказ авторизации |
| Port/target изменены после approval | Binding не совпал; запись не отправлена |
| Истёкшее или отозванное разрешение | Новая запись запрещена |
| Другой клиент обновил config | Условная запись отклонена; чужое состояние сохранено |
| Повтор после потери ответа | Сверка receipt/состояния по contract, без слепого второго write |

Для offline-разбора перед работой можно выполнить `python3 examples/ch24_delegated_approval.py` и `python3 examples/ch31_retry_boundaries.py` из корня книги. В первом примере есть смена target, expiry и потерянный ответ; во втором — сохраняемый intent и receipt получателя. Это разные учебные модели: в примере главы 24 replay отклоняется, в примере главы 31 получатель умеет дедупликацию. Они помогают сформулировать тесты adapter, но не заменяют его реализацию и не доказывают distributed exactly-once.

После успешной записи Verification заново читает config и выполняет функциональный HTTP-probe. Receipt «applied» и рабочий сервис — два разных результата. Если новая конфигурация всё ещё не даёт нужного ответа, разрешённый rollback должен учитывать текущую version и иметь явный scope. Не выполняйте безусловную запись старого config поверх последующего изменения другого клиента. При неясном исходе или конфликте остановитесь для разбора; агент не получает новые привилегии ради продолжения.

Результат работы — связанная цепочка evidence → plan → approval → receipt → post-state → функциональная проверка, а для неудачного изменения — предусмотренный rollback либо обоснованная остановка. Из журнала должно быть понятно, кто разрешил действие, почему оно допустимо, что реально изменилось и чем подтверждён итог.

## Как завершить практикум

Перед уборкой предложите коллеге повторить одну работу по вашему журналу без устных подсказок. Если ему неизвестен input commit, он не понимает ожидаемую ошибку или не может отличить модельный ответ от результата инструмента, допишите именно это объяснение. Практикум учит связывать решение с наблюдениями; количество установленных сервисов показывает лишь часть пройденного пути.

| Блок | Что должно остаться |
| --- | --- |
| 1–3: основание | Паспорт VM, восстановление учебной базы, диагностические карточки и путь запроса |
| 4–6: исполнение и состояние | Timeline Actor, проверка snapshot contents, измерения и runtime decision |
| 7–9: интеграция и границы | Протокол пары версий, checkout/checksum, фактические limits/class и allow/deny |
| 10–12: модели | Trace harness, причина остановки, рабочий диапазон выбранного endpoint; статус остальных веток |
| 13–14: прикладной результат | Сравнение с одним агентом и проверяемая цепочка ограниченного изменения |

Сначала сохраните обезличенные отчёты вне удаляемой VM и подготовьте inventory своих Tasks, Actors, Tags, templates, Workspaces, кластера и registry. Сверьте context и владельцев ресурсов. Снимите временный debug/сетевой доступ, остановите port-forwards и отзовите учебные credentials. Затем удаляйте только принадлежащие опыту объекты в порядке зависимостей, проверяя оба control planes. Atespace удаляется после зависимых ресурсов; у tags и snapshots собственный жизненный цикл. Удаление Task не отменяет запись во внешнем сервисе. Общие cluster/registry и чужие данные в эту уборку не входят. Проверьте также внешние GPU-hosts, volumes и платные endpoints, если они создавались.

В главе 33 мы вернёмся к референсным архитектурам. Теперь за каждой стрелкой можно поставить вопрос: каким опытом подтверждена связь, какие данные она переносит и что произойдёт при её отказе. Если часть маршрута остановилась на несовместимости, честный протокол этой границы полезнее схемы, на которой все компоненты изображены работающими.
