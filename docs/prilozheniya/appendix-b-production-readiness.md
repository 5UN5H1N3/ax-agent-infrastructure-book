# Приложение B. Production readiness checklist

На встрече перед выпуском инженер говорит: «Образы закреплены, backup настроен, мониторинг есть». Всё звучит разумно. Но что произойдёт, если backup не читается новой версией, агент повторит запись после timeout, а дежурный увидит только зелёную readiness? Список установленных компонентов не отвечает на эти вопросы.

**Production readiness** - готовность конкретной системы выполнять оговорённую работу с допустимым риском и поддерживаться командой эксплуатации. Это не сертификат продукта навсегда. Решение относится к выбранным images, конфигурации, workload, правам и пределам нагрузки. Изменение tool adapter или policy может потребовать новой проверки, даже если версия AX осталась прежней.

Глава 43 описала испытания и действия оператора, приложение A - границы выводов из документации и кода. Здесь соберём 25 критериев, по которым команда принимает решение о допуске. Идентификаторы `P1`, `S1` и другие нужны для связи с отчётами, а не являются полями AX API. Проверки адаптируются к вашей установке; исполнение security policy, budgets и recovery gates нельзя считать встроенным в AX только потому, что они включены в checklist.

## B.1 Область допуска и запись результата

Начните с пользовательского контракта: какие задачи агент решает, какие данные читает, что может менять и сколько пользователь вправе ждать. Read-only помощник по внутренней документации и исполнитель изменений в инфраструктуре имеют разные последствия ошибки. Для второго понадобятся дополнительные проверки approval, внешнего outcome и восстановления; хорошие результаты первого не переносятся на него автоматически.

Задайте обязательные критерии до прогона. У каждого должен быть владелец проверки и человек, принимающий итоговый риск; в небольшой команде роли могут совпадать. Разделите обязательные запреты и цели качества. Нельзя усреднить несанкционированный write с сотней успешных reads и назвать систему достаточно хорошей.

| Поле записи | Что зафиксировать |
| --- | --- |
| Область | Workload, tenant profile, доступные tools, пределы traffic и mutations |
| Identity | Image digests, commits, model и adapter versions, policy и config revisions |
| Критерий | ID, обязательность, точное ожидаемое поведение и допустимый предел |
| Условия | Fixture, среда, prerequisites, разрешённое воздействие и stop condition |
| Результат | Фактическое поведение, статус, timestamps и ссылки на evidence без secrets |
| Ответственность | Владелец, решение о допуске, ограничения и условия повторной проверки |

**Evidence** - проверяемые свидетельства: отчёт теста, relevant logs, измерение, receipt и сверка состояния конечной системы. Screenshot dashboard полезен, но обычно не содержит всех условий опыта. Другая команда должна понимать, что проверили, и иметь доступ к нужным свидетельствам; чувствительные материалы хранятся отдельно.

| Статус | Смысл | Последствие для обязательного критерия |
| --- | --- | --- |
| `PASS` | Ожидание подтверждено в записанных условиях | Закрывает только этот критерий и эту область |
| `FAIL` | Наблюдаемое поведение нарушает критерий | Допуск закрыт до исправления и повторного прогона |
| `BLOCKED` | Не хватает prerequisite или пригодного evidence | Допуск закрыт; отсутствие результата не является успехом |
| `SKIPPED` | Проверка не выполнялась; причина записана | Допуск закрыт, пока критерий остаётся обязательным |

Неприменимость определяют по контракту и согласуют до допуска, а не после неудобного результата. Например, отсутствие write tools позволяет исключить испытание их effect, но не проверки read authorization. В отчёте сохраните обоснование исключения. Такой подход согласуется с [практикой launch checklist Google SRE](https://sre.google/sre-book/reliable-product-launches/): конкретные вопросы и действия подбираются под запуск, а не разрастаются в одинаковую церемонию для всех систем.

## B.2 Платформа и доступность зависимостей

**P1. Запущена именно проверенная сборка.** Сопоставьте фактические digests control plane, runner и sandbox с release inventory. Закрепите Git revisions Workspace, model artifacts и adapters; сохраните provenance сборки. Tag удобен человеку, digest определяет image bytes, а commit связывает их с исходниками. Один tag не заменяет проверку запущенного artifact. Если runtime требует доступного image после relocation, проверьте и возможность получить его из registry.

**P2. Работает выбранная комбинация компонентов.** Пройдите create, setup, model request, нужный MCP read, suspend/resume и завершение test command на используемых sandbox classes. Сверьте API и protocol revisions, optional features и schemas. В отчёт попадёт результат приложения, не только HTTP 200. Для AX `ac233282` direct reconciliation и readiness default runner имеют границы из приложения A; не ищите доказательство успеха в несуществующей controller queue.

**P3. Нагрузка укладывается в измеренный запас.** Испытайте штатный workload, burst и предусмотренный отказ части Workers или inference capacity. Headroom - запас относительно измеренной рабочей нагрузки, а не произвольный процент свободного CPU. Укажите hardware, active и idle Actors, concurrency, длины контекста, storage latency и предел ожидания пользователя. Под перегрузкой система должна ограничивать admission и retries по выбранному контракту, а не бесконечно накапливать работу. Порог выводится из главы 41 и ваших измерений.

**P4. Отказ зависимости имеет ограниченный эффект.** На стенде проверьте недоступность DNS, registry, model/tool endpoint и используемых Redis/PostgreSQL или object storage. Для каждого случая нужен понятный error path, предел ожидания и безопасное возвращение после восстановления. Доказательство - timeline и outcome test Task, а не только alert об отключённом сервисе. Особое внимание cold start и restore: работающий cache способен скрыть недоступность registry или payload, которая проявится лишь на новом Worker.

Все fault tests выполняются в согласованной lab области с synthetic данными. Перечисление отказов здесь не является предложением отключать production store. Если стенд не воспроизводит важный failure domain, ограничьте вывод и оставьте соответствующий критерий открытым.

## B.3 Границы доступа и доверие к инструментам

**S1. Control plane недоступен посторонним и лишним identities.** Проверьте реальные AX/Substrate endpoints, administrative API, databases и runner metadata path с разрешённой и запрещённой identity. Сетевой perimeter, authentication и authorization отвечают на разные вопросы: можно ли подключиться, кто вызывает и что ему разрешено. Внешний proxy защищает только путь через него; прямой endpoint не должен обходить проверку. Threat model не заменяет реализацию разграничения доступа в конкретной версии.

**S2. Egress ограничивает фактический sandbox path.** Неоговорённые destinations запрещены по умолчанию; разрешения перечислены явно, а широкое исключение имеет владельца, обоснование и срок. Разрешённый canary destination доступен, запрещённый получает ожидаемый отказ; прямой путь и альтернативный proxy не обходят ограничение. Проверьте свежий request, уже открытое соединение и resume после смены policy по главе 40. В [Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/) наличие объекта без поддерживающего network plugin не обеспечивает enforcement; базовый механизм работает на IP/port уровне и не заменяет прикладную authorization. Не принимайте allowlist Worker Pod за автоматически доказанную границу каждого Actor.

**S3. Sandbox и tenant isolation соответствуют угрозе.** Зафиксируйте, от какого недоверенного кода и каких переходов между tenants защищает выбранный backend. Проверьте запрет чужих objects, snapshots и credentials, а также допустимый контрольный read. Namespace или UID в storage prefix не является достаточным доказательством. gVisor, microVM и обычный container выбирают по границе доверия, совместимости и цене эксплуатации из главы 8, а не только по скорости старта. Privileged escape tests требуют отдельной методики; обычный deny test не доказывает отсутствие всех escapes.

**S4. Credentials ограничены и действительно отзываются.** У каждого доступа известны issuer, holder, audience, scope, срок и refresh/revoke path. Проверьте rotation, отказ старому canary credential и поведение после restore с его сохранённой копией. [Kubernetes Secret](https://kubernetes.io/docs/concepts/configuration/secret/) не означает автоматическую encryption at rest или отсутствие транзитивного доступа через создание Pod. Следуйте главе 42: обновление secret store и прекращение действия всех старых копий - разные результаты. Evidence не должно содержать сами tokens.

**S5. Tools, skills и writes проходят разные проверки.** Закрепите происхождение и версии MCP servers, skills и repositories. Review доверенного server не разрешает ему любое действие от любого tenant. Schema validation проверяет форму arguments; authorization - право на target; approval - согласие на точное high-risk действие. Испытайте denied write и approved write на test object, сверьте binding approval и внешний effect. Если изменилась цель или arguments, прежнее approval не должно молча разрешать новую операцию.

**S6. Debug доступ и audit не подконтрольны workload.** В штатном profile нет неоговорённого SSH/debug входа. Break-glass имеет владельца, purpose, срок, audit и проверяемое закрытие. Workload может отправлять собственные logs, но не должен менять или удалять независимую историю решений, credentials issuance и tool outcomes. Для audit backend проверьте permissions, retention и доступ расследователя. Недоступность audit delivery требует явной политики для high-risk действий; отсутствие записи нельзя выдавать за отсутствие события.

Отрицательная проверка проходит, когда запрет сработал на нужной границе и запрещённого effect нет. Общий timeout не доказывает deny: возможно, endpoint был недоступен всем. Контрольный allowed path и независимая сверка test object делают результат различающим.

## B.4 Harness и контракт полезной работы

**Harness** - прикладная управляющая оболочка агента: она организует цикл model/tool calls, хранит progress, ограничивает действия и определяет, когда работа завершена. Платформа предоставляет место исполнения и lifecycle, но не знает сама, решена ли пользовательская задача. Поэтому criteria этого раздела принадлежат вашей реализации harness и adapters, а не одному факту запуска AX Task. Подробная модель дана в главе 4.

**H1. Бюджеты ограничивают всю работу.** Задайте steps, model tokens, tool attempts, wall time, стоимость и допустимое число/depth child tasks. Испытайте превышение каждого существенного лимита и отмену parent. Продолжительность штатного ожидания approval определите отдельно, но не позволяйте ему удерживать ресурсы без срока. Суммарный budget должен учитывать descendants и retries; лимит только одного model request не ограничивает бесконечный loop. Результат проверки - остановка или контролируемое ожидание, а не строка о лимите в prompt.

**H2. Запуск и завершение имеют прикладной результат.** После Workspace setup harness проверяет необходимые tools, credentials и входные данные. Success определяется проверяемым результатом: корректным artifact, допустимым ответом или подтверждённым effect. Прогоните успешный case, ошибку child command и штатное ожидание approval. Они должны иметь разные outcomes. У [default runner этого среза](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/runner/runner.go) readiness не является источником истины о результате задачи; живой runner после выхода command полезен для inspection, но не доказывает прогресс.

**H3. Tool errors не превращаются в бесконечные retries.** Проверьте malformed input/result, schema mismatch, authorization deny, rate limit и transport timeout. Adapter различает причины, а harness применяет ограниченную стратегию: исправление input, разрешённый refresh, ожидание или остановку. Deny нельзя обходить выбором другого tool или новым approval без проверки причины. Backoff без общего attempt/time budget лишь растягивает бесконечную работу.

**H4. Неизвестный outcome удерживает write gate закрытым.** В lab потеряйте receipt synthetic write после подтверждённого effect. Stable operation ID, прежний idempotency key и lookup у конечной системы должны позволить установить результат без второго logical effect. Проверьте также недоступный lookup: high-risk действие остаётся `OUTCOME_UNKNOWN`, а не повторяется с новым ID. Retention и scope deduplication provider должны покрывать вашу recovery window; exactly-once не появляется от наличия поля key.

**H5. Durable progress достаточен для продолжения.** Восстановите harness после потери процесса и из более раннего checkpoint. Проверьте текущий шаг, versions/schema state, незавершённые operations и актуальные права. Prompt, RAM и container files, не вошедшие в recovery contract, не заменяют durable checkpoint. Изменение model, tools или контекста может повлиять на качество даже при успешном restore. Для выбранной задачи нужен фиксированный eval набор с критериями correctness и safety, а не ожидание идентичных tokens от каждого прогона.

## B.5 Восстановление данных и внешней истории

**R1. Backup возвращает согласованный набор зависимостей.** Составьте inventory resource records, Actor/Tag metadata, Workspace payload, snapshots, keys, policy и operation ledger. Проверьте integrity, references и retention, включая borrowed и golden dependencies из главы 39. Ваша схема хранения может отличаться от учебной; берите реально используемые Redis/PostgreSQL и object store. Успешный backup job подтверждает выполнение job, но не читаемость полного recovery point.

**R2. Restore работает из чистой среды и укладывается в цели.** Другой оператор по runbook получает artifacts и нужные key versions, восстанавливает stores/payloads и доводит test workload до полезного результата. Задайте **RPO** - допустимое окно потери данных перед отказом - и **RTO** - предельно допустимое время от нарушения сервиса до его оговорённого восстановления. Это цели, а не названия фактических результатов; различие поясняет [AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_planning_for_recovery_objective_defined_recovery.html). Затем измерьте потерю состояния и время полезного восстановления, сравните их с целями. Например, metadata с отставанием в минуту не закрывает RPO в пять минут, если нужный application checkpoint старше на час. Заранее задайте границы измерения и класс отказа; загрузка PostgreSQL не завершает восстановление, если harness ещё не допущен к работе.

**R3. Возвращение исполнителей не возвращает старые права и двойные effects.** Пройдите gates главы 42: fencing старых writers, изолированный restore, проверка mappings и актуальных прав, reconciliation внешних операций, ограниченный допуск. Fencing означает доказанное лишение прежнего исполнителя возможности писать, а не только смену DNS. Отдельно испытайте restore до receipt, stale credential и недоступный dependency. Full snapshot не гарантирует валидный доступ сегодня, Data snapshot не обещает восстановление прежней RAM.

H4 проверяет логику действия, R3 - её сохранность через восстановление всей системы. Один общий тест может дать evidence обоим критериям, если отчёт явно подтверждает каждый. Это позволяет не дублировать работу, не теряя важных границ проверки.

## B.6 Наблюдаемость и готовность дежурного

**O1. Историю можно собрать по logical run.** Свяжите user/job, Task incarnation, Actor UID, Worker assignments, model requests и logical tool operations. Trace, logs и ledger дополняют друг друга: sampling span не должен уничтожать единственный receipt важного write. После relocation найдите события до и после переноса в центральном backend. В [Substrate v0.3.0 attribution](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/docs/observability.md) помогает найти workload, но сохранность истории и прикладной context требуют своей интеграции.

**O2. Измеряются пользовательский результат и причины задержки.** Выберите SLI - измерение полезной работы, и SLO - согласованную цель для него. Например, это доля корректно завершённых задач в пределах их срока; отдельно учитывайте штатное ожидание approval. Для диагностики собирайте model queue, TTFT, ITL и KV pressure, setup/resume time, storage/tool latency и ошибки. Не смешивайте inference queue с удалённой AX controller queue. Запишите blind spots и альтернативные probes: отсутствие store metric не делает store исправным.

**O3. Alert приводит к проверяемому действию.** На согласованном synthetic сбое подтвердите detection, доставку notification, обращение дежурного к runbook и восстановление результата. Зафиксируйте escalation и предел времени реакции; alarm только о CPU может не увидеть корректно работающий процесс с бесполезным loop. Сам monitoring path тоже имеет владельца и контроль доставки. Тихий dashboard без test event не доказывает, что alerts работают.

**O4. Операторы имеют доступ, но evidence не раскрывает secrets.** Проверьте поиск нужных logs и receipt другим инженером, доступ к runbook при отказе основной площадки и redaction с сохранением IDs/timestamps. Срок хранения должен покрывать расследование, recovery window и внешние обязательства вашей системы. Snapshot RAM, полный environment и authorization headers не прикладываются к общему ticket. При ограниченном доступе оставляйте защищённую ссылку, а не чувствительные bytes в report.

## B.7 Решение о выпуске и повторная проверка

**G1. Отчёт закрывает обязательные критерии.** Проверьте полноту cases, свежесть evidence и соответствие фактическому candidate. Для каждого обязательного ID нужен `PASS`; failures и отсутствующие prerequisites сохраняются, а не исчезают из summary. Изменились sandbox, tool permissions, snapshot format или model profile - пересмотрите затронутые критерии и повторите соответствующие cases. Ручное исключение имеет отдельное решение владельца риска, срок и предел rollout; оно не переименовывает `FAIL` в `PASS`.

**G2. Canary репрезентативна и имеет stop conditions.** Сравните ограниченную candidate группу с control по одинаковым workload classes; примените также абсолютные SLO. Окно должно охватывать meaningful work и нужные переходы состояния. [Google SRE Workbook](https://sre.google/workbook/canarying-releases/) отмечает для неинтерактивных систем зависимость наблюдения от длительности work unit и опасность смешивания сигналов. Для agents учтите shared stores, tool accounts и ожидание approval. Не зеркалируйте реальный write двум версиям ради сравнения; shadow evaluation использует read-only fixtures или simulator.

**G3. Rollback и эксплуатационная передача выполнимы.** Испытайте чтение state старой сборкой после candidate и выбранную обратную migration. Если обратного пути нет, согласуйте и проверьте forward recovery до rollout. Rollback binary не отменяет external effect. Назначьте владельца stop/rollback решения, подготовьте inventory, runbook и handoff дежурному. Выпуск без команды, способной ограничить ущерб и восстановить полезную работу, остаётся незавершённым даже при зелёных тестах.

> **Учебная запись H4.** Контракт: после потери receipt повтор одного logical write не создаёт второй effect. Наблюдение в synthetic fixture: endpoint подтвердил два отдельных изменения. Статус: `FAIL`. Решение: write path к выпуску не допускается; owner исправляет adapter и повторяет тест с проверкой конечного объекта. Это пример оценки, а не результат проверки какого-либо реального deployment.

Ограниченный read-only запуск иногда позволяет получить пользу до готовности mutation path. Но это другой явно заданный контракт: write credentials отсутствуют или права надёжно запрещены, UI и tools не обещают неподдерживаемое действие, а соответствующие gates пересмотрены. Называть тот же опасный deployment «пилотом» без изменения границ недостаточно.

## B.8 Практикум принятия решения о допуске

Используйте отдельный lab tenant, synthetic fixtures и tool simulator с независимым счётчиком effects. Fault injection и restore разрешены только внутри заранее согласованной области. Цель - получить маленький, но честный readiness record, который другой инженер сможет проверить.

1. **Задайте область.** Выберите один workflow, доступные операции, limits и проверяемый пользовательский outcome. Назначьте владельцев и обязательные IDs; запишите неприменимые критерии с причиной.
2. **Соберите identity.** Зафиксируйте фактические digests и revisions, fixture и policy. Подготовьте allowed control и ожидаемые отрицательные результаты без production credentials.
3. **Пройдите полезный путь.** Подтвердите application outcome и отличите его от readiness. Затем воспроизведите child error, budget exhaustion и штатное ожидание approval.
4. **Проверьте запреты и uncertain outcome.** Denied write не меняет объект; approved test write имеет проверенный effect. После потери receipt lookup восстанавливает результат без повтора, а недоступный lookup оставляет gate закрытым.
5. **Восстановите историю.** Из чистой operator среды верните выбранный checkpoint и dependencies. Проверьте stale access, отсутствие второго writer и logs после lab relocation; измерьте полезное восстановление.
6. **Составьте отчёт.** Поставьте статус каждому обязательному критерию. Намеренно оставьте один prerequisite недоступным и убедитесь, что отчёт показывает `BLOCKED`, а итоговый gate не становится зелёным.
7. **Передайте решение.** Другой оператор проверяет evidence и объясняет go/no-go без устных подсказок. После исправления повторите затронутые tests, обновите record и только затем пересмотрите допуск.

Готовность подтверждает не число галочек, а ясность границ: что системе разрешено, что испытано, как она ограничивает отказ и кто отвечает за следующий шаг. Приложение C поможет находить первичные источники для этих проверок; версии и ссылки служат опорой, но решение всегда относится к вашему проверенному deployment.
