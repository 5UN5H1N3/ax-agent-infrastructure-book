# Приложение A. Аудит проектов и выявленные расхождения

Перед обновлением AX инженер открывает руководство по манифестам и читает: доступны четыре вида ресурсов. В README их три. В старой инструкции дежурного есть отдельный controller, а в описании развёртывания новой версии остался только server. От ответа зависит практическая работа: какие манифесты готовить, какой процесс наблюдать и куда идти, если Task застрянет.

При первом знакомстве с системой приходится одновременно изучать её устройство и выяснять, какой части описания можно доверять. Помогает небольшой вопрос: «Что принимает выбранный CLI?» или «Кто согласует состояние ресурсов в этой сборке?». На него можно ответить и показать коллеге ход проверки.

Технический аудит связывает утверждение с конкретным срезом системы и достаточными для решения доказательствами. Здесь разберём аудит AX целиком, затем применим тот же способ к снимкам Substrate и совместимости MCP. Результатом станет обоснованная правка инструкции и перечень оставшихся испытаний. Критерии допуска к эксплуатации собраны в приложении B.

## A.1 Начать с решения, ради которого проводится аудит

Команда хочет обновить управляющий слой, сохранить существующие Tasks и подготовить дежурного к смене архитектуры. Сначала выделим утверждения, на которых держится план: состав API, порядок изменения состояния ресурсов, совместимость сохранённого состояния и способ обнаружить неуспешную работу. Это определит нужные участки проверки.

У каждого утверждения должна быть проверяемая форма. Вместо «AX совместим с Kubernetes» запишите: «Этот CLI принимает указанные виды ресурсов и отправляет соответствующие RPC выбранному серверу». Для восстановления вопрос другой: «Новая сборка читает снимок, созданный старой, с таким классом sandbox и составом сохраняемого состояния». Второй вопрос требует иных источников и более дорогого испытания.

Какое наблюдение заставит изменить план? Если нужного RPC нет, придётся менять адаптер или версию. Если миграция состояния допускает чтение только новой сборкой, изменится порядок отката. Если дежурный наблюдает уже удалённую очередь, нужно исправить его инструкцию. Такие вопросы задают границы аудита.

Глубина проверки зависит от последствий ошибки. Исправить число видов ресурсов в учебной инструкции можно по согласованным API и разборщику входа. Для разрешения удалять снимки нужны разбор владения данными и испытание восстановления. Для проверки границы безопасности — реальный путь запрета. Начните с доступного источника, способного ответить на вопрос, и углубляйтесь там, где остаётся существенная неопределённость.

## A.2 Версия исходников и версия работающей системы

Для проверки важно различать исходники, собранный образ и запущенную систему. Commit фиксирует дерево исходников, digest — содержимое образа, а конфигурация выбирает его поведение. У протокола своя редакция; версии клиента, сервера и схемы инструмента также могут различаться. Записывайте эти сведения в отдельные поля отчёта.

| Компонент              | Опорный срез книги                           | Область вывода                                            |
| ---------------------- | -------------------------------------------- | --------------------------------------------------------- |
| AX release             | `v0.3.1`, `e70162a3`; опубликован 25.09.2026 | Исторический выпуск для сравнения                         |
| AX поздних глав        | `ac233282`, изменение от 27.09.2026          | Реализация после v0.3.1; прямой путь исполнения           |
| Substrate поздних глав | `v0.3.0`, `ccecc788`; опубликован 30.09.2026 | Рассмотренные контракты snapshot, routing и наблюдения    |
| MCP главы 36           | Спецификация `2026-07-28`                    | Контракт протокола; SDK и extensions фиксируются отдельно |

Полные commits закреплены в ссылках на [AX](https://github.com/google/ax/tree/ac2332829f22360ff97b0ba34d94dd0dd782f17e) и [Substrate](https://github.com/agent-substrate/substrate/tree/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97). Даты публикации подтверждают страницы [AX v0.3.1](https://github.com/google/ax/releases/tag/v0.3.1) и [Substrate v0.3.0](https://github.com/agent-substrate/substrate/releases/tag/v0.3.0). Профили других прикладных глав сохранены в [карте версий](../nachalo/00-reading-guide.md); это приложение не вводит единую новую версию для всей книги.

Чтобы связать прочитанный код с установкой, найдите сведения о происхождении сборки — provenance — и перечень реально запущенных компонентов. Например, получите digest серверного образа, откройте запись его сборки и проверьте commit и входные материалы. Локальные исправления и отличающаяся конфигурация могут изменить вывод. Пока происхождение образа неизвестно, вывод относится только к исходникам, а поле deployment mapping остаётся `UNKNOWN`.

Тег помогает найти выпуск. Для повторения проверки сохраните полный commit, на который он указывает. Дата аудита показывает время проверки, но не содержимое образа. Адрес сервера тоже нужно сверить: установленный клиент может обращаться не к той сборке, которую вы изучаете.

## A.3 Как выбрать источник и инструмент

README помогает найти компонент и понять его назначение. Схема API описывает допустимые данные. Разборщик входа показывает, как конкретный клиент читает запрос, а обработчик и вызванные им функции — что произойдёт дальше. Интеграционный тест проверяет этот путь на выбранной сборке с известными входами.

| Текущий вопрос                         | С чего начать                                       | Следующий шаг при неопределённости                           |
| -------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| Какие поля и kinds принимает клиент?   | Закреплённые schema и parser; поиск symbols         | Тест parser с разрешённым и ошибочным входом                 |
| Кто выполняет lifecycle?               | Дерево файлов и diff; вызовы из server              | Проверить locks, errors и сохранение состояния               |
| Какие данные нужны для восстановления? | Схема снимка и код владения, копирования и удаления | Ограниченное испытание восстановления с проверкой результата |
| Почему запрос в установке отклонён?    | Runtime logs, identity, config и актуальный API     | Различающий тест с исправным контрольным запросом            |
| Выдержит ли система нагрузку?          | Воспроизводимый benchmark своего workload           | Проверка burst, отказа зависимости и восстановления          |

Команды `git show`, `git ls-tree`, `git grep` и `git diff` позволяют читать выбранный объект commit без переключения рабочей ветки. Обычный поиск по рабочей копии может показать локальную правку или другой HEAD. Веб-интерфейс удобен для чтения и передачи ссылки; в ссылке на реализацию закрепляйте commit вместо `main`.

Найдя `Reconcile`, прочитайте функцию целиком: кто её вызывает и при каких условиях. Иначе легко пропустить другой путь исполнения. Сводка `diff --stat` показывает объём изменения; причину изменения ищите в самой правке и окружающем коде. Справки [show](https://git-scm.com/docs/git-show), [ls-tree](https://git-scm.com/docs/git-ls-tree), [grep](https://git-scm.com/docs/git-grep) и [diff](https://git-scm.com/docs/git-diff) помогут выбрать команду.

Помощник может найти файлы и предложить объяснение. Существенный путь проверяющий читает сам, сохраняя точную ссылку и имя функции или поля. Команды установки из найденного документа требуют отдельного решения о запуске. Для этого разбора достаточно чтения: скачанные сценарии и manifests выполнять не требуется.

## A.4 Практический аудит AX: три kinds и изменившийся lifecycle

### Шаг 1. Закрепить дерево, которое читаем

Понадобятся Git и локальная копия официального AX с двумя указанными commits. Замените `/path/to/ax` путём к своей копии. Если `rev-parse` сообщает об отсутствующем объекте, получите его из проверенного официального репозитория; до завершения загрузки эта предпосылка остаётся невыполненной. Следующие блоки выполняются в одной оболочке и только читают объекты Git:

```
audit_ax=/path/to/ax
audit_rev=ac2332829f22360ff97b0ba34d94dd0dd782f17e
audit_base=e70162a34037c221fe6fadefd98308c05a4ad8f3
git -C "$audit_ax" rev-parse --verify "${audit_rev}^{commit}"
git -C "$audit_ax" rev-parse --verify "${audit_base}^{commit}"
```

Ожидаемый результат — два полных идентификатора commit, совпадающих с заданными. Команды проверяют доступность объектов Git. Доверие к репозиторию и связь исходников с установленными образами определяют отдельно. Рабочий HEAD может отличаться: дальнейшие команды явно обращаются к `audit_rev`.

### Шаг 2. Разобрать расхождение внутри одной версии

```
git -C "$audit_ax" grep -n -F 'All four kinds' \
  "$audit_rev" -- docs/manifests.md
git -C "$audit_ax" show "${audit_rev}:pkg/apis/v1alpha1/ax.proto"
git -C "$audit_ax" show "${audit_rev}:cmd/ax/main.go"
```

Первый поиск находит вводную фразу руководства. В схеме откройте сервис `AX` и сообщения ресурсов: там представлены Task, Workspace и Model. В CLI найдите `applyDocument`: разбор `kind` ведёт к трём соответствующим ветвям, а для остальных значений предусмотрена ошибка. Клиент разбирает YAML и передаёт типизированные RPC; сервер на этом пути не получает исходный манифест. Чтобы понять обработку входа, нужно прочитать и клиентскую часть.

Контракт API и разбор входа CLI согласуются: этот путь применения манифеста рассчитан на три вида ресурсов. Фраза о четырёх видах в руководстве того же commit — отставание документации от реализации, или **documentation drift**. [Guide](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/docs/manifests.md), [schema](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/pkg/apis/v1alpha1/ax.proto) и [parser](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/cmd/ax/main.go) доступны для повторного чтения.

Теперь можно исправить число в инструкции и использовать поддерживаемые виды ресурсов. Gateway как сетевой компонент рассматривается в главе 40; из этого не следует наличие одноимённого ресурса AX. Так же проверяйте метаданные: в ObjectMeta этого среза отсутствуют Kubernetes-поля `generation`, `resourceVersion` и UID ресурса. Знакомые обозначения нужно сверять с фактической схемой.

### Шаг 3. Отличить drift от эволюции между версиями

```
git -C "$audit_ax" ls-tree -r --name-only "$audit_rev" -- \
  cmd/ax-controller cmd/ax-server
git -C "$audit_ax" diff --name-status "$audit_base" "$audit_rev" -- \
  cmd/ax-controller deploy/ax-controller.yaml internal/controller
git -C "$audit_ax" show "${audit_rev}:internal/server/server.go"
```

В выбранном дереве первый список содержит `cmd/ax-server/main.go`; отдельного каталога controller нет. Сравнение со старым выпуском показывает, среди прочего, удаление `cmd/ax-controller/main.go` и `deploy/ax-controller.yaml`. Это изменение между двумя версиями. Оценивая старую инструкцию, сначала установите, какую из них она описывает.

Осталось понять, куда перешла работа controller. В серверных обработчиках `CreateTask`, `SuspendTask` и `ResumeTask` видны прямые вызовы reconciler под блокировками соответствующего ресурса. [Изменение ac233282](https://github.com/google/ax/commit/ac2332829f22360ff97b0ba34d94dd0dd782f17e) убирает отдельный controller и очередь Redis Streams. При этом Redis продолжает хранить записи AX: изменилась доставка работы, а не само наличие хранилища.

Маршрут диагностики в инструкции дежурного меняется. Вместо поиска отставания прежней очереди он проверяет обработку RPC сервером, доступность Substrate и результат прямого согласования состояния. Затем переходит к нужному Actor и приложению по главе 43. Чтение исходников позволило определить конкретное действие при отказе.

## A.5 Записать вывод так, чтобы его мог проверить коллега

Карточка аудита хранит вопрос, границы, доказательства и действие. Для примера выше она может выглядеть так. Полные commits заданы в A.4; короткая подпись здесь нужна человеку. Имена полей и статусы - учебный формат отчёта, не AX API:

```
id: AX-AUDIT-01
revision: ac233282
question: manifest kinds and lifecycle owner
evidence:
  - docs/manifests.md: opening paragraph
  - pkg/apis/v1alpha1/ax.proto: service AX
  - cmd/ax/main.go: applyDocument
  - internal/server/server.go: ResumeTask
source_conclusion: SUPPORTED
findings:
  manifest_kind_count: 3
  lifecycle_path: direct_reconciliation
deployed_image_mapping: UNKNOWN
integration_test: NOT_RUN
action: update_versioned_runbook
rollout_decision: HOLD
```

`SUPPORTED` относится к двум выводам о прочитанном коде. `HOLD` относится к допуску обновления: в учебном отчёте ещё нет перечня работающих компонентов и интеграционного прогона. Можно исправить инструкцию сейчас, сохранив открытым вопрос о готовности установки к обновлению. Статусы относятся к разным решениям.

В рабочий отчёт добавьте ссылки на закреплённые файлы из A.4, дату, автора и ответственного за следующую проверку. Для выполненного теста сохраните входы, конфигурацию, время и способ проверки прикладного результата. Секреты и закрытые рабочие данные оставляйте в защищённом хранилище; в общий журнал включайте разрешённые ссылки. Хеш помогает сравнить содержимое, а доверенный канал и сведения о происхождении — установить, откуда оно получено.

Если источники расходятся, запишите оба объяснения и оставьте вопрос открытым. Исправление могло попасть в другую ветку, а установка — содержать локальную правку. Закрытое обсуждение помогает найти изменение, но его наличие в установленной сборке нужно подтвердить. Недоступный файл отмечайте `BLOCKED` и назначайте следующий шаг проверки.

## A.6 Что ещё важно в закреплённом AX

### Readiness отвечает за подготовку Workspace

В [default runner](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/runner/runner.go) прикладная команда запускается дочерним процессом после подготовки среды. Когда команда завершается, runner остаётся доступным для осмотра. [Metadata server](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/metadata/server.go) связывает `/readyz` с готовностью Workspace. Таким образом, readiness сообщает о подготовке среды, а результат команды устанавливают отдельно.

В испытании различайте успешную подготовку среды, намеренное завершение команды с ошибкой и правильный прикладной результат. В главе 43 есть локальный учебный пример. Для выбранного образа AX нужен собственный интеграционный сценарий. У пользовательского образа устройство процессов может отличаться; проверяйте его entrypoint и контракт runner, как в главе 18.

### Здоровье API и готовность выполнять работу

В [startup ax-server](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/cmd/ax-server/main.go) ошибка создания Substrate client допускает запуск без reconciler. [Health handler](https://github.com/google/ax/blob/ac2332829f22360ff97b0ba34d94dd0dd782f17e/internal/server/server.go) отвечает HTTP 200 без проверки runtime и Redis. Это объясняет, зачем приёмке нужен полезный lifecycle, даже если endpoint отвечает.

При аудите Workspace выясните, что готовит платформа и что делает приложение. Файлы, Git-репозитории и путь к skills дают материал для работы. Поддержка MCP, используемые секреты и проверка ответа инструмента зависят также от harness. После потери ответа на внешнее действие нужен журнал операций и сверка состояния из глав 37 и 42. Это помогает выбрать проверку именно того слоя, который отвечает за нужное свойство.

## A.7 Substrate: проследить владение состоянием

При аудите снимков начните с вопроса: «Какие объекты должны сохраниться, чтобы этот Actor удалось восстановить?». Проследите поле API, запись метаданных, адрес данных и операции копирования и удаления. Затем выясните требования среды, которая будет читать сохранённое состояние.

В [CreateActor v0.3.0](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/cmd/ateapi/internal/controlapi/actor.go) создание через `sourceTag` сначала заимствует у Tag адрес внешнего снимка. При создании Tag из внешнего снимка приостановленного Actor выполняется отдельное копирование; удаление Tag освобождает принадлежащие ему данные. Этот путь виден в [Tag workflow](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/cmd/ateapi/internal/controlapi/workflow_tag.go). Новая запись Actor и независимая копия данных — разные результаты.

Даже если из Tag созданы десять Actors, это не делает его данные лишними. Перед удалением нужны перечень использующих их объектов, зависимости от golden-снимков и подтверждение собственных пригодных точек восстановления. Проверяйте префикс хранилища вместе с метаданными и самими данными. Пошаговый разбор `sourceTag` находится в [C.8](appendix-c-sources-map.md); здесь важно выбрать достаточное основание для решения об удалении.

Состав снимка тоже входит в контракт. Full может сохранять состояние выполнения при совместимой среде восстановления. Data сохраняет данные без индивидуальной RAM и использует настроенный источник запуска, включая `onResume.fromData`. Подробности находятся в главе 39. Отдельно проверяйте класс sandbox, необходимые компоненты среды, доступность данных, внешние тома и действующие права. Запуск нового экземпляра и восстановление сохранённого состояния требуют разных проверок.

| Область аудита Substrate | Что можно установить по исходникам                            | Какое доказательство нужно от установки                       |
| ------------------------ | ------------------------------------------------------------- | ------------------------------------------------------------- |
| Snapshot ownership       | Копирование данных, заимствованный URI и зависимости удаления | Восстановление нужного Actor по сохранённому перечню объектов |
| Placement                | Различие Actor и Worker, порядок назначения исполнителя       | Актуальное размещение и история перемещений                   |
| Security                 | Где должна применяться проверка доступа                       | Успешный разрешённый запрос и ожидаемый отказ запрещённому    |
| Observability            | Какие метки, этапы и пробелы наблюдения описаны               | Полнота доставки и корреляции нужных событий                  |

[Architecture document](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/docs/architecture.md) помечает часть архитектуры как замысел и содержит целевые показатели. Для оценки необходимых ресурсов измерьте свою активную и простаивающую нагрузку, хранилище и выбранную среду изоляции. У Actor собственный жизненный цикл; Worker связан с инфраструктурой Kubernetes. При перемещении Actor остаётся тем же логическим экземпляром, но меняет место исполнения.

Для проверки безопасности начните с угроз и найдите место, где контролируется нужное действие. UID в префиксе объекта помогает различать владельцев, а право доступа определяют отдельные проверки. [Threat model](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/docs/threat-model.md) объясняет угрозы и предлагаемые защитные свойства. Испытание изоляции должно проверять конкретное свойство в разрешённой учебной среде.

Для наблюдения сопоставьте [observability guide](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/docs/observability.md) и [metric registry](https://github.com/agent-substrate/substrate/blob/ccecc788a327dc11dcd6c21ee153f3d0cbb5cc97/docs/metrics/substrate.yaml). Чтобы после перемещения среды сохранить историю журналов, нужен центральный сборщик. Связь прикладных строк с trace зависит от того, как приложение передаёт контекст. В реестре указаны пробелы метрик хранилища и кеша Worker. Такие участки требуют дополнительной проверки, даже если оповещений нет.

## A.8 MCP: составить профиль совместимости

При выборе MCP-клиента и сервера начните с нужного сценария. Запишите редакцию протокола, транспорт, сборки SDK обеих сторон, схему инструмента и необходимые дополнительные возможности. Успешный короткий вызов чтения ещё не проверяет продолжение долгой операции.

[MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/index) передаёт версию протокола и возможности клиента в `params._meta` самодостаточных запросов. Сервер обязан поддерживать [server/discover](https://modelcontextprotocol.io/specification/2026-07-28/server/discover); решение заранее запрашивать сведения о нём остаётся за клиентом. В [revision 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) стороны согласуют работу через `initialize` и `notifications/initialized`. Прежде чем оценивать порядок сообщений сохранённой трассы, установите её редакцию протокола.

При переходе между редакциями составьте таблицу возможностей вашей пары. Проверьте разрешённое чтение, ошибочный вход и понятный отказ несовместимому запросу. Проверку доступа дополните успешным контрольным вызовом и отказом постороннему субъекту: ошибка соединения сама по себе не доказывает работу авторизации. Для записи сначала определите, как установить исход после потери ответа, затем испытайте этот путь на имитаторе или разрешённом ограниченном объекте.

В [Streamable HTTP этой revision](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) удалены сессии уровня протокола. Прикладные идентификаторы операций, права и устранение повторных эффектов продолжают жить по своим правилам. Discovery возвращает сведения о сервере; доверие к его адресу и разрешение выполнить инструмент проверяются отдельно. Запишите эту границу при выборе адаптера, особенно если он автоматически повторяет запросы.

## A.9 Перед обновлением: что перепроверять и когда остановиться

Перед обновлением откройте сохранённое решение и выясните, какие его условия меняет новая сборка: API, разбор входа, формат снимка, секреты, правила доступа, адаптер модели или инструмента, настройки sandbox. Сравните соответствующие файлы старого и нового commits, затем прочитайте изменения и вызванные функции. Маленькая правка общей функции может изменить поведение сильнее, чем большая правка руководства.

Например, [Substrate v0.4.0 от 08.10.2026](https://github.com/agent-substrate/substrate/releases/tag/v0.4.0) перечисляет несовместимые изменения в упаковке rootfs, снимках durable-dir и выводе событий Actor. По этим заметкам можно выбрать файлы для сравнения и сценарии повторной проверки. Опорный срез книги остаётся v0.3.0; совместимость снимков между ними здесь не испытывалась.

Различайте результаты проверки: `PASS` — критерий выполнен в заданных условиях; `FAIL` — наблюдение ему противоречит; `BLOCKED` — не выполнена необходимая предпосылка; `SKIPPED` — проверку не выполняли. Если обязательный критерий остался открытым, выпуск остаётся на `HOLD`. Решение можно пересмотреть после получения нужных свидетельств, сохранив предыдущую запись.

Аудит исходников можно закончить, когда на поставленный вопрос есть достаточный ответ, границы вывода записаны, а у оставшихся проверок есть ответственные. В нашем примере исправленная инструкция готова к разбору коллегой. Для выпуска ещё нужны сведения об установке и интеграционные сценарии главы 43. Удаление прежних снимков и изменение рабочих правил доступа требуют отдельного допуска.

## A.10 Самостоятельная работа и передача результата

Повторите разбор A.4, не меняя изучаемую систему. В карточке отделите число видов ресурсов внутри одного commit от изменения жизненного цикла между выпуском и следующим срезом. Для каждого расхождения укажите источник, механизм, действие оператора и оставшийся вопрос. В этом упражнении не нужны доступ к кластеру, модель или установка AX.

Если следующий вопрос касается независимости копии из Tag, перейдите к разбору C.8. По его результатам подготовьте план разрешённого испытания восстановления с синтетическими данными. План получает `NOT_RUN`, пока опыт не выполнен: вывод по исходникам и результат испытания записывают отдельно.

Передайте карточку коллеге. Он должен открыть те же объекты Git, найти указанные функции и поля и объяснить принятое решение. Если ему приходится угадывать версию или смысл слова «работает», уточните запись. Результат аудита понятен, когда другой инженер знает, что можно сделать сейчас и какое свидетельство нужно для следующего шага.

Приложение B переводит эти выводы в критерии допуска. Приложение C помогает найти первичные источники для других вопросов. Вместе они поддерживают рабочий цикл: выбрать важное утверждение, разобраться в механизме, проверить нужный сценарий и сохранить основание решения.
