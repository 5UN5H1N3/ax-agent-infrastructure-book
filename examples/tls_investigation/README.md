# Расследование TLS по подготовленным наблюдениям

Практикум главы 3 помогает выбрать следующее чтение, сопоставить наблюдения и
решить, достаточно ли их для вывода. Сначала откройте initial, запишите следующий
запрос и ожидаемые различия между гипотезами. Затем откройте нужную карточку.
Не начинайте с key: программа выдаёт готовый ключ, а не оценивает ваш ответ.

Два случая независимы: это разные состояния учебной среды, не одна хронология.
Всё содержимое cases.json синтетическое. Время, адреса, ответы resolver и
результаты проверки цепочки заданы автором. Программа только читает соседний
файл: не создаёт сертификаты, не проверяет подписи, не обращается к сети,
модели или AX, не запускает таймер, reload и scheduler. L1/I1/R1 — метки
сертификатов, не настоящие fingerprints или PEM. Revocation не оценивалась.

Дополнение опубликовано отдельным закреплённым срезом. Ссылки и команды получения
полной копии находятся во входе «Расследование TLS по данным» главы 0.
Старые закреплённые срезы каталога и L01–L05 не содержат этих файлов;
новое дополнение не относится к прежним commit.
Проверено на Linux x86_64 и Python 3.13.5; нужна только стандартная библиотека.

## Получить наблюдение

Из корня полной рабочей копии книги:

```sh
python3 -m examples.tls_investigation.exercise --case chain
python3 -m examples.tls_investigation.exercise --case chain --packet peer
python3 -m examples.tls_investigation.exercise --case chain --packet inventory
python3 -m examples.tls_investigation.exercise --case chain --packet verify
python3 -m examples.tls_investigation.exercise --case dns
python3 -m examples.tls_investigation.exercise --case dns --packet dns
python3 -m examples.tls_investigation.exercise --case dns --packet address_control
python3 -m examples.tls_investigation.exercise --case dns --packet cache
python3 -m unittest discover -s examples -p 'test_ch03_tls_investigation.py' -v
```

| Случай | Доступные карточки | Что требуется объяснить |
| --- | --- | --- |
| chain | initial, dns, peer, inventory, verify, history | Почему один leaf проходит на западе и не проходит на востоке |
| dns | initial, dns, address_control, cache | Почему правильный SNI ещё не означает правильное назначение |

Обычный просмотр печатает одну карточку и заканчивается с кодом 0. Это успех
чтения файла, не доказательство исправности TLS. Неизвестная карточка даёт код 2.
Количество вызовов viewer не является счётчиком budget harness: этот код не
реализует agent loop. Контракт такого loop и места его остановки — в главе 3.

Перед ключом напишите пять коротких пунктов: следующий tool и его вопрос;
вывод с ID наблюдений; отвергнутая гипотеза; оставшаяся неопределённость;
следующее состояние run. Причина выбора важнее совпадения порядка карточек.

## Ключ случая chain

A0 показывает правильное имя и срок действия L1 на момент наблюдения. Это
исключает expiry именно для показанного leaf и времени, но не доказывает всю
цепочку. Ошибка issuer_unavailable допускает как нехватку intermediate,
так и неподходящее хранилище доверия. Поэтому peer — сильное следующее чтение:
в A2 восток передаёт L1, запад — L1 и I1. A3 задаёт связь L1 → I1 → R1.
Одного совпадения имён issuer и subject недостаточно для проверки подписи.

A4 — подготовленное сравнение при одинаковых времени, имени, trust anchor R1
и правилах strict-r1. Добавлен только I1 как недоверенный строительный материал
цепочки, а не новый trust anchor; path_ok меняется с false на true. Это
различает две причины. В этих наблюдениях восточному peer не хватает I1 для
этого профиля клиента. Root R1 не требуется передавать с сервера только потому,
что он завершает путь доверия: клиент уже хранит его отдельно.

A1 связывает DNS с фактическим dial и снимает подозрение на старое назначение
для этой пары probes. A5 объясняет, почему проблема появилась: r17 после 09:55
отдаёт только L1; r16 содержала L1/I1 с тем же serial leaf. Один serial не
определяет полный bundle. Альтернативный порядок inventory → peer → verify
также разумен. Начать с DNS полезно, если ещё не известно, куда реально попал
клиент. Повторять одинаковый failed probe без нового вопроса неинформативно.

Итог — предложение для east/api.example.com: при актуальной r17 заменить
bundle на L1/I1, не выпускать новый leaf и не добавлять случайный CA клиентам.
Rollback — сохранённая r16 после сверки её пригодности. До любого изменения
нужны повторное чтение revision, актуальные права и approval точного diff.
Run находится в WaitingForApproval; исправление не выполнено. Для Succeeded
нужны новые независимые probes и окно error rate, которых в наборе нет.

Если inventory и verify недоступны и других разрешённых источников нет,
сохраните A0/A2, сформулируйте подозрение и завершите Blocked с запросом
недостающих данных. Не превращайте предположение в подтверждённую причину.

## Самостоятельный случай dns и его ключ

B0 содержит две цепочки с path_ok=true, но у востока SAN не содержит ожидаемое
имя. В ClientHello записан именно api.example.com. Повтор «с правильным SNI»
не меняет этот факт. Сначала получите DNS и сопоставьте ответ с dial. B1
показывает: authoritative и запад знают 198.51.100.20, восток ещё использует
192.0.2.10. В B2 тот же восточный клиент, имя и trust anchors проходят проверку
на новом адресе. Изменён только dial. Это локализует различие назначения,
но не проверяет обычный DNS-путь и ещё не объясняет причину старого ответа.

B3 позволяет сделать более точный вывод. Запись получена в 09:57:30, до смены
authoritative в 09:58:00. Исходный TTL 300 s заканчивается в 10:02:30. На момент
B1, 10:00:10, остаётся 140 s. В заданной policy нет serve-stale и TTL override:
это ещё допустимое кэширование старого адреса, а не доказанный сбой resolver.
Изменение authoritative не очищает уже полученные клиентские записи.

Разумный следующий шаг — ограниченное ожидание, затем чтение DNS и TLS через
обычный путь east в 10:03:00. Owner ожидания — incident-workflow, deadline —
10:04:00. Run находится в WaitingForTool, не в Succeeded. Таймер здесь не
реализован. Отключение проверки hostname, выпуск сертификата и новый DNS write
не следуют из этих данных. Если после срока адрес остаётся старым, откройте
новую ветку: фактический resolver приложения, его cache policy и наблюдения
после срока. Не переиспользуйте старое объяснение автоматически.

Без B3 можно утверждать различие назначения, но нельзя уверенно объяснять его
старым TTL. Допустимо сначала получить cache/history, а не выполнять B2;
важно явно назвать, какую неопределённость снимает каждое чтение.

Полные ключи доступны явно:

```sh
python3 -m examples.tls_investigation.exercise --case chain --key
python3 -m examples.tls_investigation.exercise --case dns --key
```

## Следующий опыт и границы

Для настоящего локального TLS с временными CA используйте отдельно программу
главы 40. Она показывает другие сетевые границы и не воспроизводит эти пакеты
или incident из двух регионов. Перенос в Actor требует проверки реального
пути gateway и DNS; здесь прямое соединение без посредника задано условием.
Успех tests означает согласованность карточек и viewer, не качество модели,
полную PKIX conformance или восстановление сервиса.

Нормативная опора: [TLS certificate list, RFC 8446 §4.4.2](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.2),
[SNI, RFC 6066 §3](https://www.rfc-editor.org/rfc/rfc6066.html#section-3),
[срок сертификата, RFC 5280 §4.1.2.5](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.5),
[TTL записи, RFC 1035 §4.1.3](https://www.rfc-editor.org/rfc/rfc1035.html#section-4.1.3).
Наблюдения и конкретные verdicts не заимствованы из этих RFC: они синтетические.
