# Первый модельный профиль для harness и eval

Этот маршрут продолжает L01/L02: известные `batching.py` и пять заданий остаются
теми же, но вместо подготовленных ответов можно подключить собственный сервер.
Паспорт помогает зафиксировать, **какую именно связку** вы пробуете, и отделить
проверку файлов от качества объяснений. Общая теория и заполненная карточка —
в главе 20; расчёт памяти связан с главой 41, CPU-практика — с Lab 11.

Файлы `examples/model_profile/` относятся к дополнению L03; закреплённый срез
для новой учебной копии указан во входе в практику главы 0 опубликованной книги.
Старые срезы 51572b91 и 7d927c1a не содержат этого дополнения. Сам код L01/L02
сохранён без изменений; паспорт проверяет его SHA256, включая корпус и fixtures.

## Что выбрано и что известно

`qwen3_06b_profile.json` описывает учебный кандидат
`qwen3-06b-q8-cpu-learning-v1`: официальный `Qwen/Qwen3-0.6B-GGUF`, Q8_0,
CPU, один slot, context 8192, f16 K/V, non-thinking, non-streaming.
Назначение — первый синтетический read-only опыт, не production-рекомендация.

- GGUF revision: `23749fefcc72300e3a2ad315e1317431b06b590a`.
- Файл: `Qwen3-0.6B-Q8_0.gguf`, 639446688 bytes.
- Ожидаемый SHA256: `9465e63a22add5354d9bb4b99e90117043c7124007664907259bd16d043bb031`.
- Лицензия издателя: Apache-2.0; сохраняются LICENSE поставки и исходной модели.
- Справочная ревизия исходной модели: `c1899de289a04d12100db370d81485cdf75e47ca`.
- llama.cpp: `6e66cb5d4e9a2b4f02820a9f3053422b92ec4d51`, профиль книги не обновлялся.

Карточка GGUF указывает имя исходной модели, но не точный commit, из которого
сделана конверсия. Поэтому `conversion_parent_revision=null`: справочный
snapshot не выдан за доказанную историю конверсии. Для более строгой политики
поставки потребуется проверяемый conversion manifest либо собственная конверсия.

Авторская проверка сверила закреплённые небольшие файлы и метаданные из первых
8 MiB GGUF по ограниченному HTTP Range; метаданные заняли 5932855 bytes.
Полный файл не скачивался, его SHA здесь взят из LFS-метаданных издателя и остаётся
**ожидаемым** до локальной проверки всех байтов. Модель и runtime не запускались.

У издателя есть расхождение описаний: карточка заявляет context 32768, а GGUF
metadata и справочный config содержат 40960. Оба числа сохранены в паспорте.
Выбранные 8192 ниже обоих; проверку максимального context этот опыт не заменяет.
Первичные закреплённые источники: [карточка GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF/blob/23749fefcc72300e3a2ad315e1317431b06b590a/README.md),
[config](https://huggingface.co/Qwen/Qwen3-0.6B/blob/c1899de289a04d12100db370d81485cdf75e47ca/config.json),
[server README](https://github.com/ggml-org/llama.cpp/blob/6e66cb5d4e9a2b4f02820a9f3053422b92ec4d51/tools/server/README.md).

Встроенный template имеет SHA256
`57f1fd00f0013a2be96aa79b857391f27e23df5b5f847072b524c897e24d0361`,
а справочный `source-tokenizer_config.json` — template с SHA256
`a55ee1b1660128b7098723e0abcd92caa0788061051c62d51cbe87d9cf1974d8`.
Это два разных текста. Сервер использует **встроенный** template; внешний
tokenizer/template в GGUF-поставку не подмешивается. Сам GGUF SHA связывает
зафиксированные сведения о встроенном шаблоне с известным файлом. Скрипт —
проверка этой конкретной карточки, не универсальный анализатор неизвестного GGUF.

## Первый шаг без модели и сети

Запускайте из корня рабочей копии книги, Python 3.13.5 — проверенная версия.
Для файловой проверки и сбора ответов нужны POSIX и доверенные каталоги.

```sh
python3 -m examples.model_profile.profile
python3 -m examples.model_profile.profile --plan
python3 -m unittest discover -s examples -p 'test_ch20_model_profile.py' -v
```

Первая команда показывает паспорт, статусы допуска и memory sheet. Вторая
**печатает**, но не выполняет команды получения шести файлов, сборки и запуска
сервера. Нет скрытой загрузки весов, установки библиотек или обращения к API.
Unit tests используют маленькую искусственную поставку и локальный HTTP mock.

## Получить и проверить поставку

Из `--plan` возьмите блок `download_commands_not_executed`: он создаёт новый
`ax-first-model` и скачивает GGUF, MODEL_CARD, два LICENSE и два справочных JSON.
Каждый URL содержит полный commit. Команды требуют `curl`, HTTPS, около 640 MB
для модели плюс запас на runtime, сборку и результаты. Каталог не должен
существовать; `set -eu` останавливает блок при ошибке. Проверьте допустимость
лицензии и происхождения по правилам вашей команды до загрузки.

Затем, из корня книги:

```sh
python3 -m examples.model_profile.profile --check ./ax-first-model
```

Проверка открывает только шесть названных обычных файлов, без конечных symlink,
сверяет размеры и SHA256, GGUF v3 header и справочную архитектуру/template.
Каталог и его родители должны быть доверенными, файлы нельзя менять параллельно.
Полный GGUF читается потоково для hash, но не загружается в inference runtime.
Успех даёт `delivery=VERIFIED_LOCAL_BYTES`; interface, quality и capacity остаются
`NOT_RUN`. Неверный формат, размер, hash или reference завершают проверку кодом 2.

У upstream Safetensors другой loader: переименование `model.safetensors` в
`.gguf` не создаёт GGUF. Для llama.cpp нужна корректная конверсия; для vLLM-пути
главы 41 — отдельная полная HF/Safetensors-поставка с её собственным паспортом.

## Собрать runtime и запустить endpoint

Блок `build_commands_not_executed` из плана получает отдельный `llama-l03`,
переключает его на закреплённый commit и собирает `llama-server` через CMake/C++.
CUDA, Vulkan, Metal и native-only оптимизации явно выключены. Путь не должен
существовать. Требования компилятора и зависимостей сверяют в закреплённом README
llama.cpp; этот companion их не устанавливает.

Сохраните build options, версию компилятора, `llama-server --version`, SHA256
бинарника, CPU/OS и свободную RAM рядом с карточкой. Hash бинарника фиксирует
полученный файл, но сам по себе не доказывает происхождение из нужного source:
для этого нужен сохранённый ход сборки. В исходном паспорте binary SHA и имя
реально выбранного format handler намеренно пусты.

`server_command_not_executed` запускает listener на 127.0.0.1:8080 с alias
`review-code`, одним slot, двумя CPU threads, context 8192 и f16 K/V.
`--jinja` включает работу шаблона; `--reasoning off` выбирает non-thinking для
этого короткого опыта. Это не то же самое, что скрыть reasoning в выдаче.
Sampling записан явно: temperature 0.7, top_p 0.8, top_k 20, min_p 0,
presence_penalty 1.5, seed 42. Seed не обещает воспроизводимость между разными
сборками и устройствами; реальные генерации всё равно повторяют.

После запуска отдельно проверьте `/health` и `/v1/models`, сохраните startup log
с фактическими backend, context и template/handler. Успешный health ещё не
означает работающий tool use. Тот же HTTP alias может скрывать другую модель,
поэтому клиентский сборщик не аттестует содержимое endpoint.

## Проверить harness и собрать новые ответы

Для одного цикла достаточно неизменённого L01:

```sh
python3 -m examples.learning_harness.harness \
  --base-url http://127.0.0.1:8080/v1 --model review-code \
  --allow-source-upload --seconds 120
```

Он использует свой синтетический временный `batching.py`. Если нужен исходный
проект Lab 10, добавьте его доверенный `--root`. Предел 120 s выбран для первого
CPU smoke, не как обещание интерактивной latency. Server defaults должны
совпадать с паспортом; harness по-прежнему ограничивает 3 model calls, 2 чтения
и просит до 512 output tokens на запрос.

Для пяти задач L02 создайте **новый** каталог отчёта:

```sh
python3 -m examples.model_profile.profile \
  --collect-eval ./first-model-review \
  --base-url http://127.0.0.1:8080/v1 --allow-source-upload
```

В `review.json` попадут полный профиль, hash корпуса, новые цели, trace,
ограниченные сырые ответы endpoint, заявленный им usage и время каждого run.
Все поля `assessment` пусты: оцените новые ответы по смыслу и trace, используя
рубрику главы 2. Подготовленные ответы `careful/cheap/fluent` и их баллы не
копируются. `answered` и код 0 у сборщика означают только, что все проходы дали
форматный финал; они **не означают** правильные объяснения.

Заблокированные proposals и неверные ответы сохраняются для разбора, итоговый
код будет 2. Транспортная ошибка или deadline останавливают весь сбор, оставшиеся
задачи отмечаются `not_run`: повторять 401 по всем входам незачем. Каталог нельзя
перезаписать, в том числе через symlink. Незавершённый каталог после ошибки I/O
нужно осмотреть, а не считать завершённым отчётом.

`--repeat 3` даст три прохода по пяти заданиям, каждый с новой историей; максимум
45 model calls. Это ограниченная учебная серия, не оценка частоты редких ошибок.
По умолчанию проход один. Прикладной deadline прекращает ожидание клиента,
не гарантируя остановку серверной генерации. Денежный лимит и server-side cancel
в этом adapter не реализованы. Non-streaming время всего run нельзя назвать TTFT;
usage сохраняется как сообщение endpoint, не как доказанный счёт provider.

## Как заполнить следующий паспорт

Для другого кандидата начните с задачи, допустимого формата и лимитов, затем
выберите и закрепите целую поставку. Получите точные bytes/hash и лицензию у
издателя, проверьте metadata артефакта подходящим upstream reader, отдельно
сохраните tokenizer/template, runtime build и способ разбора tool calls.
Числа memory sheet берут из config/metadata, а не из названия модели.

В Qwen3-0.6B `head_dim=128`, тогда как 1024/16=64. Для одного slot 8192 и f16
K/V идеализированный KV равен `2*28*8*128*8192*2 = 939524096 bytes` (896 MiB).
Файл занимает около 0.596 GiB, KV — 0.875 GiB, сумма — около 1.471 GiB.
Это арифметический ориентир: размер файла не равен resident weights, а buffers,
alignment, runtime, startup/prefill peaks и ОС здесь не посчитаны. 4 GiB свободной
RAM — стартовый учебный бюджет для проверки, не измеренное требование.

Неизвестные поля оставляйте пустыми с причиной и следующим испытанием. При смене
формата, template, quantization, runtime, context или sampling меняется профиль:
сначала поставка и интерфейс, затем ручной eval и только потом capacity/SLO.
