# Сквозной read-only harness и разобранный eval

Этот companion соединяет главу 4, оценку ответов в главе 2, транспорт главы 20
и локальную часть Lab 10. Запускайте из корня **той же редакции книги**:
старый срез 51572b91 содержит 39 прежних программ, но не этот новый каталог.
Точный срез companion закреплён отдельной ссылкой во входе в практику и главе 4.
Локальные запуски ниже используют подготовленные ответы, а не настоящую модель.

Требуются POSIX, Python 3.13.5 (проверенная версия), main thread, разрешённый
loopback и временный каталог. Сторонних пакетов, AX, GPU и ключей не нужно.
На Windows без POSIX-окружения таймер и файловые flags не поддерживаются.

## Первый запуск

```sh
python3 -m examples.learning_harness.harness
python3 -m examples.learning_harness.harness --scenario denied
python3 -m examples.learning_harness.harness --scenario budget
python3 -m examples.learning_harness.evals
python3 -m unittest discover -s examples -p 'test_ch04_learning_harness.py' -v
```

Ожидаемые итоги: `answered`, `blocked`, `budget_exhausted`. Первый завершается
с кодом 0; два ожидаемых отказных опыта — с кодом 2. Eval завершается с кодом
0, когда все подготовленные обмены воспроизводятся, **даже если кандидаты
отклонены**: их решения перечислены в `accepted_for_next_trial`. Тесты — OK.

Без `--root` программа создаёт собственный временный `batching.py`, читает
его и убирает каталог при штатном выходе. Loopback HTTP mock выдаёт заранее
подготовленные предложения и ответ именно для дефектного fixture. Он не
анализирует произвольный файл. Чтобы читать проект Lab 10, укажите его
доверенный каталог через `--root /absolute/path/ax-lab32-batching`; штатный
mock-ответ содержательно применим только к исходному, ещё не исправленному
`batching.py`. Для оценки новой версии используется отдельный case C5.

В `trace` видны `model_request`, `tool_proposed`, `tool_allowed`, `tool_result`
и `final_received` либо `stop`. Второй запрос сохраняет сообщение assistant
и результат tool с тем же `tool_call_id`. SHA256 относится к прочитанным
байтам, а не к Git commit или доказательству неизменности всей рабочей копии.
Trace содержит текст файла: в примере допустим только синтетический код.

## Что ограничивает контроллер

`run` допускает до 3 обращений к модели и 2 чтений. Неверный ответ тоже
расходует обращение. `read_file` разрешает только `batching.py`, не принимает
дополнительные поля, не следует конечным symlink и читает не более 4096 bytes
обычного UTF-8 файла. Каталог и его родители должны быть доверенными; менять
файл одновременно нельзя. Это не sandbox против владельца ОС.

У завершённого ответа проверяются формат и наличие чтения, но **не смысл**.
`answered` означает «получен ответ после чтения», а не «задача решена правильно».
Даже текст с выдуманным запуском тестов может пройти форматный контроллер;
этот дефект должен попасть в оценку ответа.

На ответ HTTP отведено 16384 bytes, на финальный текст — 4096; каждый запрос
просит `max_tokens=512`. Ограничение bytes не заменяет tokens и денежный лимит
сервера. Общий локальный deadline по умолчанию 5 s реализован через POSIX
SIGALRM, охватывает синхронный цикл и ожидание HTTP. Нужны main thread и
свободный таймер. При остановке удалённая генерация может продолжаться и
оплачиваться: это не server-side cancellation. Встраиваемому сервису нужен
собственный механизм deadline/cancel и авторитетный учёт usage.

Ретраев нет. 401, 429 и другие HTTP-ошибки завершают опыт с причиной и кодом
HTTP в trace. Не печатаются URL с credential или тела ошибок. Путь чтения и
схема проверяются кодом; текст system prompt лишь объясняет контракт модели.
Повторение разрешённого чтения расходует остаток бюджета, не расширяя права.

## Собственный разрешённый endpoint

```sh
python3 -m examples.learning_harness.harness \
  --root /absolute/path/ax-lab32-batching \
  --base-url http://127.0.0.1:8080/v1 \
  --model review-code --allow-source-upload --seconds 30
```

Тот же контроллер отправляет выбранному endpoint цель, schema, затем прочитанный
файл и его hash. Флаг подтверждает именно эту передачу. Не используйте секреты
и чужой код. Поддерживается только узкий non-streaming контракт из главы 20,
без auth, redirect, proxy из окружения и fallback. Model ID должен существовать
на вашем сервере. Для cloud-сервиса с авторизацией нужен отдельно проверенный
adapter и безопасный credential path; в URL и этот пример ключ не помещают.
Пригодность конкретной модели этими локальными проверками не установлена.

## Как читать eval

`cases.json` задаёт 5 входов, разрешённые действия, обязательный смысл и 15
специально написанных ответов трёх вымышленных кандидатов. Полные исходники
входов определяет `SOURCES` в `evals.py`: fixture Lab 10, он же с враждебным
комментарием, и вариант с исправленной границей. Каждый обмен проходит через
HTTP mock и **тот же** `run`, фактически читает свой файл и возвращает его
результат во второй запрос. Полученный ответ, статус и источник сверяются
с образцом перед показом оценок.

Числа `[quality, faithfulness, conduct]` — опубликованные **ручные аннотации**.
Каждая ось имеет шкалу 0–2; точные правила и причины находятся в JSON и главе 2.
Это не keyword grader и не LLM-as-judge. Программа воспроизводит разбор, а не
умеет автоматически понять новый текст. На новой модели сохраняйте реальный
trace и оценивайте её ответ заново по required и rubric, не подставляя готовый
балл по ID задачи. SHA без правильного содержания не даёт положительной оценки.

Суммы: careful 30/30, cheap 17/30, fluent 24/30. У cheap один запрещённый
proposal, фактическое чтение секрета предотвращено. У fluent правильные на вид
объяснения содержат выдуманный тест и неверную ревизию. Для этого узкого опыта
следующий этап допускает только кандидат с 2 по каждой оси каждого case;
это учебный критерий, не универсальный production threshold.

У каждого кандидата фактически 10 mock-запросов и 5 разрешённых чтений.
Дополнительно показаны **вымышленные** расходы 1.0/0.4/0.7 условной единицы:
они нужны лишь для разбора «дешевле не значит пригодно». Цена, tokens, latency
и качество настоящих моделей здесь не измерены. `careful` принят только к
следующему испытанию, не в production.

Для нового case сначала задайте цель, полный вход, разрешённые действия и
обязательный смысл. Затем независимо напишите ответ и разбор баллов. Перед
переносом аннотаций на новую формулировку проведите повторную ручную оценку.
Для живого сравнения зафиксируйте model revision, template, prompt/schema,
server config и budgets; дайте обоим вариантам одинаковые задачи, скройте
имя кандидата от проверяющих и разберите расхождения двух оценщиков. Вынесите
новые случаи в закрытую проверочную часть, повторите реальные генерации и
покажите разброс. Пять известных примеров не оценивают частоту редких ошибок.
